Agents claim. The controller decides.

The controller is ordinary code, not a language model. It starts each run, waits for it, and writes down what happened.

An agent can say anything: "I committed abc123", "the tests pass", "PASS". Each of those is a claim. The controller checks what it can, and only then turns the claim into an event in the log.

From there, apply decides the next stage. No agent ever changes a stage itself.

What the controller does for every run

  1. Mints a run ID. For a developer, records a claim event first.
  2. Starts the adapter with a deadline.
  3. Takes whatever comes back, and makes it plain data.
  4. Writes exactly one event: a result, a verdict, or run_failed.

"Exactly one" holds even when the adapter crashes, hangs, lies or returns rubbish. The lab below tries all of those.

The adapter seam

An adapter has one job: start one run and settle with an outcome. It knows nothing about cycles, stages or events.

There are only three outcomes: completed with a claim, failed with a reason, or cancelled. The claim is unchecked JSON. The controller classifies it.

That is why the factory can swap claude for pi, or for a test double, without touching the lifecycle. how a CLI becomes an adapter


  






  
Every run has a deadline

  
A runtime can simply never answer. The 03-a spike saw claude -p fail to return for a one-turn prompt in four runs of ten. So execute refuses to start a run without a deadline.

  
bounded races the adapter against a timer. When the timer wins, the outcome is failed: timeout, and only then is the adapter told to abort. Whatever the adapter does afterwards lands on a promise that has already settled, and is dropped. So even an adapter that ignores the abort cannot hold a cycle.

  
Why not just await the adapter? Because a throw inside start(), a rejection, a late answer and no answer must all become one well-formed event. bounded turns all four into an outcome.

One run, one outcome

  
receive can be called twice for the same run, for example after a restart. The store keeps one outcome per run ID: a second result, verdict or run_failed for that run writes nothing and returns the cycle as it is. the event log

  
Reviewer runs also check the stage before they start. A verdict is counted against whatever review stage the cycle is in, so a reviewer run in the wrong stage would be miscounted. That is a controller bug, so it throws instead of escalating.

Takeaway

  
Whatever an agent does, the controller writes exactly one well-formed event for its run. Only then does the state machine decide what that event means.
