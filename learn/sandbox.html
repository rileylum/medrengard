Candidate code is untrusted

The factory runs code nobody has reviewed yet: the developer's commit, its tests, its build scripts. Any of it could be wrong, and some of it could be hostile.

So everything that touches candidate code runs inside a sandbox: bubblewrap, a small Linux tool that starts a process in its own namespaces and shows it only the directories it is given.

The defences need not be airtight (A-037). What matters first is that a run cannot damage the owner's machine or leave its remit; malicious code comes second.

Everyone gets

  • The system directories (/usr, /etc, /opt…) read-only
  • A private /tmp
  • An empty environment: only PATH, HOME and LANG
  • No view of the owner's home, other runs, or the repository's .git

The owner can add read-only roots with sandbox.read in the job file, for a toolchain outside /usr.

Try it: build a policy

Each stage builds a Policy for what it spawns. The factory's wrap turns it into the bubblewrap command line. Pick who runs, then change anything: add a write root, turn the network on, switch the backend to none. The table on the right shows what the command can then see.

Put a relative path, or one that does not exist, into sandbox.read: checkSandbox refuses at setup rather than failing every check later.

The rogues' gallery

Each of these was found by an adversarial reviewer trying to break the factory, then closed by a ticket. Together they are why the sandbox looks the way it does.

A committed symlink

A check followed a symlink in the commit and read the developer's worktree next door.

Now: checks run in bwrap and see only the checkout.

Git that obeys the candidate

A check wrote a .git pointer or set core.hooksPath, so the controller's own Git read state the candidate chose.

Now: the checkout has no .git; Git uses the repository's git dir and a private index.

07-b · 08-a

A formatter in disguise

A check rewrote a tracked file, so the reviewers would read something other than the commit.

Now: the controller's tree check FAILs with the changed paths as evidence.

06-c · 07-c

Locked doors

A check removed its own read permission on what it rewrote; Git skipped the file with a warning and exit 0.

Now: owner access is restored before comparing, and Git's warnings count as dirt.

08-b

Gitlinks and dangling links

A committed submodule entry and a symlink to nowhere survived the clean-up before review.

Now: gitlinks are emptied and checked, dangling symlinks removed.

08-d

A FIFO where a file should be

A named pipe left where Git opens a file blocked the controller's Git forever, and with it every deadline.

Now: every controller Git call over a tree a run wrote is killed at the stage deadline.

08-e · 08-f

Typing into the owner's terminal

A process sharing the controller's terminal can push keystrokes into it with the TIOCSTI ioctl.

Now: --new-session.

08-a findings

Tokens in the environment

The controller's environment may hold API tokens and the owner's settings.

Now: --clearenv, then only PATH, HOME and LANG.

bwrap or none

The job file names the backend; the default is bwrap. none runs candidate code as the owner, unconfined, and must be written out. The seam is small on purpose: Docker, a VM or a cloud runner would be further cases of wrap and checkSandbox, and nothing else would change.

Before the paid developer run starts, the loop calls checkSandbox. It starts a trivial command in bubblewrap. If that fails (no bubblewrap, no unprivileged user namespaces), the run stops at setup instead of failing every check as if the candidate were wrong.

Takeaway

  
Every process that runs candidate code gets a box built for its job: write only what it must, read only what it needs, no network for checks, no environment, no terminal. The box is one function, so it can change backend without touching the rest.
