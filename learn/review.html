Fresh eyes, nothing but the evidence

A reviewer is a new agent run that has never seen the developer at work. It reads what the controller hands it, and returns a verdict bound to one SHA.

Why fresh? A reviewer who reads the developer's reasoning tends to agree with it. A reviewer who only has the ticket and the diff has to check the work itself.

It gets

  • The ticket
  • AGENTS.md, read from the candidate commit
  • Each check's result
  • Every changed path
  • The diff, base to head
  • The evidence files
  • A read-only checkout of the commit

It never gets

  • The developer's transcript
  • The developer's clone
  • A shell, or any write
  • The owner's settings, hooks or MCP servers

The controller has no transcript to leak: the adapter keeps only the claim.

Two kinds of reviewer

Standard

"Judge the diff against the ticket, the repository instructions and the verification evidence." PASS only if every requirement is met by the diff and shown by the evidence. A FAIL must name a file and a line.

Up to two per cycle. The first FAIL sends the findings back to the developer for one fix run.

Adversarial

"Your job is to break it: find inputs, sequences or states under which it does not do what the ticket says, and report what you can show."

One per cycle, after a standard PASS. A FAIL stops the cycle at once: there is no second chance.

Both end their reply with the same claim: {"head": "<sha>", "verdict": "PASS" | "FAIL", "findings": [...]}. A verdict for any other SHA is recorded and counted, but cannot move the cycle.

Try it: spend the budget

Every cycle has a budget of two standard reviews and one adversarial review. Pick each verdict. The events go through the factory's real apply, which moves the cycle and the counters.

Counters never go down. A fix run does not reset them: the second standard review is the last. After an escalation only the owner can go on, by cancelling or by opening a child cycle with its own fresh budget.

Try it: the reviewer's prompt

This is the prompt the factory's own buildPrompt writes for a candidate in the simulator's todo repository. Click a section to jump to it.

Every section header carries a nonce: eight random hex characters, new for every run. The ticket, the commit and the evidence can hold any text, including a line that looks like a header. They cannot hold one with a nonce they have never seen. Press Hide a fake section in the ticket: the fake header is quoted text, and the prompt says so.

Try it: a diff too big to send

A model reads a prompt; it is not a log viewer. The diff is cut to its first and last 128 KiB, with a marker where the middle was. Each evidence file is cut the same way at 16 KiB a side.

What review refuses before it starts

A reviewer is never started on something the controller did not verify. review() throws, and the loop escalates with reject_dispatch, if:

  • the cycle is not in a review stage, or has no candidate;
  • the verify checkout is missing, or is not clean against the head (a check rewrote a file);
  • there is no verification event, or it is for another SHA;
  • any evidence file is missing.

The reviewer's runtime is locked down too. claude runs --restricted with only Read, Glob and Grep, and --strict-mcp-config. A .claude/settings.json committed in the candidate could otherwise add hooks that run as the owner. pi runs with read-only tools, --no-approve and --no-context-files. Both run in bubblewrap with the checkout read-only.

Takeaway

  
Two reviewers who never saw the developer work, one of them told to break it, each bound to one SHA. Three verdicts at most per cycle. Then a human decides.
