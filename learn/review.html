Fresh eyes, nothing but the evidence

A reviewer is a new agent run that has never seen the developer at work. It reads what the controller hands it, and returns a verdict bound to one SHA.

Why fresh? A reviewer who reads the developer's reasoning tends to agree with it. A reviewer who only has the ticket and the diff has to check the work itself.

It gets

  • Its stage's role text, then the ticket
  • AGENTS.md, read from the base commit, with a note when the candidate changes it
  • Every command stage's results for this head
  • Every changed path, and the commits
  • The diff, base to head
  • The evidence files
  • A read-only checkout of the commit

It never gets

  • The developer's transcript
  • The developer's clone
  • A shell, or any write
  • Your settings, hooks or MCP servers

The controller has no transcript to leak: the adapter keeps only the claim.

Two kinds of reviewer, by default

A review stage is an agent stage whose role produces a verdict. The default workflow has two, and its role text is all that makes them differ:

STANDARD_REVIEW, budget 2

"Judge the diff against the ticket, the repository instructions and the verification evidence." Its first FAIL sends the findings back for a fix run.

ADVERSARIAL_REVIEW, budget 1

"Your job is to break it: find inputs, sequences or states under which it does not do what the ticket says." Its FAIL goes straight to ESCALATED.

Every reviewer ends its reply with the same claim: {"head": "<sha>", "verdict": "PASS" | "FAIL", "findings": [...]}. PASS only if every requirement is met by the diff and shown by the evidence; a FAIL must name a file and a line.

Every path through the budget

Each row is one way the verdicts can fall, played through the factory's real apply. Switch to the light workflow, with one reviewer and three tries, and the table is rebuilt from that workflow. How a budget counts is in Workflows.

Every path ends at a human stage or at ESCALATED: none goes round for ever, because the workflow had to spend a budget on its loop to be accepted at all.

Try it: the reviewer's prompt

This is the prompt for a candidate in the simulator's todo repository: gather in src/review.ts collects the parts, and reviewPrompt in src/prompt.ts words them. Click a section to jump to it.

Every section header carries a nonce: eight random hex characters, new for every run. The ticket, the commit and the evidence can hold any text, including a line that looks like a header. They cannot hold one with a nonce they have never seen. Press Hide a fake section in the ticket: the fake header is quoted text, and the prompt says so.

Try it: a diff too big to send

A model reads a prompt; it is not a log viewer. The diff is cut to its first and last 128 KiB, with a marker where the middle was. Each evidence file is cut the same way at 16 KiB a side, and the commit messages at 16 KiB.

What review refuses before it starts

A reviewer is never started on something the controller did not verify. review() throws, and the loop escalates with reject_dispatch, if:

  • the cycle is not at a review stage, or has no candidate;
  • the checkout from the last command stage is missing, or is not clean against the head;
  • there is no verification event, or the last one is for another SHA;
  • any evidence file is missing.

The reviewer's runtime is locked down too. claude runs --restricted with only Read, Glob and Grep, and --strict-mcp-config: a .claude/settings.json committed in the candidate could otherwise add hooks that run as you. pi runs with read-only tools, --no-approve and --no-context-files. Both run in the sandbox with the checkout read-only.
