Runtime, model and role are three different things

Runtime

The program that runs the agent: claude (Claude Code), pi, or one you add. The factory starts it as a child process.

Model

The language model behind it. The runtime picks it; the core of the factory never names one.

Role

What the run is for. The workflow names the roles: the default has a developer, a standard reviewer and an adversarial reviewer. The role sets the prompt and the permissions.

The job's runtime picks a runtime per role: {"developer": "claude", "adversarial": "pi"}. standard and adversarial stand for the default workflow's reviewer roles. Nothing in the engine knows which one ran: it sees an adapter and its outcome, and the outcome event records the runtime's name.

Chosen by name

Runtimes live in a registry, a map from name to entry. claude and pi are built in. A job or your personal file adds one more as a single TypeScript module:

"runtimes": { "local-llm": { "module": "runtimes/local-llm.ts" } },
"runtime": { "developer": "local-llm" }
  • The module gets the whole run request as JSON on stdin and prints one outcome as JSON on stdout, under the controller's own node, in the sandbox, with only its own folder bound: it must be one bundled file.
  • Its SHA-256 is read before any run and recorded on every outcome event as moduleHash, so the log says which code answered.
  • A name may not reuse a built-in one: claude meaning someone's module would hide which runtime ran.

Sandbox backends are chosen by name too, bwrap or none, but only from the built-in ones: a backend you could add would decide what confines candidate code (A-074).

A CLI becomes an adapter

One function, cliAdapter(spec), makes an adapter from a CliSpec. The spec is small: the command, its flags, the files of yours it needs to read, and a parse function. Everything else is shared: the sandbox, the process, the byte cap, the cancel.

  1. The prompt goes to the CLI on stdin.
  2. The CLI prints its answer on stdout: one JSON object (claude) or JSON Lines (pi).
  3. parse finds the model's reply in that, and the claim at its end.






  
Try it: finding the claim

  
The claim is the last fenced json block in the reply, or the whole reply if it is a JSON object. The fields are not checked here; the store does that. Write a reply, or pick a preset, and see what the real parser returns.

  

  
Why not a regex? The first version used one. On an unclosed fence followed by blank lines it backtracked for seconds, on the controller's event loop, holding every cycle past its deadline (04-d adversarial). The scan is now two indexOf calls from the end: the reply length is the only cost.

Starting and stopping the process

  

    

      
spawnRuntime starts the CLI in a systemd user scope named sf-<runId>. A scope is a cgroup: every process the run starts is in it, even one that left its process group with setsid (the 03-b finding).

      
To cancel, it sends SIGTERM, waits a grace period, then writes cgroup.kill: everything in the scope dies at once. It does the same after a normal exit, so nothing the agent started in the background survives the run.

Kits: the contract an extension must keep

  
Each kind of extension has a kit: a function you call from your own test file, run with node --test. It registers test cases that drive your extension the way the controller would. Import it by path; the factory is not a package.

  

    
KitForIt checks

    
      
runtimeKita runtime adapterit has a name; a request for each role settles, without rejecting, to a plain outcome; an aborted run settles within 10 s

      
commandKita command stage (command stages)a passing change gives PASS and a failing one FAIL, through the real verify; the request names every field; nothing is written outside output/ and the checkout; with network unset, a connection fails; a grant stage writes the head

      
observerKitan observer (the stream)your cases' actions, in order; an event type it does not know makes it neither throw nor act; a refused command does not make it throw
