This repository is built the way the factory builds

Until the controller can run its own lifecycle, people run it by hand. Each plan row becomes small tickets; each ticket gets tests first, two standard reviews at most, one adversarial review, and an owner who merges.

Same shape as a cycle, same budget, same rule at the limit: stop and ask the owner.

The rules that make it work

Tests first

"A spec sentence without a test is a proposal." Each ticket's done-when list becomes failing tests, committed before the code.

Independent verification

The owner runs npm test on the SHA. The implementer's claim does not count, exactly as a developer agent's does not.

Fresh reviewers

A review is a new claude -p session given the ticket, the diff, the SHA, the test output and AGENTS.md. Never the implementer's conversation.

Approvals are quoted

An owner decision is a reply quoted in docs/decisions.md with a date. Nobody may write one on the owner's behalf.

Every ticket, and what the reviews found

Read live from docs/work/. Each plan step became several tickets. Notice how often the adversarial reviewer broke something a standard review had passed: that is why it exists.

Fast or Design

After an adversarial FAIL

An adversarial FAIL stops the ticket. The owner then chooses, finding by finding, with the implementer's risk weighing (A-042):

  • Fix ticket: a new ticket that names the old one, with a fresh budget.
  • Park: merge, and the finding goes to docs/work/parked.md against the ticket that must close it. That ticket is not READY until its done-when list covers it.
  • Accept the risk: the finding goes to docs/work/accepted-risks.md with the reason and the event that would reopen it.
