Four layers, later wins

A job's settings come from four layers, read in order. Each may set some keys, and a later layer replaces what an earlier one set.

  1. Factory defaults: the runs directory and the bwrap sandbox.
  2. Your personal file, ~/.config/software_factory/config.json: runtimes, the sandbox, deadlines, grants. Missing is fine.
  3. The repository, .factory/config.json as committed at the base: its checks, its workflow, its runtimes.
  4. The job file: which work, which ticket, which repository, and anything to override.

How "replaces" works

runtime, runtimes, sandbox and grants merge one level down: the job can change the developer's runtime and keep the reviewers'. Every other key is replaced whole, lists included: a job's checks are all the checks.

What a repository may not do

The repository layer is the developer's to edit: a commit can change it. So it is read from the base commit with git show, never from the working tree, and it may set three keys only: checks, workflow and runtime. The list is an allow list, so a key added later is closed to repositories until someone opens it.

  • No sandbox. sandbox.read alone could show the sandbox your ~/.ssh, and none would turn it off.
  • No grants, and its workflow may not ask for one: a personal grant would otherwise reach any repository you clone (grants).
  • Its workflow must be a path inside the repository. The file is copied out of the base commit and imported from the copy, with the files its commands name beside it. It is imported only when a branch or tag outside sf/* contains the base, so a candidate you have checked out never runs. It runs unsandboxed in the controller, at import: an accepted risk (A-078).

Paths, the base, and later commands

  • A relative path resolves against the folder of the file that set it, before the merge: once merged, a value no longer knows which file it came from. The one exception is the job file's runsDir, which resolves against the working directory, as it always did.
  • The base is resolved to a SHA once, when the layers are read, and the repository layer is read at that SHA. The developer starts from the same commit, even if the branch moves meanwhile. The SHA is recorded on the cycle.
  • accept, cancel and events read the layers at the base the cycles recorded, not at today's tip: you may have merged since, and the new tip's workflow may not be the one the cycles were opened under.
