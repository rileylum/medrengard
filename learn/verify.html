The controller runs every command itself

A developer agent may say "all tests pass". That is a claim. The factory does not take it on trust.

In a command stage, the controller makes a fresh checkout of exactly the candidate commit and runs commands there. The developer never touches this checkout. In the default workflow the one command stage is VERIFYING, and its commands are the job's checks. A workflow may add stages with commands of their own: packaging, release notes, a merge.

Three rules for every command stage

  1. Fresh checkout, no .git. Only the commit's files. Nothing the developer left behind, and no Git state a command could rewrite.
  2. Evidence is bound to the SHA. Each command's stdout, stderr and exit go to runs/evidence/<head>/<stage>/. A new commit needs new evidence.
  3. Missing evidence is never PASS. A command that cannot run is MISSING, which fails the stage like a FAIL. So does an empty list.

Try it: build a command stage

Write a command stage and see what the controller would run, and what each command would be given. The made-up machine has npm and node in /usr/bin, ruff in the owner's ~/.local/bin, and no eslint; the candidate commits scripts/smoke.sh.

Try: set test to "exits 1". Add /home/owner/.local/bin to sandbox.read and watch fmt come back. Pick NOTES and edit the script: its hash in the event changes. Name a command tree.

PASS, FAIL and MISSING

ResultWhenWhat the exit file says
PASSThe command ran and exited 0.exit 0
FAILIt exited non-zero, ran past the deadline, or printed more than 8 MiB.exit 1, timeout, overflow
MISSINGIts binary is not on PATH, or it resolves outside what the sandbox can see.missing: eslint not found

MISSING is evidence that does not exist; FAIL is evidence that says no. Either takes the stage's FAIL transition, but you learn different things: MISSING says install a tool or add its directory to sandbox.read; FAIL says the candidate is wrong. The factory looks up the binary itself before it starts anything, so MISSING means the same under every isolation.

All commands run, in order, even after one fails. The evidence is for you and the reviewers, who want the whole picture.

A stage of its own

A command stage with run runs its own commands instead of the job's checks. This is how you add a step without writing a new kind of extension (D-024).

  • Names are file stems, unique in the stage, because each names its evidence files. tree is reserved for the controller's own check, below.
  • A file argument, { "file": "scripts/notes.js" }, names a file beside the workflow. The controller copies it into the stage's evidence, runs the copy, and records its SHA-256 on the event: what was hashed is what ran. The job's checks, which the repository may set, may not use one.
  • The request: SF_REQUEST names request.json, with the cycle, the stage, the head and base, the ticket, the diff (the checkout has no .git to work it out from) and outputDir, the one folder it may write besides the checkout.
  • Network is off unless the stage sets network: true. A stage that holds a credential must, and has more rules (grants).

commandKit in src/kits/command.ts checks a stage keeps this contract: it runs the stage through the real verify on a scratch repository, once on a change that should pass and once on one that should fail.

The tree check: reviewers must read the commit

The reviewers read the same checkout the commands ran in. But a command runs the candidate's code, and that code can write files. A formatter rewrites a source file. A hostile test replaces one.

So after the commands, the controller compares the checkout with the commit. If any tracked file differs, it adds its own result, named tree, as a FAIL, with the changed paths as evidence.

Untracked files (build output, caches) are not dirt. They are deleted before review, so a reviewer cannot be shown a planted .git or a symlink to your files.

Why it is this careful

Each line here closed an adversarial review finding:

  • 06-c: a formatter left the checkout dirty, and review refused it on every call. Now the dirt is recorded as evidence and the stage fails.
  • 07-b: a check ran git in the checkout and hid a rewritten file from the comparison. Now the checkout has no .git; the controller's Git uses a private index outside it.
  • 08-a: a committed symlink let a check read the developer's worktree. Now commands run in bubblewrap, and leftovers are removed before review.
  • 08-b: a check locked a file so Git skipped it with only a warning. Now owner access is restored first, and Git's warnings count as dirt.
