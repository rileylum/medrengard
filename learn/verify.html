The controller runs the checks itself

A developer agent may say "all tests pass". That is a claim. The factory does not take it on trust.

After the developer's commit is accepted, the controller makes a fresh checkout of exactly that commit and runs the repository's checks there. The developer never touches this checkout.

The owner declares the checks in the job file, not in the repository. A file in the candidate commit belongs to the developer, who could edit it to declare no checks at all.

Three rules

  1. Fresh checkout, no .git. Only the commit's files. Nothing the developer left behind, and no Git state a check could rewrite.
  2. Evidence is bound to the SHA. Each check's stdout, stderr and exit go to runs/evidence/<head>/. A new commit needs new evidence.
  3. Missing evidence is never PASS. A check that cannot run is MISSING, and MISSING stops the cycle like a FAIL.

Try it: the checks lab

These four checks are declared for a candidate. The guide finds each command the way the factory does, on a made-up machine: npm is in /usr/bin, ruff is in the owner's ~/.local/bin, eslint is not installed, and scripts/smoke.sh is committed in the candidate.

Try: set test to "exits 1". Add /home/owner/.local/bin to sandbox.read and watch fmt come back. Tick "rewrites a tracked file". Delete every check.

PASS, FAIL and MISSING

ResultWhenWhat the exit file says
PASSThe check ran and exited 0.exit 0
FAILIt exited non-zero, ran past the deadline, or printed more than 8 MiB.exit 1, timeout, overflow
MISSINGIts binary is not on PATH, or it resolves outside what the sandbox can see.missing: eslint not found

MISSING is evidence that does not exist; FAIL is evidence that says no. Both escalate, but the owner learns different things. MISSING tells them to install a tool or add its directory to sandbox.read. FAIL tells them the candidate is wrong.

The factory looks up the binary itself, before it starts anything. Under a systemd scope, systemd-run would do the lookup and exit 1 on a missing binary, which would read as FAIL.

All checks run, in order, even after one fails. The evidence is for the owner and the reviewers, who want the whole picture.

The tree check: reviewers must read the commit

The reviewers read the same checkout the checks ran in. But a check runs the candidate's code, and that code can write files. A formatter rewrites a source file. A hostile test replaces one.

So after the checks, the controller compares the checkout with the commit. If any tracked file differs, it adds its own check, named tree, as a FAIL, with the changed paths as evidence. The name is reserved: a job may not declare a check called tree.

Untracked files (build output, caches) are not dirt. They are deleted before review, so a reviewer cannot be shown a planted .git or a symlink to the owner's files.

Why it is this careful

Each line here closed an adversarial review finding:

  • 06-c: a formatter left the checkout dirty, and review refused it on every call. Now the dirt is recorded as evidence and the cycle escalates.
  • 07-b: a check ran git in the checkout and hid a rewritten file from the comparison. Now the checkout has no .git; the controller's Git uses the repository's git dir and a private index outside it.
  • 08-a: a committed symlink let a check read the developer's worktree. Now checks run in bubblewrap, and leftovers are removed before review.
  • 08-b: a check locked a file so Git skipped it with only a warning. Now owner access is restored first, and Git's warnings count as dirt.

What a check may touch

Every check runs inside bubblewrap with one policy: write the checkout, read the system directories and the owner's sandbox.read list, no network. It gets a private /tmp and a cleared environment. It cannot see the developer's clone, the repository's .git, or the owner's home.

Takeaway

  
The developer's word counts for nothing. The controller runs the checks on the exact commit, keeps the output against its SHA, and stops when anything is missing or changed. Only then does a reviewer see it.
