Stages are data

A workflow is a plain object: a start stage, and for each stage its kind, where PASS and FAIL lead, and an optional budget. Nothing in it runs. That is what lets the factory check it, and record which one a cycle used, before any agent starts.

agent

A run of the role it names. A role produces a commit (a developer) or a verdict (a reviewer). The stage's roleText is the first line of the prompt.

command

The controller runs commands on the candidate: the job's checks, or the stage's own run. Checks and command stages

human

The cycle waits for you. accept with the candidate's SHA takes the PASS transition.

Four more stages belong to the engine, and no workflow may define them: QUEUED, where every cycle starts, and ESCALATED, CANCELLED and ACCEPTED, where it stops. The v1 lifecycle is one workflow among many: defaultWorkflow, used when a job names none.

What no workflow can switch off

You may change every stage. These rules sit in the engine, in checkWorkflow and apply, and hold under any workflow.

Every loop spends a budget

Take away the stages with a budget and the stages left must have no loop. So a cycle cannot go round forever: each pass round a loop counts against a stage, and a FAIL at the limit escalates.

Every stage can finish

Each stage needs a path to ESCALATED, CANCELLED or ACCEPTED. A FAIL with no transition escalates.

Unclear means stop

An event that does not fit the stage escalates with its reason: a verdict outside a review stage, an accept for another SHA, an event type nobody knows, a step named for another stage. Nothing retries by itself.

Only the owner moves on

A cancel ends any open cycle. An ESCALATED cycle ignores everything else and waits for you to cancel it or open a child cycle, which starts with every budget empty.

Two more: a role produces either commits or verdicts, never both, because the controller tells a claim from a verdict by the role alone. And role text is one line, so it cannot forge the contract's Rules: line below it (see the developer room).

How a budget counts

A stage with a budget counts every outcome recorded while the cycle is in it: a developer's result, a verification, a verdict or an acceptance. Two things are checked against the count:

  • A FAIL at the limit escalates rather than following the FAIL transition. In the default workflow, STANDARD_REVIEW has a budget of 2: the first FAIL goes back to DEVELOPING for a fix run, the second escalates.
  • A spent stage cannot be entered again. A transition into a stage whose budget is used up escalates with "budget exhausted".

Counts never go down inside a cycle. A fix run makes a new candidate and the checks run again, but the review counts carry on. A failed run (run_failed) counts nothing: it was not a review. A verdict for a stale SHA counts, and escalates: the review ran, so a stale reviewer cannot be retried for free.

One workflow per job, bound by its hash

A job names a workflow with "workflow": "path/to/module.ts"; the module's named export workflow is the object. The job file, your personal file or the repository can set it (see the configuration room). A repository workflow is read from the base commit, never from the working tree.

When a cycle opens, the store writes the workflow's name, its hash and the whole definition into the cycle's first row. Every later load replays the cycle under the store's workflow, and refuses if the hashes differ: a cycle replayed under another workflow could land in a stage its log never had (A-059).

The hash is SHA-256 of the object's JSON, so reordering two keys makes a new workflow. That is safe: old cycles are refused, never misread. The editor above shows the hash as you type.
