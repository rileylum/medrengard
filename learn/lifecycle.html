Nine stages, one function

Every piece of work moves through a cycle. A cycle is always in exactly one of nine stages. Seven are the happy path, from QUEUED to ACCEPTED. Two are where a cycle stops: ESCALATED and CANCELLED.

Only one thing moves a cycle: the function apply. It takes the cycle and one event and returns the next cycle. It reads no files, starts no processes and asks no model. So the same events always give the same cycle.

Drive it yourself

This is the real apply from src/lifecycle.ts. Press claim, then developer_result, verification and two verdicts to walk the happy path. Then break it: send a verdict for the wrong head, the same run ID twice, or an accept for a SHA that is not the candidate.

An event that does not fit is never silently dropped. Either apply records it with a note and leaves the stage alone, or it escalates.

The guards, and why each one is there

A stale verdict counts, but cannot move the cycle

A verdict must name the SHA it reviewed. If that SHA is not the current candidate, the review was of other code. apply still adds one to the budget, because the review ran and was spent, and then escalates. Counting it stops a stale reviewer being retried for free.

One outcome per run

Every result and verdict carries the run ID that made it. Once a run's outcome is consumed, a second one with the same ID is noted as a duplicate and changes nothing. A redelivered message must never count twice.

Escalated and terminal cycles ignore everything

After ACCEPTED or CANCELLED every event is ignored. After ESCALATED every event except a cancel is ignored. Only the owner moves on, by cancelling or by opening a child cycle.

Counters never reset

A fix run makes a new candidate and runs verification again, but standard and adversarial carry forward. Only a child cycle starts at (0, 0), and only the owner can open one.

Two more: an infrastructure failure (run_failed) escalates without touching the counters, since it was not a review. And an event type apply does not know escalates as "unclassifiable", because types are stripped at runtime and events arrive as JSON.

The scenarios the tests check

The spec's acceptance tests keep their old names, SC-01 to SC-19, plus a few added later (RF for run failures, RT for runtimes). Each is a list of events and the stage and counters it must end at. Takeaway

  
The controller's rules fit in one pure function. Agents can say anything; only events that apply accepts move a cycle, and anything it cannot place stops the cycle for the owner.
