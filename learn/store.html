A ledger, not a record

The factory never stores "the cycle is in STANDARD_REVIEW". It stores what happened: a claim, a result, a verification, a verdict. One event per row, in order, and no row is ever changed or deleted.

To know where a cycle is, the store reads its rows and replays them through apply. The state is a sum, like a bank balance worked out from the statement.

Why this way

  • A crash loses nothing: the rows are the truth, and a restart replays them.
  • Every decision has its reason on record: which event, from which stage, and apply's note.
  • The rules can be tested without a database: the same events give the same cycle.

Time travel

Pick a scenario. Its events are appended to a store, one row each; row 0 is the store's own "open" marker. Drag the slider to replay only the first rows and see where the cycle stood at that moment.

Some scenarios have fewer rows than events: a redelivered verdict is not written at all. The next slide shows why.

One outcome per run

Results, verdicts and run_failed carry a run ID. The table has a unique index on (cycle_id, run_id), and the insert uses OR IGNORE. So the second outcome for the same run writes nothing, and append returns the cycle unchanged. That holds even if two processes race: the database, not the code, decides.

apply ignores duplicates too (the consumed list). The index is the second lock on the same door: a duplicate never reaches the log, so a replay never sees it.

Check the bytes, not the object

Before a row is written, append turns the event into JSON, parses it back, and runs isEvent on that. Not on the object it was given. A JavaScript object can say one thing when you look at it and serialise to another. The row holds the JSON, and the replay reads the JSON, so that is what has to be valid. This came from an adversarial review (ticket 02-c): every object below fooled a check on the object.

A row apply could not read would make the whole cycle unloadable. So an unreadable event is refused before writing, with UnclassifiableEvent; the controller turns that into a run_failed for the run that sent it.

One open cycle per work item

A work item has at most one cycle that can still move. An ESCALATED cycle cannot move, but it waits for the owner: a new cycle for the same work must name it as its parent. That is a child cycle. Cancelling the escalated one frees the work instead.

Try it: open a cycle, try to open a second, escalate the first, open again with and without a parent.

The table

One table for every cycle. WITHOUT ROWID stores rows in key order. The partial unique index is the one-outcome rule. busy_timeout lets a second process, such as main.ts cancel during a run, wait for the write lock instead of failing.

Takeaway

  
The log is the only state. Rows are only ever added, each is checked as the bytes it will be, and a run gets one outcome. Replay the rows through apply and you have the cycle.
