What the developer gets, and what it must give back

It gets

  • A Git clone of the repository of its own, on a branch named sf/<cycleId>, at the base commit.
  • The ticket, word for word.
  • Two rules: commit on this branch and nowhere else; end the reply with a fenced json block naming the commit.

It runs inside the sandbox: it can write its clone and nothing else of yours. the sandbox

It gives back a claim

{"head": "<full commit sha>", "artifacts": ["<paths>"]}

That is all. Not "the tests pass", not "it works". The controller runs the tests itself, later, on a fresh checkout. verification

And the controller checks the claimed commit before it believes it. That is the guard further down.

In a fix run the findings come from the reviewer, so they are untrusted text. Look at the second finding: it has a newline and a fake Rules: line inside. oneLine folds every line break into a space, so a finding cannot start a section of its own.

How the branch comes back

The clone is the developer's: it could hold anything, including Git config and hooks that would run if the controller's own Git read them. So the controller never runs Git inside it with the owner's rights.

  1. The repository fetches the clone's branch. The one process that reads the clone, git upload-pack, runs in bwrap with the clone read-only, under the stage deadline.
  2. The objects land under a private ref, refs/sf/incoming/<cycle>, checked with fetch.fsckObjects.
  3. refuse judges the claimed head there. Only an accepted head moves refs/heads/sf/<cycle>. The private ref is deleted either way.

Try it: the claim guard

The spec says a developer result must name a commit that exists on the branch, with a non-empty diff. refuse is that rule, in Git. Pick what the developer did. The real refuse runs against a fake repository and says yes, or why not.

RuleWhy
Not the base, not the previous candidateNothing new was made; a review would judge a diff it has already judged.
The full SHA, at the branch tipThe tip is what verify checks out. A short SHA could name a different commit later.
Descended from the baseOtherwise base..head, the diff every reviewer reads, means nothing.
A changed treeAn empty commit fixed nothing, and would spend the next review on the same diff.

The fix run

After the first standard FAIL, apply sends the cycle back to DEVELOPING. fix() runs the same developer on the same clone, with the last verdict's findings in the prompt.

Before it starts, it checks that the clone is still on the branch and the branch is still at the candidate. Anything else is a head change outside a fix run, which goes to the owner. The guard then also needs a head that is new in SHA and in tree. the review budget

What a claude developer may do

pi has no per-path permissions, so the sandbox is its only fence. Claude Code can scope tools, so the factory gives it a short allow list, on top of the sandbox: read anything, edit and write only in the clone, and four Git subcommands.

Not git log or git diff: both take --output=<path> and can write anywhere (05-a adversarial). The paths start with // because in Claude's rules a single / means "relative to the project".

Takeaway

  
The developer gets a clone and a ticket, and returns one claim: "this commit". The controller fetches the branch itself, in a sandbox, and believes the claim only if the commit is new, at the tip, and changes something.
