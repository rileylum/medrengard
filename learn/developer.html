What the developer gets, and what it must give back

It gets

  • A Git clone of the repository of its own, on a branch named sf/<cycleId>, at the base commit.
  • A prompt: the stage's role text on line 1, then the ticket word for word, then the core's rules.
  • Two rules: commit on this branch and nowhere else; end the reply with a fenced json block naming the commit.

It runs inside the sandbox: it can write its clone and nothing else of yours.

It gives back a claim

{"head": "<full commit sha>", "artifacts": ["<paths>"]}

That is all. Not "the tests pass", not "it works". The controller runs the tests itself, later, on a fresh checkout. And it checks the claimed commit before it believes it: that is the guard below.

On a fix run there is one more answer: keep the commit and say why the findings are wrong. That is a dispute.

Try it: what changes a prompt's version

A prompt has two parts, and each outcome event records a hash of each. The role text is the workflow's: you may change it. The contract is the core's: the claim's shape, the SHAs and the rules the controller parses. Edit either input and watch which hash moves.

The ticket changes neither hash. The contract's hash is built once from placeholders, so it names the wording, not one run. That lets you ask the log which runs had which wording, after a reworded role or a new release (09-c).

Try it: the claim guard

The spec says a developer result must name a commit that exists on the branch, with a non-empty diff. refuse is that rule, in Git. Here the real refuse judges nine things a developer might leave behind, each on a fake repository of its own.

RuleWhy
Not the base, not the previous candidateNothing new was made; a review would judge a diff it has already judged.
The full SHA, at the branch tipThe tip is what the checks run on. A short SHA could name a different commit later.
Descended from the baseOtherwise base..head, the diff every reviewer reads, means nothing.
A changed treeAn empty commit changes nothing. On a fix run a new commit with the same tree is allowed only on top of the failed one: a new commit message can be the whole fix.

How the branch comes back

The clone is the developer's: it could hold anything, including Git config and hooks that would run if the controller's own Git read them. So the controller never runs Git inside it with your rights.

  1. The repository fetches the clone's branch. The one process that reads the clone, git upload-pack, runs in bwrap with the clone read-only, under the stage deadline.
  2. The objects land under a private ref, refs/sf/incoming/<cycle>, checked with fetch.fsckObjects.
  3. refuse judges the claimed head there. Only an accepted head moves refs/heads/sf/<cycle>. The private ref is deleted either way.

The fix run, and the dispute

When a FAIL sends the cycle back to a commit stage, fix() runs the same developer on the same clone, with the last verdict's findings in the prompt and the stage's fixRoleText on line 1, or its roleText when it has none. Before it starts, it checks that the clone is on the branch and the branch is at the candidate. Anything else is a head change outside a fix run, which goes to you.

The findings are untrusted text from a reviewer. oneLine folds every line break in a finding into a space, so a finding cannot open a section of its own, such as a second Rules:.

A dispute

A developer may think a finding is wrong, or that it asks for a change the ticket rules out. Then it commits nothing and claims the previous candidate with a reason:

{"head": "<the previous candidate>", "artifacts": [], "dispute": "<reason>"}

Nothing is fetched and no branch moves. The cycle escalates with the reason, folded to one line and cut at 2 KiB, and no budget is spent. Only you can weigh a dispute against a verdict: cancel, or open a child cycle (07-e).

What a claude developer may do

pi has no per-path permissions, so the sandbox is its only fence. Claude Code can scope tools, so the factory gives it a short allow list, on top of the sandbox: read anything, edit and write only in the clone, and four Git subcommands.

Not git log or git diff: both take --output=<path> and can write anywhere (05-a adversarial). The paths start with // because in Claude's rules a single / means "relative to the project".
