# Route peer messages through the controller

The answer is a no-VM design, and it is good enough. Agents never talk to each other directly. Each run sends a message to the controller as a claim. The controller records the claim as an event, bound to the run and its commit SHA, and delivers it to a linked run. The channel is one Unix socket per run, owned by the controller and bind-mounted into that run's bubblewrap sandbox. The controller knows the sender from the socket the message came in on, so no agent can pretend to be another. There is one catch: today's sandbox does not keep runs apart. With `--share-net`, a run reached a host loopback port and a host abstract socket in a local probe, so two runs can already talk outside the controller's view. Replacing `--share-net` with `pasta --splice-only` and a small allowlisting proxy closes that gap. It costs about 10 ms per start, and every tool it needs is already installed. The home-server VM option is stronger: one VM per run, with the broker reached over vsock. It costs more RAM, takes more code, and hides the agent from herdr. Choose it when you run repositories you do not trust, not for messaging. Before you build any live channel, test the cheapest pattern. The upstream ticket publishes an interface file at a SHA, and the downstream ticket checks its code against that file. The evidence on multi-agent systems favours that kind of shared artifact over chat.

## Runs can reach each other today, so the sandbox needs one fix first

The project's `wrapBwrap` in `src/sandbox.ts` starts every run with `bwrap --unshare-all --share-net`. A local probe on 2026-10-22 showed what that permits. **A sandboxed run connected to a host TCP listener on 127.0.0.1 and to a host abstract Unix socket** (probe script `probes/probe.sh`). The decisions log already records this as security finding 3. The cause is in the kernel: "network namespaces isolate the UNIX domain abstract socket namespace" ([network_namespaces(7)](https://man7.org/linux/man-pages/man7/network_namespaces.7.html)). A run that shares the host's network namespace therefore shares its abstract sockets and its loopback ports. Any two runs that do this can open a private channel the controller never sees. Your design rule "controller decides state" only holds if that channel is closed.

pasta is the no-VM fix, and it is already installed (passt 2026_10_02). `pasta --splice-only` gives each run a private network namespace and "only forwards loopback traffic between namespaces" ([pasta(1)](https://passt.top/builds/latest/web/passt.1.html)). With `-T 3128:<hostport>`, a run sees one loopback port, and that port leads to one host port. In the local probes, **the run reached its own forwarded port and nothing else**. Other host loopback ports, abstract sockets, sibling runs' listeners and the internet were all unreachable. **Startup rose from 3 ms to 12 ms** (`probes/probe.sh`, `probe2.sh`). Each run gets its own host port, so the proxy on the host can tell runs apart without trusting anything the run says. Avoid pasta's default tap mode. In that mode pasta maps the gateway address to host loopback, so a run would reach every host-loopback service again ([pasta(1)](https://passt.top/builds/latest/web/passt.1.html)).

The run still needs its model provider, so a host-side CONNECT proxy, written in plain Node, allows only named hosts. Anthropic's own sandbox runtime uses the same shape: it removes the network namespace and routes all traffic through host proxies that check hostnames ([sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)). Claude Code honours `HTTPS_PROXY`. It needs `api.anthropic.com`, plus `platform.claude.com` and `claude.ai` for subscription login and refresh ([Claude Code network config](https://code.claude.com/docs/en/network-config)). pi 1.1.0 installs undici's `EnvHttpProxyAgent` globally, so it follows the same variables. **Plain Node 24 ignores `HTTPS_PROXY` unless `NODE_USE_ENV_PROXY=1` is set.** A local probe confirmed this: without the flag, fetch went direct ([Backstage proxy docs](https://backstage.io/docs/tutorials/corporate-proxy); `probes/proxytest.sh`). No client accepts a `unix://` proxy URL, which is why the run needs a TCP port inside the namespace and pasta supplies it.

The rootless alternatives fail on this machine. In a systemd user manager, `IPAddressDeny=` is silently not enforced ("unit configures an IP firewall, but not running as root"). Scopes reject `PrivateNetwork=` and `RestrictAddressFamilies=`, and nftables needs root ([systemd.resource-control(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html); `probes/sd.sh`). Landlock network rules filter by port only, not by address, so they cannot express "Anthropic only" ([kernel Landlock docs](https://docs.kernel.org/userspace-api/landlock.html)). This fix touches decision A-043, which accepted full network access as an open gap. That makes it your call, not an agent's.

## Option 1, no VM: a per-run socket broker that records every message

**What it is.** The controller opens a listener for each run at a host path such as `<runsDir>/<runId>/broker.sock` and bind-mounts it at `/run/sf/broker.sock`. A local probe showed that a bind-mounted socket works even with no network at all. Identity comes from which listener accepted the connection. `SO_PEERCRED` adds nothing, because every run has the owner's uid. The controller writes each accepted message to the store before delivery. The event looks like `message_sent {cycleId, fromRun, toRun, seq, inReplyTo, head, bodySha256, bodyPath}`. When the recipient's hook or tool runs, a `message_delivered` event follows. The agent's text is a claim. Who sent it, when, and at which `HEAD` are the controller's facts. Store bodies as files with a hash, as A-109 does for outputs, and never put them in argv.

**How agents send.** Claude Code gets a per-run stdio MCP server through `--mcp-config <file> --strict-mcp-config`. pi gets the same server, or a small extension loaded with `-e`. Either one forwards JSON lines to the bound socket. The CLI starts that server inside the sandbox, so it inherits the sandbox. If you hand-write the MCP JSON-RPC with `node:net`, it is about 50 lines and needs no dependency. The official SDK would become the project's first dependency. herdr already ships a pi extension, `~/.pi/agent/extensions/herdr-agent-state.ts`, that writes newline JSON to a socket with `node:net`. It is a ready template.

**How agents receive.** Each runtime has a way in:

| Runtime and mode | Delivery path | Source |
| --- | --- | --- |
| Claude `-p` and interactive | A `PostToolUse` hook returns pending mail as `additionalContext`. A `Stop` hook returns `decision: "block"` so a finished agent takes one more turn. | [Claude Code hooks](https://code.claude.com/docs/en/hooks) |
| pi headless | The controller already owns stdin in `--mode rpc` and sends `steer` or `follow_up` itself. | pi docs/rpc.md (local) |
| pi interactive | An extension calls `pi.sendUserMessage(..., {deliverAs: "steer"})`. | pi docs/extensions.md (local) |
| Any herdr tab | `herdr agent prompt` sends a fixed doorbell ("New message 17; read it with read_messages"). The message body never travels as keystrokes. | `herdr agent prompt --help` (local) |

The doorbell matters. herdr injects keystrokes that cannot be told apart from your typing, and it rejects a prompt while the agent is blocked. A fixed string means a hostile sibling has no way to type into your tab.

**What not to build on.** Claude Code's built-in cross-session messaging works in `-p` and delivers "between tool calls during an active turn" ([cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)). It does not fit here. Its message schema is undocumented, Claude Code chooses where the socket lives, and "a session inside a container and a session on the host can't reach each other". Deny `SendMessage` and `ListAgents` in sandboxed runs so the only channel is yours. Channels are ignored under `-p`, and interactive sessions need a dev flag behind a confirmation dialog ([channels](https://code.claude.com/docs/en/channels)). Agent teams do not spawn teammates under `-p`, and any teammate can message any other ([agent teams](https://code.claude.com/docs/en/agent-teams)). That is the opposite of "controller decides state".

**Threat model.** The run is untrusted. The controller, the broker and the proxy are trusted. With pasta, a run can reach only its own broker socket and its own proxy port. The remaining risks sit in the channel and in the model:

| Threat | What closes or limits it |
| --- | --- |
| A sibling run forges its identity | Identity comes from the per-run listener, so a sibling cannot forge it. |
| A run–run side channel through loopback or abstract sockets | Closed by pasta splice-only. It stays open while `--share-net` stays. |
| A side channel through a shared writable directory, FIFO or pathname socket | Do not bind any shared writable path. Landlock ABI 9 `RESOLVE_UNIX` can scope sockets ([kernel Landlock docs](https://docs.kernel.org/userspace-api/landlock.html)). |
| Injection that spreads through messages | Limited by schema-typed messages with size caps, routing only along links you declared, and a fresh-nonce quote block with sender, run and SHA. These are defence in depth. In the Prompt Infection study, marking alone let 76% of attacks through, and only marking plus tagging blocked every tested attack ([arXiv 2410.07283](https://arxiv.org/html/2410.07283v1)). |
| Claim or approval laundering ("ticket 12 confirmed it", "owner said ship") | A message never counts as evidence or approval. Only a check stage at a named SHA counts. |
| Exfiltration through the allowed provider | Not closed. The provider host is itself an outbound channel. Hostname checks without TLS inspection also allow domain fronting ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). |
| Credentials | Still readable inside the run (A-043). Masking needs a TLS-terminating proxy ([sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)), which is a separate project. |

Your own processes outside the sandbox, the controller and your shell, can still signal or ptrace a run. The isolation runs in one direction only.

**Costs.** The broker, the MCP shim and the CONNECT proxy are each small Node programs with no dependencies. pasta adds a second long-lived process per run, and it must live in the same systemd scope so `cgroup.kill` ends it. The listener lives as long as the run, so the process that supervises the cycle must hold it. That respects A-122's no-daemon decision only if that process lives as long as the run. Check this before you build. There is also a lost capability: no DNS inside the run, and tools that ignore proxy variables (ssh, raw database drivers, UDP) stop working.

## Option 2, home server: one VM per run, with the broker on vsock

**What it is.** The message layer stays the same. Only the transport changes. The controller runs as a service on the server host, which is the daemon that O-006 anticipates. Each run gets its own VM. Its only channel is vsock to the broker and to a proxy that injects credentials. In Firecracker, a guest connection to vsock port N arrives on the host socket `<uds_path>_N`, which the controller chose for that run ([Firecracker vsock.md](https://github.com/firecracker-microvm/firecracker/blob/main/docs/vsock.md)). With kernel vhost-vsock (QEMU, Cloud Hypervisor, Incus), the host assigns each guest's CID and the broker reads it with `getpeername()` ([vsock(7)](https://www.man7.org/linux/man-pages/man7/vsock.7.html)). Either way, the guest cannot choose its identity. Results come out as a `git bundle`. The host verifies the bundle and records the SHA it computed itself, never one the agent reported.

**Which VM stack to start with.** Start with Incus VMs on ZFS. Incus already provides vsock, snapshots, images and `incus exec` for attaching a terminal. ZFS clones make one golden instance per base SHA cheap to copy, which matches A-126 pools ([Incus 6.22](https://stgraber.org/2026/03/02/announcing-incus-6-22/); [Incus forum on storage](https://discuss.linuxcontainers.org/t/btrfs-os-disk-subvolume-for-var-lib-incus/24239/8)). Firecracker boots in about 125 ms with under 5 MiB of overhead, but you must build the kernel, the root filesystem and the TAP setup yourself. It also lacks virtiofs, so each SHA needs its own disk image ([Northflank comparison](https://northflank.com/blog/kata-containers-vs-firecracker-vs-gvisor)). Claude Code's own docs rank a dedicated VM as the strongest boundary and recommend one for an untrusted repository ([Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments)). A cheaper first step is to put the whole factory in one VM and reach it with `herdr --remote`. That protects your desktop, SSH keys and home directory, but it does not keep runs apart from each other. Inside that VM, the Option 1 fixes are still needed.

**Threat model.** The guest kernel is untrusted. KVM is the boundary. A run cannot reach the host's loopback, abstract sockets, files or sibling VMs unless the controller wires them in. With no TAP device, the guest has no outbound network except through the broker and the proxy. That closes the A-043 network gap. The prompt-level threats are unchanged: injection, laundering, collusion and exfiltration through the provider all ride on the messages, not on the transport. A VM removes the risk of a sandbox escape. It does nothing about a persuasive message.

**Costs.** The local desktop has `/dev/kvm` and `/dev/vhost-vsock`. The server's hardware, filesystem and RAM are unknown, so measure there. QEMU-based VMs cost about 131 MB of VMM memory plus guest RAM each, against about 3 MB for Firecracker. Those figures come from a paper, not from your machine ([arXiv 2411.01129](https://arxiv.org/pdf/2411.01129)). Inside a VM, herdr sees `ssh` or a console, not `claude`, so agent state must come from the broker. The subscription OAuth token still has to live in the guest. Whether Claude Code works behind a proxy that injects the header is undocumented ([devcontainer docs](https://code.claude.com/docs/en/devcontainer)). Every run would also go through a new `vm` entry in the `BACKENDS` table, plus bundle transfer. That is weeks of work, against days for Option 1.

## Ranking: the shared artifact beats live chat, and both beat a VM for this question

The research on multi-agent systems points one way. MetaGPT found that structured intermediate outputs in a shared pool "significantly increase the success rate" ([MetaGPT](https://www.arxiv-vanity.com/papers/2308.00352)). MAST names inter-agent misalignment and missing verification as two of the three main failure categories ([arXiv 2503.13657](https://arxiv.org/html/2503.13657v3)). Debate studies find that extra rounds rarely beat cheaper single-agent baselines at matched cost ([arXiv 2502.08788](https://arxiv.org/html/2502.08788v3)). They also find that using different models helps. "Agent B agreed" is not validation. A type-check of B's code against A's interface at SHA x is.

| Rank | Option | VM? | Fit with the project | Main cost |
| --- | --- | --- | --- | --- |
| 1 | **Contract artifact plus a question claim.** The upstream run outputs an interface file bound to its SHA (A-117). The downstream run receives it as quoted data, and a check stage compiles or tests against it. A run that needs more ends with a structured `question` claim. The controller records it, routes it on the next run or escalates to you at a deadline (the A2A `INPUT_REQUIRED` pattern, [A2A spec](https://a2a-protocol.org/latest/specification/)). | No | Best. It uses existing machinery, opens no channel between live runs, and produces evidence rather than opinion. | It is slower than live chat. It needs a link field on work items and two claim types. |
| 2 | **Option 1: a live per-run socket broker**, with pasta and a proxy closing side channels. | No | Strong. The controller records everything, and identity cannot be forged. | A few small Node programs, a proxy, and the A-043 change. |
| 3 | **Option 2: Incus VM per run, broker on vsock.** | Yes | Good isolation, but it needs a daemon (O-006). | RAM, new backend code, and lost herdr detection. |
| 4 | Factory in one VM. | Yes | It protects the desktop only. | Runs still see each other. |
| 5 | Claude agent teams, Claude cross-session messaging, mcp_agent_mail over HTTP. | No | Poor. Peers talk directly, and mcp_agent_mail identifies a sender by a `sender_name` argument ([mcp_agent_mail](https://github.com/Dicklesworthstone/mcp_agent_mail)). | The audit trail is weak. |

Rank 1 and rank 2 are not rivals. Rank 2 is rank 1 with live delivery. Build rank 1 first. Add rank 2 only if waiting for the next run proves too slow. The network fix in rank 2 is worth doing on its own, because the side channel exists today whether or not you add messaging.

## Suggested order of first experiments

1. **Claude Code and pi through the proxy.** Run each inside `pasta --splice-only` with bwrap and a stub CONNECT proxy, end to end, including an OAuth refresh. This gates everything in Option 1. The docs say it works, but nobody has tested Claude Code's bundled runtime. Set `NODE_USE_ENV_PROXY=1` for any plain Node tools.
2. **Delivery hooks inside bwrap.** Test a `PostToolUse` `additionalContext` hook and a `Stop` block hook that read from a bound socket, in both `-p` and a herdr tab. Then test pi's `steer` over RPC and from an extension. Also check that inotify sees writes made through a bind mount, and what `SO_PEERCRED` reports across the PID namespace. The notes left both open.
3. **Rank 1 on two toy linked tickets.** The upstream ticket outputs an interface file, and a downstream check stage type-checks against it. Make one deliberate mismatch and confirm the check fails at the right SHA. Then have a new upstream SHA mark the downstream result stale.
4. **Adversarial pass.** Plant an injection in repo A's README. Confirm that it cannot reach run B except as a quoted, capped, recorded message. Confirm that "A confirmed it" in a commit message is not accepted as evidence.
5. **The live broker (rank 2)**, only if step 3 shows that waiting for the next run costs too much.
6. **On the server.** Start one Incus VM per run with vsock to a host broker. Measure boot time, RAM per agent, and whether herdr can show agent state.

## Conclusion

The question sounded like a transport problem. It is mostly an evidence problem. Every transport here (bind-mounted socket, vsock, mailbox directory) can carry a message. What keeps the factory honest is that the controller writes the message down, binds it to a SHA, and refuses to count it as proof. Seen that way, O-010 and peer messaging are the same open question. Answer it once, for owner answers and peer answers together.

The finding that changes priorities is the one you did not ask about. Runs that share the network namespace can already talk to each other today. Close that with pasta before you add any sanctioned channel. Otherwise the sanctioned channel will be the less interesting one. Your next step: run experiment 1, then decide on O-010 and A-043 before writing any broker code.
