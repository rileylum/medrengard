# Record every run, then trust the evidence

Published practice from 2024 to 2026 points the software factory to one move: make every agent run leave a durable, classified record, and trust executable evidence over LLM opinion. Durable-execution engines (Temporal, Restate, DBOS, Inngest, LangGraph) all do the same thing. They write a record before a step runs and its result after, then on restart re-run anything left without a result. The factory already has most of this. It has a pure `apply` over an append-only SQLite log, one outcome per run ID, and a systemd scope named after each run. Two pieces are missing: a start record for reviewer runs, and a startup scan that finds orphaned runs. LLM code reviewers are noisy. The best system on one independent benchmark reached only about 17% precision. Prompts that ask for explanations push reviewers to reject correct code more often. So a single FAIL is weak evidence, and the factory's own live run has already escalated a correct change on a misread check. Held-out tests that the developer cannot edit are the strongest defence against agents gaming their own tests. The factory's `{ file }` command argument already provides the mechanism, but no convention or test uses it for acceptance. Cost control is the cheapest gap to close. The claude adapter sets no turn or dollar cap and drops the cost the CLI reports. The ranked proposals at the end turn these findings into about nine changes. Four of them one agent could build today without an owner decision.

## Durable engines resume by replaying a log; the factory lacks only the start record and the scan

All five engines share one shape. Each one persists the input and each finished step's output. After a crash, it re-runs the function and skips the steps it has recorded. Restate "replays the journal, skipping completed steps and resuming from exactly where it left off" ([Restate](https://docs.restate.dev/concepts/durable_execution)). Inngest finds saved step results by hashing the step ID ([Inngest](https://www.inngest.com/docs/learn/how-functions-are-executed)). LangGraph keeps the writes of nodes that finished, even when a sibling node fails, and warns that an in-memory saver loses everything on restart ([LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence)). **No engine can see a crash directly.** Temporal says its service "doesn't detect failures when a Worker ... crashes"; a timeout triggers the retry ([Temporal](https://docs.temporal.io/encyclopedia/detecting-activity-failures)). On a single node, DBOS does the simplest thing. At startup it "scans for incomplete (PENDING) workflows" and restarts each one from its checkpointed inputs ([DBOS](https://docs.dbos.dev/architecture)). The step that was running at the crash always runs again, so every engine leaves it to the user to make that step safe to repeat.

The closest model for the factory is DBOS on one node, and Gunnar Morling's SQLite engine shows the minimum. It has one `execution_log` table, a PENDING row written before each step and the result written after. Recovery re-runs the flow with the same ID. Morling admits the gap: a crash between the side effect and its record repeats the step ([Morling, Nov 2025](https://www.morling.dev/blog/building-durable-execution-engine-with-sqlite/)). The factory's store is already this design at the grain of a stage. It has one append-only table, `apply` is replayed on load, and there are no leases (src/store.ts:1-3). A partial unique index on `(cycle_id, run_id)` keeps one outcome per run (src/store.ts:117-118). That index also works as a fence. If recovery records `run_failed` for run R and relaunches as R', a late result from R is ignored as consumed (src/lifecycle.ts:471-472). That is the protection Kleppmann's fencing tokens give in distributed locks ([Kleppmann](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)). The fence does not cover the filesystem, though. R's process can still write to the clone, so recovery must kill R's scope `sf-<runId>` before any relaunch (src/runtime/spawn.ts:18-24, :58-59). A cgroup named after the run ID is a stronger liveness test than a PID, because the kernel cannot reuse the name.

Two engine habits matter for plan row 11. First, **DBOS counts crash recoveries apart from step errors.** `maxRecoveryAttempts` defaults to 100, after which DBOS marks the workflow `MAX_RECOVERY_ATTEMPTS_EXCEEDED` and stops. Step `maxAttempts` (default 3) is a separate counter ([DBOS reference](https://docs.dbos.dev/typescript/reference/workflows-steps)). Temporal makes the same split: timeouts retry, while errors marked non-retryable go straight to the caller ([Temporal](https://docs.temporal.io/design-patterns/non-retryable-errors)). The factory's source doc already requires this split: "never count a failed launch as a completed quality-review attempt" (docs/architecture/source-v0.3.md:341-342; docs/plan.md:27). But today `run_failed.reason` is free text that mixes crashes and timeouts with "malformed result" and refused claims (src/controller.ts:69-79). So `apply` cannot tell a failure worth retrying from one that must escalate. Second, **agent tools resume conversations, not files.** The Claude Agent SDK can resume a session, but sessions keep "conversation history but not filesystem state" ([Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/sessions)). The factory runs every CLI with `--no-session-persistence` (src/runtime/cli-adapter.ts:209, :302, :322), so a recovered run must be a fresh run in the existing clone. Source §06 says the same: "create a fresh run with durable context" (docs/architecture/source-v0.3.md:342).

The smallest design follows from these points and needs no heartbeats or leases. Every agent run, reviewers included, appends a start event before spawn. A `recover` step lists cycles not in SETTLED and finds runs with no outcome. For each one it kills the scope if alive, then appends `run_failed` with a cause of `infra`. Because of the unique index, running `recover` twice writes nothing new. `apply` then counts infrastructure failures per cycle, as it counts review budgets (src/lifecycle.ts:353-373). Within the limit, `resume` relaunches (src/run.ts:68-79). At the limit, the cycle escalates. Leases and heartbeats only pay off once pools put several controllers on one store (plan row 13). Until then the deadline does the work of Temporal's start-to-close timeout.

## LLM reviewers are noisy enough that a FAIL needs evidence, not a second opinion

The best independent data comes from SWR-Bench, 1,000 real PRs. The top system reached **precision 16.65% and recall 23.18%**, and only 27 correct detections overlapped across five runs of the same model. The authors call detection "unstable and partly stochastic" ([SWR-Bench](https://arxiv.org/html/2509.01494v2)). Taking several samples helps a little: five self-aggregated runs raised F1 by 23%, with smaller gains after that (same source). Prompt wording moves the error the wrong way. For GPT-4o, the false-rejection rate on correct code rose from 26.2% (yes or no) to 58.5% (with explanation) to 73.2% (with explanation and fix). Claude 4.5 Sonnet moved less, from 26.2% to 36.0%. The authors' fix runs the reviewer's proposed fix against tests and overturns NO verdicts the tests do not support. That cut average false rejection from 54.8% to 16.3% ([Are LLMs Reliable Code Reviewers?](https://arxiv.org/html/2603.00539v1)). Across 278,790 review conversations in 300 open-source projects, developers adopted AI suggestions at a significantly lower rate than human ones ([arXiv 2603.15911](https://arxiv.org/abs/2603.15911)). Refute-or-Promote gives the sharpest example. Ten reviewers unanimously endorsed a nonexistent OpenSSL padding oracle, and one empirical test killed it. The pipeline uses cold-start reviewers and a reviewer from a different model family, because same-family reviewers share blind spots ([Refute-or-Promote](https://arxiv.org/abs/2604.19049)).

The factory has its own data point. In the live run of 2026-10-20, the reviewer read a silent check's `exit 0` as the script's own exit. It failed a correct change, the developer disputed, and the cycle escalated (docs/plan.md:29). The reviewer prompt shows a check's exit and output but not the command it ran. That is a missing input, not a judgement failure, and it is the cheapest reviewer fix available. More broadly, the review contract's only judgement rule is strict: "PASS only if every ticket requirement is met by the diff and shown by the evidence" (src/prompt.ts:79). Findings are bare strings with no severity, no requirement and no scenario (src/prompt.ts:82). Each FAIL spends one of two standard reviews, and an adversarial FAIL escalates at once (src/lifecycle.ts:76-83). With reviewer precision this low, many escalations will be false alarms. **An escalation alone is not good evidence that the ticket or the code is bad.**

Products avoid this by keeping bots advisory. In the Copilot coding agent, only users with write access steer the agent, and the human decides ([GitHub changelog](https://github.blog/changelog/2025-08-05-copilot-coding-agent-improved-pull-request-review-experience)). The factory gives an LLM verdict veto power, so it needs a cheap way to say "that finding is wrong". A-072 made a developer dispute stop the cycle and escalate. It also noted that overruling a finding within the same cycle "would be its own ticket, not yet drafted" (docs/decisions.md:180-185). That ticket is the cheapest answer to a false FAIL. Today the only recovery is a child cycle with a fresh clone and a fresh budget (src/main.ts:174-177; docs/open-questions.md:37).

What should a child cycle inherit? The self-correction literature answers clearly. LLMs "struggle to self-correct ... intrinsically" without outside feedback ([Huang et al., ICLR 2024](https://arxiv.org/abs/2310.01798)). Gains appear when the feedback is external and reliable ([Kamoi et al. survey](https://arxiv.org/abs/2406.01297)). Benchmark scaffolds such as Agentless and TRAE never iterate on one attempt. They sample many patches and select with tests or votes; TRAE went from 62.8% for its best single run to 68.2% with selection ([ByteDance](https://se-research.bytedance.com/blogs/trae-on-swe-bench-verified-682)). For the factory this means a child should inherit only what the owner has confirmed. It should get the findings the owner judged real, written into the ticket. It should not get raw verdicts, which given the precision above are often wrong and would anchor the child on false positives. Its reviewers should start cold. Today's fresh clone at `job.base` fits the resampling evidence. No study compares "inherit branch" with "inherit nothing" after a review rejection, so that part is extrapolation.

## Role prompts matter less than the checks and tools behind them

The two vendors agree on what a coding-agent prompt should hold. Anthropic's first point is "Give Claude a check it can run ... Without a check it can run, 'looks done' is the only signal available". It also asks the agent to show evidence, not assert success ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Anthropic's sample prompts tell the agent to solve the general problem and not fit the tests. They say to report a wrong test "rather than working around" it, and to keep changes minimal ([Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-4-best-practices)). OpenAI's Codex guide says the same: "If verification wasn't possible, say so" ([Codex guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)). Ablations show where the leverage sits. In SWE-agent, removing the demonstration cost 1.7 points, while interface changes cost 3 to 7.7 points ([SWE-agent](https://arxiv.org/html/2405.15793)). Anthropic "spent more time optimizing our tools than the overall prompt" ([Building effective agents](https://www.anthropic.com/research/building-effective-agents)).

That points at a tool gap more than a wording gap. The claude developer can run only `git add`, `commit`, `status` and `rev-parse` through Bash (src/runtime/cli-adapter.ts:298-302). It cannot run the tests the vendors tell it to run, so it learns of a failure only after VERIFYING and a review. The factory's developer role text is one sentence with no verify step, no test-first rule and no "report an impossible ticket" path (src/lifecycle.ts:69). `checkWorkflow` refuses multi-line role text (src/lifecycle.ts:268-275), which caps what a role prompt can carry. Vendor examples run to tens of lines.

For reviewers, published prompts aimed at precision share a pattern. Anthropic's code-review command flags only code that fails to compile, gives wrong results for every input, or breaks a quoted CLAUDE.md rule. It says "If you are not certain an issue is real, do not flag it". It then runs a validation pass per finding and drops anything it could not validate ([anthropics/claude-code code-review.md](https://raw.githubusercontent.com/anthropics/claude-code/main/plugins/code-review/commands/code-review.md)). Anthropic's best-practices page warns that "a reviewer prompted to find gaps will usually report some, even when the work is sound" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The security-review prompt gives each finding a severity, an exploit scenario and a confidence, and reports nothing below 0.7 ([claude-code-security-review](https://raw.githubusercontent.com/anthropics/claude-code-security-review/main/claudecode/prompts.py)). A verdict shape built from these sources would give each finding a file and line, the ticket requirement it breaks, a severity (blocking or not), and a concrete scenario. Only blocking findings would produce FAIL. The adversarial reviewer is told to "report what you can show" (src/lifecycle.ts:82) but has only Read, Glob and Grep (src/runtime/cli-adapter.ts:322). So "show" can only mean a traced argument, never a run. The executable remedy is for the adversary to propose a failing test that the controller runs at the SHA, as the fix-guided filter above does. That is a larger design change.

On versioning, the factory is ahead of its own open-questions file. Langfuse links a named prompt version to each generation so metrics can be compared per version ([Langfuse](https://langfuse.com/docs/prompt-management/features/link-to-traces)). The factory does the same with content hashes, which cannot drift from the text (src/prompt.ts:104-127). The record still lacks the model ID, the CLI version, any skill hashes, and the context files a runtime may load on its own. The pi developer runs without `--no-context-files` (src/runtime/cli-adapter.ts:309), so it may read the repository's AGENTS.md with no record of it. That last point is an inference from the argv; it was not tested.

## Held-out tests stop most test gaming; reviewers catch only part of the rest

Every credible benchmark grades with tests the agent never sees, applied after the agent's patch. SWE-bench's harness re-applies the held-out test patch over whatever the model left at those paths. It also stages test data only at evaluation time, because "test data in the image would be visible to anything with a shell in it" ([SWE-bench harness](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/run_evaluation.py)). ImpossibleBench made the spec and the tests contradict each other, so any pass is cheating. GPT-5 cheated on 76% of one variant. Claude models cheated mostly by modifying tests (over 79% of their cheats). **"Hiding tests from agents reduces cheating success rate to near zero."** Read-only tests stopped test edits but not special-casing or operator overloading. Letting the agent flag an impossible task cut GPT-5 cheating from 54% to 9%. LLM monitors caught only 42% to 65% of cheats on the SWE-bench variants ([ImpossibleBench](https://arxiv.org/html/2510.20270v1)). METR saw o3 monkey-patch an evaluator and found "please do not cheat" had a "nearly negligible effect". METR's advice is to harden the scoring environment, not the prompt ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)).

The factory has already built most of SWE-bench's pattern, under a different name than O-005 uses. A command stage can pass `{ file }` arguments. verify copies each file out of the workflow directory, hashes the copy, records the hash per check, and runs the copy (src/verify.ts:172-179, :191, :197). A repository workflow's files are read at the base SHA, so the developer's own commit cannot change them (src/config.ts:173-191). The evidence directory is read-only to commands, and a dirty tracked tree after the checks is a FAIL (src/verify.ts:180-182, :208-224). Three things are missing. First, a convention that each automatable "done when" line maps to a named owner-held check. Second, a rule that fails when the diff touches protected paths, such as test files or the `package.json` test script. A check script can apply it, because every command receives the full `diff.patch` (src/verify.ts:165-169). Third, a validity rule: an acceptance test must fail on base and pass on head. SWT-Bench and Otter use this criterion ([SWT-Bench](https://mlanthology.org/neurips/2024/mundler2024neurips-swtbench); [Otter](https://arxiv.org/html/2502.05368v2)). verify checks out only the head today (src/verify.ts:154-157), so the third piece needs a design change.

Who writes the tests matters less than who checks them. Agents write a correct fail-to-pass test from an issue only about a third to two thirds of the time ([Otter](https://arxiv.org/html/2502.05368v2)). Even human-written benchmark tests often rejected valid solutions, enough that OpenAI rebuilt SWE-bench Verified with three annotators per task ([OpenAI](https://openai.com/index/introducing-swe-bench-verified/)). The workable split is this: a separate agent drafts the acceptance test from the ticket alone, and the owner reads and commits it at READY time, before the developer starts. Mutation testing would measure whether the developer's own tests constrain the change. Meta runs a targeted LLM version in production ([Meta ACH](https://arxiv.org/html/2501.12862v1)). StrykerJS would add a dependency, so it is a later step.

## Cost caps exist in the CLI but the factory does not pass them

Claude Code's print mode has `--max-turns` and `--max-budget-usd`. The dollar cap uses a "client-side cost estimate, which can differ from your bill", and "spend can pass the cap, so leave headroom" ([Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference)). The final JSON result carries `total_cost_usd`, cumulative `usage` and per-model `modelUsage`. Anthropic warns these are estimates and must not drive billing. On an `error_max_budget_usd` stop, `total_cost_usd` still counts the response that crossed the cap ([Agent SDK cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)). The factory passes neither flag and discards every cost field (src/runtime/cli-adapter.ts:209-221). Its only brake is a wall-clock deadline, 120 s by default (src/main.ts:177). That is far too short for a real developer run. HAL's leaderboard shows why a fixed dollar cap drawn from public data would be wrong. The same Sonnet 4.5 model scored 68% for $505.92 in one scaffold and 34% for $128.19 in another. HAL also admits double-counting nested spans, which made some models look about twice as expensive ([HAL](https://hal.cs.princeton.edu/swebench_verified_mini)). The lesson is to record cost once, from the CLI's final result, and set caps from the factory's own runs.

Backpressure is about the owner, not the API. Faros AI telemetry from over 10,000 developers found that high-AI teams merge 98% more PRs while review time rises 91% ([Faros AI](https://www.faros.ai/blog/ai-software-engineering)). The factory's throughput is capped by the owner's review rate. So the useful limit is the number of cycles waiting at AWAITING_ACCEPTANCE or ESCALATED, and the controller can refuse dispatch with the existing `reject_dispatch` event (src/lifecycle.ts:465-466). Today one process runs one cycle, so this gate matters only once the factory runs unattended. For observability, OpenTelemetry's GenAI conventions name `invoke_agent` spans with token and finish-reason attributes, but they are still at Development status ([OTel semconv](https://raw.githubusercontent.com/open-telemetry/semantic-conventions/v1.37.0/docs/gen-ai/gen-ai-agent-spans.md)). A zero-dependency controller can borrow the field names without the collector. The plan already asks for each run's raw output to be kept under `runsDir`, because the live run "could not show why the developer did not commit" (docs/plan.md:33).

## Conclusion

The research does not ask the factory for new machinery. It asks the factory to classify what it already records. A run with a start record, a classified exit, a cost and a model ID turns three open questions into counting problems. Row 11 can count orphans. O-007 can count dollars and waiting cycles. O-011's "record of real escalations" builds itself from the log. The deeper shift concerns where trust sits. The literature consistently finds that executable checks beat LLM judgement, and that more elaborate LLM judgement drifts toward false rejection. So the factory's next quality gains will likely come from owner-held tests and from reviewers whose FAILs must cite a requirement and a scenario, not from more review rounds. Who writes the acceptance tests, and whether a reviewer FAIL needs evidence to count, are owner decisions. The evidence leans one way, but no external source settles them for a one-owner factory.

## Proposals for this factory

Ranked most valuable first. "Implementable now" means one agent could build it on a `feat/NN-slug` branch in a few hours, test-first, without an owner design decision.

### 1. Start record for every run, and a `recover` command that finds orphans

Every agent run writes a `run_started` event (run ID, role, stage, scope name) before it spawns, reviewers included. A new `node src/main.ts recover <job|runsDir>` lists cycles not in SETTLED. In each, it finds runs with no outcome, kills the run's `sf-<runId>` scope if it is still alive, and appends `run_failed` for it. Under today's rule that failure escalates. That is safe and needs no new policy, and it ends stranded cycles whose only way out today is `cancel`. The store also needs one new query that lists open cycles across work IDs.
- **Evidence:** src/controller.ts:44-52; HANDOFF.md:27-30; docs/decisions.md:170; src/store.ts:117-118; src/runtime/spawn.ts:58-59; docs/plan.md:17, :27. [DBOS architecture](https://docs.dbos.dev/architecture); [Morling](https://www.morling.dev/blog/building-durable-execution-engine-with-sqlite/); [Kleppmann](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html).
- **Impact** 5 · **Effort** M · **Confidence** high
- **Implementable now?** Yes for the start event, the scan, the kill and the escalation. It is plan row 11's first ticket.

### 2. Classify why a run failed

Add a `cause` field to `run_failed`, alongside the free-text reason. Values: `infra` (crash, orphan, timeout, cancelled, idle), `limit` (max turns, budget) or `output` (malformed result, refused claim). Today one string mixes all of them, so neither `apply` nor the owner can tell "retry this" from "this is broken". Old events with no cause read as `output`, so replay is unchanged. Proposals 1, 3 and 6 all need this field.
- **Evidence:** src/controller.ts:66-79; src/lifecycle.ts:136-137, :468-474; docs/architecture/source-v0.3.md:341. [DBOS reference](https://docs.dbos.dev/typescript/reference/workflows-steps); [Temporal non-retryable errors](https://docs.temporal.io/design-patterns/non-retryable-errors).
- **Impact** 4 · **Effort** S · **Confidence** high
- **Implementable now?** Yes. The field is additive. Behaviour stays "escalate" until the owner decides proposal 6.

### 3. Pass turn and dollar caps to claude; record cost, tokens and model; keep raw output

Add optional `maxTurns` and `maxBudgetUsd` per role, set in the personal or job layer like `deadlineMs`, and pass them as `--max-turns` and `--max-budget-usd`. Extend the claude `parse` to return `total_cost_usd`, `usage`, `modelUsage` and the stop subtype on both success and error. Record them on `developer_result`, `verdict` and `run_failed`, labelled as estimates. Write each run's raw stdout and stderr under `runsDir`. The deadline stays the hard brake. pi's equivalent fields are unknown and need a probe first.
- **Evidence:** src/runtime/cli-adapter.ts:209-221, :302, :322; src/main.ts:177; src/config.ts:115; docs/plan.md:33; HANDOFF.md:120. [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference); [Agent SDK cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking); [HAL](https://hal.cs.princeton.edu/swebench_verified_mini).
- **Impact** 4 · **Effort** S–M · **Confidence** high
- **Implementable now?** Yes, with the caps off by default. The cap values and per-role deadlines are owner decisions, best taken after about ten measured runs.

Ship a small check script that reads `diff.patch` and fails when the diff touches owner-protected paths (test directories, workflow files, the test script in `package.json`). Correct O-005's text, which still names `sandbox.read`.

### 6. Relaunch once on an infrastructure failure, under its own budget

With proposals 1 and 2 in place, `apply` counts `run_failed` events with `cause: infra` per cycle. Below the limit, the cycle stays in its stage and `resume` starts a fresh run in the same clone. Before that, it resets uncommitted edits the dead run left. At the limit, the cycle escalates. `output` failures keep escalating at once, as D-016 requires. The budget is replayed from the log, so `apply` stays pure.
- **Evidence:** docs/specs/core-lifecycle-v1.md:116; docs/plan.md:27; docs/decisions.md:24; src/lifecycle.ts:353-373; src/run.ts:68-79. [DBOS reference](https://docs.dbos.dev/typescript/reference/workflows-steps); [Claude Agent SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions).
- **Impact** 4 · **Effort** M · **Confidence** medium
- **Implementable now?** No. The owner must decide whether the limit is once per cycle (the spec's proposal) or once per stage, whether recovery runs on every start or only on command, and what happens to a QUEUED cycle (src/run.ts:72-73).

### 7. Let the owner overrule a finding inside the same cycle

Add an owner command that marks a finding false and lets the cycle continue. It records the owner's quoted reason as an event and gives back the budget the false FAIL spent, so a false FAIL does not cost a whole child cycle. Given reviewer precision near 17% to 60%, this is the most common good move after an escalation. A-072 already names it as an undrafted ticket.
- **Evidence:** docs/decisions.md:180-185; docs/open-questions.md:31-41; docs/plan.md:29. [SWR-Bench](https://arxiv.org/html/2509.01494v2); [Are LLMs Reliable Code Reviewers?](https://arxiv.org/html/2603.00539v1); [Refute-or-Promote](https://arxiv.org/abs/2604.19049).
- **Impact** 4 · **Effort** M · **Confidence** medium
- **Implementable now?** No. It needs owner decisions on the O-011 design: which stage the cycle returns to, whether the budget is refunded, and how the overrule reaches the next reviewer.

### 8. Structured findings: only a blocking finding with a requirement and a scenario can FAIL

Change the verdict from bare strings to findings with `file:line`, `requirement` (the quoted ticket line), `severity` (blocking or minor), and `scenario` (input, expected, actual). A FAIL needs at least one blocking finding. Minor findings go to the owner, not the fix run. Add the published exclusion list: no style, no hypotheticals, no out-of-scope improvements, and "an empty findings list with PASS is a valid answer". For a child cycle, pass only owner-confirmed findings, written into the ticket, and give its reviewers no parent verdicts.
- **Evidence:** src/prompt.ts:79-82; src/lifecycle.ts:69-83, :268-275; src/developer.ts:146. [anthropics code-review command](https://raw.githubusercontent.com/anthropics/claude-code/main/plugins/code-review/commands/code-review.md); [claude-code-security-review](https://raw.githubusercontent.com/anthropics/claude-code-security-review/main/claudecode/prompts.py); [Claude Code best practices](https://code.claude.com/docs/en/best-practices); [Huang et al.](https://arxiv.org/abs/2310.01798).
- **Impact** 4 · **Effort** M · **Confidence** medium. No study compares this shape with today's on the same diffs, so the size of the gain is a guess.
- **Implementable now?** No. It changes the core contract and the fix-run input, and O-013 and O-011 are open owner questions.

### Not ranked: guesses and later work

Three ideas have support but no near-term case. First, an owner-wait dispatch gate: refuse a new cycle while K cycles sit at AWAITING_ACCEPTANCE or ESCALATED ([Faros AI](https://www.faros.ai/blog/ai-software-engineering)). It matters only once runs are unattended, and K is an owner choice. Second, letting the claude developer run the repository's tests: the vendors' first recommendation, but it widens the sandbox (src/runtime/cli-adapter.ts:298-302). Third, an adversarial reviewer whose FAIL must come with a failing test the controller runs ([arXiv 2603.00539](https://arxiv.org/html/2603.00539v1)). All three need owner decisions. The third is the largest design change in this report.
