## 1. Intent and scope

The owner needs approved work to progress without manually kicking each stage, while retaining control over scope, terminal failures and acceptance. The immediate design goal is a lifecycle precise enough to implement as deterministic transitions with reproducible tests.

Observed here: only documents exist; no controller, runtime capabilities or recovery guarantees have been tested. The source reports orchestration friction; interruption reduction is an intended outcome, not measured evidence.

In scope: a single local controller, one repository and one active delivery initially; identities, transition guards, independent evidence, bounded reviews, safe recovery and release handoff. TypeScript/SQLite are accepted implementation choices. Pi and Claude Code sit behind vendor-neutral adapters; this specification assumes no particular integration capability.

Out of scope: adapter implementation, full schemas/SQL, scheduler fairness, UI, remote hosting, automatic merging/deployment and runtime-specific permission configuration. UX mockups are N/A for this internal protocol. State tables and failure scenarios are the design artifacts. Recovery guarantees require executable tests before unattended use.

Success signal: SF-002 can encode representative fixtures with one unambiguous expected transition and counter outcome. Later, M2 demonstrates READY → human-reviewable PR without routine intervention, plus verified failure/restart behaviour.

## 2. Identities and authority

| Record | Identity and required meaning |
| --- | --- |
| Work | Stable work ID and immutable contract version; goal, criteria, dependencies and risk profile |
| Specification | ID/version/content digest and explicit approval reference where required |
| Delivery cycle | Unique cycle ID, parent cycle if revised, work/spec/policy versions, authorised scope, pinned effective policy values/digest, all budget counts and append-only history |
| Candidate | Repository identity, work branch, target branch, exact head SHA and pinned target-branch tip SHA (`base`); base is NOT the Git merge-base. Record merge-base separately for diff calculation. Evidence refers to this tuple, not moving branch names |
| Logical attempt | Unique ID, role, cycle, input candidate/context and reserved review ordinal where relevant |
| Execution | Unique run ID for one launch; runtime/model/config versions, attempt ID, workspace and lease generation; retries use new run IDs |
| Evidence | ID, producer/verifier, work/spec/policy versions, candidate, environment, check identity, time, result and artifact digest/location |
| Decision | Unique ID, authenticated human actor, action, exact scope/version/candidate, rationale and authority reference |
| Event | Unique event ID plus source dedupe key, actor, cycle, expected state version, before/after, evidence references and timestamp |

The controller alone commits authoritative automated transitions. Workers submit untrusted results. The designated owner alone initially approves designs, waivers, revisions, governance changes and final acceptance (proposal Q4). No role or authority is inferred from issue prose, a model response or a successful process exit.

### Structured Design Studio → controller handoff

The Design Studio prepares immutable specification and contract artifacts, not execution authority. The first owner interface is a local CLI over a deterministic command boundary; future UI/GitHub integrations must use the same validation semantics. Chat, an LLM interpretation, a Git commit or a READY label alone grants no authority.

Commands include `approve-policy`, `approve-design`, `authorise-work` (individual/batch), `revoke`, `pause`, `resume`, `request-revision`, `accept-delivery`, and separate `authorise-merge`. Each binds command/dedupe ID, authenticated owner identity, exact action, work/cycle/expected version where applicable, artifact digests/versions, policy digest, scope and relevant expiry. Preview the exact objects and effective limits before confirmation. The controller validates actor capability, current authority, versions and all transition guards, then atomically persists the decision/event and effect. Same ID/same payload returns the original result; same ID/different payload is rejected; different IDs cannot bypass work-tip uniqueness. Transport replay never creates a second cycle. An acceptance command binds the candidate AND acceptance-package digest; missing/stale gates reject it. Merge remains a separate guarded action, never implicit in acceptance.

Owner authentication/transport and process privilege separation are implementation obligations BEFORE enabling owner commands or worker execution. Worker launch environments must not possess the owner credential, privileged socket access or policy-store write capability. A shared Unix identity with unrestricted access is not adequate separation. A worker's repository policy-file edit is only a proposal, never a runtime policy activation. If that isolation cannot be established, block execution; do not rely on a prompt instruction. Secrets are referenced through protected storage, not embedded in policy files. CLI syntax and foreground/daemon transport remain separately designed; no CLI exists yet.

Design approval and work authorisation are separate decisions: approving a design does not authorise every derived contract. An authorised contract can wait on dependencies/design approval. The controller alone derives READY and rechecks readiness at dispatch.

Work readiness is distinct from cycle stage: `NEEDS_REFINEMENT`, `NEEDS_DESIGN_APPROVAL`, `READY`. Becoming work-READY requires valid fields, resolved dependencies, required design approval or allowed N/A, eligible repository/environment and a defined quality profile. Dispatch rechecks these conditions, rather than trusting an old label.

A cycle is created under recorded owner authority (individual initial-work authorisation, a bounded initial-work batch under proposed Q5, or an individual Q1 revision), before readiness promotion, in `PREPARING`, control `ACTIVE`, counters `(0,0)`. It pins immutable contract/spec/policy/profile versions, authority references and review limits, even when a referenced design still awaits approval. The controller promotes it to `QUEUED` only once work readiness is READY. Changes to those pinned versions require a new authorised cycle; never edit them in place. READY in the source roadmap denotes work readiness, not a second cycle stage.

**One lineage per work ID:** the work record has exactly one current cycle tip and at most one nonterminal cycle. Initial creation is allowed only when no cycle has ever existed for that work. ACCEPTED with PENDING or INVALIDATED handoff still occupies the work's live-delivery slot. Supersession transfers that slot atomically to one child, recording a unique parent→child link and updating the work tip. Every child creation must compare-and-swap the expected current tip and require no existing child. A replay of the same decision returns the existing child; a different decision against a parent that already has a child is rejected, even if its event ID is new. A second initial authorisation is rejected regardless of the current stage. Cancelled work can only be reopened by an explicit child-cycle authorisation from its current tip after containment; completed/merged work's new product scope uses a new work ID. No branch/contract-version change creates an exception to this invariant. In the initial single-delivery mode, PREPARING through acceptance/handoff resolution occupy the slot; M5 must revisit strict base-drift policy before enabling concurrent delivery.

## 3. Delivery states and transition rules

Delivery states: `PREPARING`, `QUEUED`, `DEVELOPING`, `VERIFYING`, `STANDARD_REVIEW`, `ADVERSARIAL_REVIEW`, `AWAITING_ACCEPTANCE`, `ACCEPTED`, `ESCALATED`, `CANCELLED`, `SUPERSEDED`.

Orthogonal execution control: `ACTIVE`, `PAUSED`, `RECOVERING`, `QUARANTINED`. Only ACTIVE permits ordinary dispatch/advancement. Recovery may record observations and stop workers, but cannot advance quality gates. Store the interrupted stage and reason; do not use PAUSED as a new cycle or budget reset.

All transitions require matching cycle/state version, allowed actor, applicable control state, current approval/policy eligibility and a unique event. The following adds stage-specific guards. Invalid input never triggers the indicated successful transition. Escalation defaults to control PAUSED once containment is proven; uncertain containment requires QUARANTINED. For safe VERIFYING blockers, containment means verified read-only candidate access and isolated check scratch space, not necessarily process termination; the sibling-execution rule below applies. Safety/context invalidation and cancellation still require stopping workers. Controller failure/staleness handling may interrupt any nonterminal control state; ordinary quality advancement requires ACTIVE.

| From / trigger | Required guard/evidence | To / effect |
| --- | --- | --- |
| No cycle / controller applies owner initial-work authority | Individual or bounded Q5 batch authority naming exact work/version/scope/limits; work has no prior cycle; atomic unique work-tip creation | PREPARING/ACTIVE `(0,0)`; replay same decision returns existing cycle, different initial decision for same work rejected |
| PREPARING / owner adopts refined pinned versions | Explicit child authorisation with new versions/scope/limits; expected current work tip, no existing child, no live workers | Atomically SUPERSEDED parent → PREPARING/ACTIVE child `(0,0)`; preserve parent link and transfer work slot; no dispatch until child READY |
| CANCELLED / owner reopens same work | Explicit child authorisation, same lineage guards, completed containment and result reconciliation | Parent remains CANCELLED; atomically create/link PREPARING/ACTIVE child `(0,0)` and transfer tip |
| PREPARING / controller readiness evaluation | Work readiness READY; valid pinned versions and required approvals | QUEUED; record readiness evidence |
| QUEUED / scheduler claim | Dependencies satisfied; approved context; eligible slot/runtime; exclusive branch/workspace ownership; durable launch intent; capture target tip B1 | DEVELOPING; create development attempt and execution |
| DEVELOPING / result | Assigned run/lease identity; valid result and artifacts; actual committed head; no undeclared scope change; writer stopped before handoff | VERIFYING; freeze candidate tuple |
| VERIFYING / independent verification succeeds | Every required check PASS, permitted HUMAN-WAIVED or eligible KNOWN_BASELINE_FAILURE (§5); no pending classification/correction, all expected results reconciled; candidate/context current; standard and adversarial slots remain | STANDARD_REVIEW; reserve next standard ordinal |
| VERIFYING/ACTIVE / valid assertion failure | Preserve FAILED evidence; classify under §5, never use infrastructure replacement as quality rerun | Remain VERIFYING while bounded classification completes; eligible known failure may satisfy only its check as an exception; candidate defect uses Q6 correction admission; unclassifiable, disallowed or exhausted case ESCALATES |
| VERIFYING / missing mandatory completion evidence, material scope deviation or unsafe failure | Record evidence; distinguish retained-artifact retrieval from malformed completion and real quality failure | ESCALATED with applicable containment; no automatic correction for authority/safety/provenance anomalies |
| VERIFYING / required check cannot launch its initial execution | Record configuration/eligibility blocker and check intent; prove no launch or uncertain external action exists | ESCALATED/PAUSED, resume_stage VERIFYING; initial execution remains unused; no Q3 allowance consumed |
| STANDARD_REVIEW / valid PASS | Exact assigned candidate; independent fresh context; ordinal available; all pre-review evidence and required standard-review output current | ADVERSARIAL_REVIEW; atomically count standard completion once and reserve adversarial attempt |
| STANDARD_REVIEW / valid FAIL | Same validity guards; current candidate, ACTIVE control | Count standard completion once; apply Q6 using post-verdict counts: admit one bounded correction if the full remaining path fits, otherwise ESCALATED |
| ADVERSARIAL_REVIEW / valid PASS | Current standard PASS on same candidate/context; independent verdict and pre-review/review-stage evidence current; acceptance-stage human observations may still be pending | AWAITING_ACCEPTANCE; count adversarial completion; assemble package |
| ADVERSARIAL_REVIEW / valid FAIL | Valid assigned verdict; current candidate, ACTIVE control | Count adversarial completion once; apply Q6 using post-verdict counts. Eligible correction returns through VERIFYING and a NEW standard PASS before another adversarial attempt; exhausted path ESCALATES |
| AWAITING_ACCEPTANCE / owner approves | Explicit decision bound to current candidate and package; mandatory gates satisfied; no stale approvals/checks | ACCEPTED; no automatic merge or deployment |
| AWAITING_ACCEPTANCE or ESCALATED / owner requests revision | Q1 authorisation; expected current work tip and no existing child; old workers contained and results reconciled; immutable scope/version and new cycle ID; pending design approval cannot be bypassed | Old cycle SUPERSEDED atomically with new PREPARING/ACTIVE cycle `(0,0)`; new work must independently meet readiness |
| Any nonterminal stage / owner cancels | Stop/quiesce workers; reconcile results; retain artifacts and findings | CANCELLED/PAUSED only after containment; otherwise ESCALATED/QUARANTINED with pending cancel intent; no new dispatch |
| Any nonterminal stage / controller detects ambiguity, context invalidation, disallowed head/base drift, safety violation or budget exhaustion | Persist reason, relevant evidence and decision options; stop active workers safely; apply §§4–5 precedence | ESCALATED, with quarantine if containment is uncertain |

**Interrupted quality results (not execution failures):** while delivery is non-escalated and control PAUSED or RECOVERING, authenticate and persist each valid review verdict exactly once, consume its reservation/increment S or A once, and mark its stage-routing effect PENDING. Valid verification assertion results likewise persist raw evidence and PENDING classification/routing, without a review count or an escalation blocker merely because control is interrupted. Neither PASS nor FAIL advances a gate, starts diagnostics or admits a correction before ACTIVE. Invalid/stale results and actual execution failures retain their separate escalation/containment precedence; D-008 is unchanged. Valid assigned review verdicts arriving while delivery is ESCALATED use the explicit disposition table below, just like results pending when escalation committed; neither timing advances the gate while ESCALATED. Verification sibling results use their existing evidence/blocker rules. Stale, fenced, closed-run or unassigned output cannot acquire authority through this rule.

The controller's non-escalated ACTIVE-origin recovery row may reconcile authenticated valid COMPLETIONS as well as live runs. Once identity/context/containment are proven and no execution failure, intervening pause, escalation or cancel requires another outcome, that row returns ACTIVE and applies pending quality routes. PAUSED-origin recovery returns PAUSED with routes still pending; the owner's explicit PAUSED→ACTIVE resume is then the actor/transition that applies them. Owner pause racing ACTIVE-origin recovery wins through CAS/revalidation and preserves the pending route for owner resume, not an automatic ACTIVE exit.

Before any ordinary dispatch on either ACTIVE-return path, atomically revalidate the pinned candidate/context, current stage, registered result and remaining budgets; apply its normal PASS or Q6 FAIL routing once WITHOUT consuming its already-counted verdict again, then mark routing APPLIED. If eligibility/budgets now fail, escalate/contain instead of dispatching. A pending verification result routes through §5 classification: diagnostics may be scheduled only after ACTIVE is committed; until classification completes the gate stays blocked. Multiple pending check results reconcile before worker dispatch as Q6 requires. Replays of accepted results or resume/recovery commands never recount, re-reserve the next stage, or create a second correction. Terminal cancellation or supersession abandons pending routes permanently without erasing their evidence or counts. Escalation instead gives every pending result the explicit disposition below; it must not silently abandon an actionable result. Context/candidate/provenance invalidation preserves stale evidence but forbids reusing it to advance. Thus a healthy observation interruption alone does not forfeit a valid in-scope correction or require the owner to resume ACTIVE-origin recovery.

### Pending-result disposition on escalation — A-009 revision

In the SAME state-version transaction that records any escalation, the controller reconciles every PENDING quality route before recomputing blockers or considering restoration. Apply this table also when a valid assigned review verdict is reconciled AFTER escalation, fulfilling the reservation outstanding for the reviewer role at `resume_stage`. Accept only under the existing registered-run/lease and reservation rules: fenced/replaced/closed-run output and unassigned verdicts remain diagnostic or rejected, not a new HELD_PASS. A newly accepted valid assigned verdict consumes its reservation and increments its role count once in the SAME transaction as its disposition and any blocker; stale valid assigned verdicts retain their counting semantics but get INVALIDATED, never held for advancement. Persist the source result ID, candidate/context, interrupted stage, original reservation/count receipt and disposition. Repeated escalation or duplicate result delivery reuses that record; it does not count again or create duplicate blockers. Apply these rules before a competing resolution/resume can observe an empty blocker set. Verdict arrival before versus during bounded reviewer termination does not withdraw the durable stop intent; containment must still be proven before restoration/release:

| Pending quality result or valid assigned review verdict reconciled while ESCALATED | Escalation disposition | Resolution / later effect |
| --- | --- | --- |
| Standard or adversarial FAIL | `BLOCKED_FAIL`; OPEN `review-failure` blocker linked to the counted verdict | Not operationally resolvable or waivable. Child cycle/cancellation required even with unused S/A/C capacity; no Q6 dispatch after restoration |
| Verification assertion FAIL | `BLOCKED_FAIL`; OPEN `verification-failure` blocker linked to raw FAILED evidence | Only an exact permitted FAILED-outcome waiver or complete §5 known-baseline classification using existing evidence may resolve it in this cycle. Atomically mark the route `DISCHARGED` with the effective HUMAN-WAIVED/KNOWN_BASELINE_FAILURE evidence when its blocker resolves. No rerun, diagnostic launch while escalated, C use or delayed Q6 correction. If neither resolution is eligible, child cycle/cancellation is required |
| Review or verification PASS, still bound to unchanged candidate/pinned context and authentic registered result | `HELD_PASS`; retain original receipt and once-only routing obligation, not an OPEN quality-failure blocker | While ESCALATED, do not route, dispatch, or count again. Unrelated unresolved blockers still prevent restoration. After all blockers resolve, restore the interrupted stage/PAUSED with HELD_PASS retained; the owner's separate resume applies the once-only release below |
| Result whose candidate/context/provenance is invalid, or whose held route no longer matches the interrupted stage | `INVALIDATED`; retain evidence/counts and an OPEN `result-route-invalid` blocker | Cannot be operationally restored or routed; explicit child cycle/cancellation required. Invalid identity/containment additionally retains safety/quarantine rules. No synthetic PASS or spare-ordinal re-review on the unchanged cycle |

Invalidation takes precedence over HELD_PASS retention; review and verification FAIL blockers are never lost merely because other invalidation blockers also exist. A temporary unmet prerequisite (e.g. waiver expiry on an otherwise unchanged candidate/profile) holds a PASS behind that prerequisite blocker; it is not itself a change to the reviewer result's identity. Legitimately renewing the waiver does not rewrite that PASS or grant automatic routing. Actual candidate/base/pinned-context drift, conflicting results or revoked result provenance instead invalidate the route, and later supplying configuration cannot reactivate it. Terminal cancellation/supersession never releases held results. Quarantine exit only returns PAUSED with delivery still ESCALATED; pending cancel or containment intent cannot be bypassed by a held PASS.

**Once-only release:** after normal blocker-set restoration to the matching stage/PAUSED, an authenticated owner resume atomically revalidates every HELD_PASS (along with ordinary pending routes), all current gate evidence/authority, candidate/context, containment and absence of stop/cancel intent. A consumed PASS ordinal needs no fresh slot for its OWN role; only the NEXT required reservation needs available capacity. Standard PASS reserves one adversarial ordinal and advances; adversarial PASS with current standard evidence advances to AWAITING_ACCEPTANCE without another review; verification PASS satisfies its check and normal gate evaluation waits for all required checks. No current role re-review is reserved. Apply each routing effect and mark it APPLIED in the same transaction, without recount or C/R/D use. A failed revalidation/capacity guard atomically records an explicit blocker, re-escalates from the restored stage with that stage as `resume_stage`, and settles ESCALATED/PAUSED once contained (otherwise applies quarantine) rather than returning ACTIVE with a stranded route; irreparable result/stage/budget invalidity requires a child cycle. Replays return the recorded effect, including an existing next-stage reservation, never a duplicate launch. A concurrent new failure or invalidation forces CAS reload and blocks release. DISCHARGED failure routes cannot be replayed into classification or Q6; waiver/known-baseline revocation reopens their failure blocker under the existing rules.

Nonterminal means PREPARING, QUEUED, DEVELOPING, VERIFYING, STANDARD_REVIEW, ADVERSARIAL_REVIEW, AWAITING_ACCEPTANCE and ESCALATED, regardless of control state. These are the stages covered by generic interruption/cancel rules. PREPARING may wait for owner refinement/approval without launching workers; there is no automatic expiry or budget renewal. Owner may explicitly supersede or cancel it. ACCEPTED, CANCELLED and SUPERSEDED cycles do not resume. An accepted cycle may be the immutable parent of a new cycle through the separate merge-handoff rules (§7); its recorded acceptance is not erased. Human resolution never synthesises a missing review PASS.

### Operational resolution and control transitions

All rows require version-guarded events and recorded actor/evidence. Control states never reset counters, pinned context, execution deadlines or Q3 replacement use. `resume_stage` records the stage interrupted by the FIRST escalation; new blocker observations while already ESCALATED do not overwrite it with ESCALATED. Clearing control does not itself clear ESCALATED or permit a terminal cycle to dispatch.

### Blocker set and partial resolution

Each escalation records durable blocker IDs with kind, affected check(s)/candidate, evidence, required resolution and OPEN/RESOLVED status. History is append-only; a new failure/revocation reopens the applicable blocker through a new event rather than deleting earlier evidence. Ordinary pending/running checks are not escalation blockers until an actual failure, missing completion artifact or dispatch/configuration problem is observed.

The three owner-resolution rows below validate only the targeted blocker(s); other OPEN blockers do not prevent recording a valid partial resolution. A single shared configuration update may resolve all named check blockers provided every target's eligibility independently validates. A command targeting multiple blockers commits all targeted resolutions atomically only if each target's own guard passes; otherwise reject that command without partial mutation. Separate valid commands may always resolve items incrementally.

After each resolution, the controller reconciles pending-result escalation dispositions above and recomputes the entire blocker set under the same state-version transaction. No pending FAIL may be omitted from that set; HELD_PASS remains a routing obligation across restoration, not permission to bypass an OPEN blocker. If any OPEN blocker remains, stay ESCALATED/PAUSED and dispatch nothing. Only if none remain, pinned context/containment are valid and no terminal quality verdict is bypassed, restore `resume_stage`/PAUSED. The owner must then explicitly resume control; only ACTIVE permits dispatch. Initial check allowances remain per-check: after resume each eligible, never-launched check may launch its initial execution once. Neither resolving a blocker nor restoring VERIFYING means its check has passed. Gate advancement still waits for every required check's valid evidence. CAS conflicts reload/revalidate the entire set, so a concurrent new failure cannot be lost behind a resolution.

### Running sibling checks during VERIFYING escalation

For a safe verification-only blocker (missing configuration for a never-launched check, a failed pre-review check, or missing evidence with no provenance/safety anomaly), already-registered sibling checks continue under ESCALATED/PAUSED observation if their own authority/environment remain eligible, their execution deadlines remain finite/unchanged, and enforced confinement prevents writes to the candidate or other checks' scratch areas. Record the identity/confinement proof and decision to keep observing each such run. No new or replacement execution launches while ESCALATED, even if another check's configuration is fixed. Unknown confinement, unsafe behaviour, candidate drift, authority revocation or owner cancel overrides this exception: request bounded termination and quarantine if containment cannot be proved.

A continuing sibling's valid result is recorded and independently verified while paused: PASS satisfies only its own check; FAILED adds an OPEN blocker under the existing sticky-failure rule; malformed, unattributable or conflicting completion results use the uniform execution-failure rule below (and quarantine where provenance/containment is unsafe). Missing attachment of an independently authenticated, valid completed result is instead the evidence-retrieval case defined below. Neither result advances the delivery stage or clears unrelated blockers. An in-flight check remains running rather than becoming “missing evidence” merely because another check escalated. An observed sibling timeout/crash follows the uniform paused-execution-failure rule below, whether delivery is still ESCALATED or has been restored to VERIFYING/PAUSED. No post-restoration exception or deferred Q3 retry exists.

### Uniform paused-execution-failure rule — direction accepted in A-004

An **execution failure** here means an infrastructure failure of an assigned execution: failed launch, crash, timeout, transport failure requiring replacement, or malformed/unattributable/conflicting completion. No completion by the execution deadline is a timeout, not proof of success. This is distinct from both a valid quality FAIL and a valid completed execution whose retained artifact has not yet been retrieved/attached.

The **evidence-retrieval** case requires an independently authenticated completion receipt proving the same registered run, candidate/context, valid result and retained artifact identity/digest/location; a worker's unsupported claim or a malformed result is insufficient. The artifact's absence from the package adds an OPEN evidence-retrieval blocker, not paused-execution-failure. Retrieving and validating that exact retained output may resolve it under §5/SC-53 even while PAUSED or ESCALATED; no new execution is allowed and it is not reclassified merely by entering PAUSED. If the receipt is invalid, output conflicts, or execution success cannot be established by the deadline, apply execution-failure/provenance handling instead; retrieval cannot repair malformed completion. A genuine quality FAIL in the retrieved output retains its sticky-failure/review semantics, never PASS by attachment.

Valid reviewer FAIL and valid test assertion failure keep their existing review-budget, sticky-failure and profile-waiver semantics; no execution restart is inferred from them.

If an execution failure is observed while control is PAUSED, while RECOVERING from PAUSED, OR while delivery is ESCALATED under ANY control state (including ACTIVE-origin RECOVERING), the controller immediately records an OPEN `paused-execution-failure` blocker with run identity, failure evidence and containment status. Delivery becomes/remains ESCALATED. Confirmed termination yields control PAUSED; unknown containment triggers bounded stop/reconciliation and QUARANTINED if proof is unavailable. Attach termination proof when obtained; it is not a prerequisite for recording the blocker. This blocker requires an individually authorised Q1 child cycle or cancellation. It cannot be waived, cleared by supplying configuration, or transformed into a pending same-cycle replacement. Used initial allowances and the cycle-wide Q3 count remain unchanged regardless of remaining configured replacement capacity.

This applies to owner-paused work and verification restored to PAUSED alike. A healthy observed run may continue or complete under the existing safe-observation rule. Losing observation alone is not proof of a healthy run or a licence to relaunch; reconcile identity and containment first. If reconciliation establishes failure, apply this rule. ESCALATED delivery has the same explicit blocker and containment outcome under every control state; it cannot remain stuck in ACTIVE-origin RECOVERING awaiting an ineligible retry. The blocker name records the conservative no-resume policy, not a requirement that control was literally PAUSED. The escalation gate is not a source of execution authority.

**Escalated recovery settles to PAUSED — direction accepted in A-007:** recovery never returns ACTIVE while delivery remains ESCALATED, regardless of interruption origin or escalation timing. PAUSED prevents dispatch/advancement, not permitted observation. Once required reconciliation and containment are complete, retain safe sibling observations and settle ESCALATED/PAUSED; unresolved stops continue bounded containment, uncertain containment uses quarantine, and pending cancellation follows its existing finalisation rules. This removes the former ACTIVE-preserving exception and any presumed escalation-before-default-pause window. Interruption origin remains audit evidence, not permission to restore ACTIVE. Explicit owner resume is still a separate existing transition; it does not make ESCALATED delivery dispatchable.

**Safe-sibling decisions during recovery:** when a safe VERIFYING escalation is recorded during RECOVERING, evaluate the sibling exception using authenticated current reconciliation evidence, not merely the last pre-interruption proof. In the same state-version transaction, record the escalation/blockers, each eligible run's identity/confinement evidence and keep-observing decision, and the applicable recovery control outcome below. A previously absent keep-observing record is not by itself a stop trigger until this eligibility evaluation has run. If current identity/context/confinement or healthy-run evidence cannot be established, do not defer the decision awaiting potentially better evidence: apply existing bounded stop/quarantine rules. A pending stop/containment/cancel intent is never withdrawn by fresh healthy evidence. If escalation was already recorded, its decisions and stop intents remain binding; reconciliation revalidates continuation against current evidence, never grants it over a required stop. An owner pause uses its own transition to PAUSED with safe observations retained; a concurrent recovery transaction must reload/revalidate after a state-version conflict.

**Empty escalated recovery:** after reconciling known outcomes, RECOVERING with ESCALATED delivery (ACTIVE or PAUSED origin) and no live runs, unresolved launch intents, pending stops/containment/cancellation, or unprocessed results settles to PAUSED under the explicit empty-set row below. This includes a genuinely empty execution history and a fully reconciled completed history. This row takes precedence over the healthy-completion exit when its guards hold; an empty set never vacuously authorises ACTIVE. Failure observations and their required blockers are processed first; missing proof of absence/containment is not an empty set. Blockers and completed evidence remain intact, with no dispatch or quality advancement.

Both restoring `resume_stage` and owner control resume must reconcile known run outcomes and persisted failure observations before their state-version transaction. A pending failure observed during PAUSED retains that classification across restarts/control changes; unknown order between a failure and resume is handled conservatively as paused failure. After a validated ACTIVE resume with no known failure, genuinely new ACTIVE failures use Q3's existing eligible recovery path. A controller entering PAUSED with an already-known unresolved execution failure (including an interrupted ACTIVE recovery) records the same blocker rather than carrying a retry through pause. No replacement launches while PAUSED, ESCALATED or QUARANTINED, and no failure's recorded origin is rewritten to satisfy the ACTIVE-recovery guard.

An initial allowance remains used once its execution has launched. Safe observation consumes no additional allowance or Q3 replacement. If the controller must terminate a sibling for context/safety/cancellation, that execution remains used; record an OPEN missing-evidence/replacement-required blocker for any required check left incomplete. The stop itself does not qualify for a Q3 retry or restore an initial allowance. A new cycle or cancellation is required rather than an operational resume that silently reruns the terminated check. Result reconciliation and any necessary child-cycle authorisation follow the existing containment rules. These rules do not require concurrent checks: a sequential verifier applies the same blocker accounting without running siblings.

A review FAIL that has escalated (rather than entering the authorised Q6 correction path), or a failed human acceptance observation, cannot be resolved by operational resume. A pre-review FAILED result remains blocking for the SAME candidate except for a profile-permitted waiver or the proven known-baseline classification in §5; a later rerun PASS is never a substitute. Authorised Q6 corrections produce a NEW candidate with new evidence; they do not erase earlier failure. Owner-authorised retries outside Q3 require a new explicitly budgeted cycle; there is no same-cycle manual retry loop. Observing an existing run, attaching its already-produced artifact or recording a valid permitted waiver is not a replacement execution. Producing new evidence through a rerun IS a new execution, even if an owner launches it outside the controller; §5 registration/eligibility rules apply.

### Reservation lifecycle

A review attempt reservation is `RESERVED`, then either `CONSUMED` by one valid completed verdict (including stale PASS/FAIL), or `CLOSED_UNUSED` when the cycle is cancelled/superseded and the run is proven unable to produce a further verdict. RESERVED survives pause, recovery, escalation and a Q3 replacement run. No release back to the same cycle's available budget is permitted. CLOSED_UNUSED is retained history, not a reusable ordinal. Duplicate results are no-ops; conflicting results escalate the nonterminal cycle and preserve the first accepted result (terminal cycles retain an anomaly and block any merge handoff).

Completed plus outstanding review reservations cannot exceed the limit. Only one review attempt is active per cycle at a time. A safely replaced run is fenced/closed before accepting the replacement's verdict; delayed output from that replaced run is diagnostic only. Completed verdict/counter/transition are one transaction. A valid assigned verdict arriving after escalation due to staleness still consumes its reservation but cannot resume the cycle. Cancellation/supersession finalisation waits for reconciliation of completed verdicts; later output from closed runs is retained diagnostically, never used to reopen budgets.

## 4. Review-budget and revision policy proposals

### Q1 — New cycles require explicit authorisation (O-002)

A new immutable cycle requires an explicit owner command naming the parent, findings/scope, exact contract/spec/policy/profile versions and limits. Required after terminal failure, acceptance-stage requested revision or pinned-policy/context changes. A bare “fix this” message is not authority. Child creation retains the lineage/containment guards and old counters; all required gates repeat.

Before terminal failure, either standard or adversarial FAIL may use Q6's configured same-cycle correction path. After terminal escalation, unused capacity is not permission to reopen that path. No review-counter resets or old-PASS reuse. Initial implementation supports an owner-requested budget change through a newly authorised child with a different pinned policy, not in-place mutation of a live cycle.

### Q2 — Freeze review candidates; escalate unexpected changes (O-003)

Code changes are permitted only in initial DEVELOPING or a controller-admitted Q6 correction episode. A correction creates a distinct candidate and invalidates all prior candidate-specific verification and review PASSes for advancement; repeat verification, standard and adversarial review. This includes authorised correction after adversarial FAIL. Unexpected head changes during review/acceptance still escalate; scope/base/pinned-context changes require a child cycle, never an automatic rebase or budget reset.

The target-branch tip B1 is captured at the first development claim, not at work intake. A moving target branch is detected before each dispatch, result/verdict acceptance, package presentation, human acceptance and merge handoff. After capture, any target-tip drift in DEVELOPING (including the fix), VERIFYING, either review or AWAITING_ACCEPTANCE escalates, preserving counters. No automatic rebase is permitted, including during the post-FAIL fix. The authorised developer may change the work-branch head only in its assigned DEVELOPING stage; external/unattributed head changes always escalate. PREPARING/QUEUED have no captured candidate, so target movement there only changes the tip captured at claim. After ACCEPTED, drift invalidates the separate merge handoff (§7).

Never silently replace the stored base. Old evidence stays in history marked stale. New commits are not assumed harmless, even if labelled docs-only. A stale valid FAIL increments its role counter but escalates; it does NOT grant a Q6 correction. Staleness handling takes precedence over normal PASS/FAIL stage routing.

A well-formed verdict for its assigned candidate consumes its reserved attempt even if that candidate became stale while the reviewer ran. Record it as historical evidence, but it cannot advance the new candidate. Malformed or misattributed results do not consume a completed quality verdict. Cancelled/no-verdict runs retain their reservation until safely resolved; cancellation is not a budget-recycling mechanism.

Rejected alternative: automatically review an externally changed latest head while capacity remains. Only explicit Q6 correction intents authorise same-cycle new candidates; counters and pinned B1 never reset.

### Q3 — Bounded operational retries; no hidden quality-fix loop (O-004)

Use the pinned policy's `max_replacement_executions` (Rmax) and `replacement_backoff_seconds`, shared across all worker, verifier, diagnostic and reviewer executions in the cycle. Each eligible replacement consumes one allowance atomically BEFORE launch; exhausted allowance escalates. No reset between stages/candidates/restarts. A no-op observation/reattachment is not a replacement. The old values one and five seconds are illustrative configuration values, not hard-coded product ceilings. Manual bootstrap still stops for owner guidance after any infrastructure failure.

Eligible only for ACTIVE-origin recovery with no intervening pause/escalation AND no pending Q6 correction intent. Q6's old-candidate failure precedence below overrides Q3 eligibility even when R remains. Otherwise eligible failure kinds are: proven failed launch, transient verifier transport failure, or timeout/crash after termination is confirmed. Under accepted direction A-004, an execution failure during PAUSED/paused-origin recovery (including after stage restoration) requires child cycle/cancellation, even with unused Q3 budget; see the uniform rule in §3. Invalid/missing result artifacts, identity mismatch, unsafe activity or uncertain termination escalate immediately. Actual assertion failures are quality evidence, not transport errors: classify under §5 and, if eligible, use Q6's shared worker-correction allowance, not Q3. Malformed output or a launch/crash/timeout never becomes a known baseline test failure.

Each execution needs finite configured execution, heartbeat/lease and cancellation deadlines before eligibility. Exact durations are environment configuration to be validated by runtime spikes; missing values block unattended dispatch. No indefinite waits or polling. An execution deadline is not renewed by heartbeat.

Rejected alternatives: retry forever; reuse review counts as retry limits; or reset retries per run/stage. The proposed cycle-wide allowance is easy to audit, though it may cause extra human intervention. Tune only through approved policy versions and measured evidence.

### Configured policy authority — direction accepted in A-008

The authoritative product policy is an owner-approved immutable configuration artifact, identified by version AND content digest in protected controller storage. The specification defines how it is interpreted. Numerical limits are not compiled constants or permanent 2+1 ceilings. Approval must bind the exact bytes; changing a repository file neither activates it nor changes an existing cycle. New versions govern only newly authorised cycles unless an explicit child decision adopts them. Revocation follows §5; publication alone leaves existing pinned authority intact.

Before creation/readiness, validate the entire policy: Smax/Amax are finite integers >=1 (both independent gates remain required); Cmax, Rmax and Dmax are finite integers >=0; deadlines and replacement backoff are finite positive values. Reject missing/unknown fields, negative/fractional/infinite values, contradictory profiles and unapproved digests. No silent fallback or unlimited sentinel. Concrete default values and environment-specific QA profiles remain separate approved configuration, not inferred from examples.

- Smax / `max_standard_reviews`: total standard ordinals across ALL candidates in a cycle.
- Amax / `max_adversarial_reviews`: total adversarial ordinals across ALL candidates.
- Cmax / `max_worker_corrections`: shared total correction episodes initiated by verification or either review role; initial development is not a correction.
- Rmax / `max_replacement_executions`: infrastructure replacements only, governed by Q3's eligibility rules.
- Dmax / `max_diagnostic_executions`: total registered baseline-comparison/diagnostic executions across the cycle; never grants quality rerun PASS or worker correction authority.
- Profile: required check identities, phases, known-baseline eligibility/comparison protocol, non-waivable gates and permitted outcome-specific waivers; execution/lease/cancellation deadlines, runtime/model/environment eligibility and capacity limits are configuration inputs too. Increasing concurrency does not bypass the initial single-delivery/single-writer eligibility rule.

Configuration cannot disable owner authentication, immutable evidence/counters, same-candidate independent passes, containment, or explicit final acceptance. A worker cannot configure itself out of these invariants. Every cycle stores effective values alongside the digest; every gate verifies the pin/authority and remaining capacity.

### Q6 — Shared bounded correction admission

Let S/A be completed verdict counts, SR/AR outstanding reservations, C the count of correction intents already committed. After counting the current FAIL, a new correction requires **S + SR < Smax, A + AR < Amax, C < Cmax**. Both future reviews are necessary even after adversarial failure. A PASS on the last available ordinal is valid; reaching a cap alone is not failure. Correction may be unnecessary (Cmax=0) on a fully passing initial candidate. Review capacity sufficient for one best-case remaining path does not promise success; further failures re-evaluate the same guards.

Admission also requires ACTIVE control, current candidate/context/authority, in-scope reproducible defect, and no unresolved safety, infrastructure or other escalation blocker. It is allowed only from VERIFYING or the failing review stage, never as an operational escape from ESCALATED. If a guard fails, escalate and retain all results; no worker is dispatched merely because one budget has capacity.

Commit a unique candidate-bound correction intent and increment C once in the same CAS transaction as failure handling. Verification may need classification first (§5); no correction is committed for a known-baseline exception. Multiple classified defects for that candidate join the same pending episode, not multiple increments; check for that existing intent before applying the new-episode C guard. Freeze further ordinary check/review dispatch. Already-launched checks/diagnostics finish under their original finite deadlines; reconcile all outcomes and prove all old executions/write access contained before entering DEVELOPING or launching a writer. Needed bounded classification of already-observed failures may still run from Dmax while ACTIVE. Never terminate a check merely to claim its missing evidence passed; existing stop/failure rules take precedence. **Old-candidate precedence:** once the correction intent exists, Q3 is ineligible for EVERY execution associated with that candidate, including sibling checks and classification diagnostics; freeze includes replacement dispatch. A crash/timeout/transport failure, even proven contained, escalates with C retained and R unchanged, not an old-candidate replacement or silently discarded failure. Unsafe/uncertain containment still uses quarantine. Additional valid assertion failures must be classified before writer dispatch; if classification is necessary but inconclusive, unsafe or cannot fit its remaining D protocol, escalate rather than assuming the discarded candidate makes that evidence irrelevant. This conservative rule intentionally may forfeit an admitted correction; no missing/uncertain evidence is hidden by moving to a new candidate. New safety/infrastructure/context blockers likewise abandon automatic correction and escalate with C retained, not refunded. PAUSE retains the intent without dispatch; explicit resume revalidates all guards except the already-consumed C slot. No new episode is created by replay or restart.

Once the pending episode is fully reconciled, controller transitions to DEVELOPING/ACTIVE for one findings-scoped worker execution with durable intent and normal single-writer guards. The new result must be a distinct committed candidate addressing the recorded defects; no-op or scope-changing results escalate. Test changes must preserve approved acceptance meaning/coverage; deleting/weakening tests to hide failure is a material deviation. At VERIFYING, the new candidate gets its own initial check executions; previous failures remain associated with the old candidate/episode and do not falsely block the new one. S, A, C, R and D remain cycle totals. Changed candidate requires fresh standard AND adversarial PASS, with no old PASS substitution. A failure still present on the new candidate requires another admitted episode; it is never cleared by a same-candidate rerun.

### Q4 — Owner authority and non-waivable invariants (O-008)

Recommend the owner as sole initial approver for design, revisions, profile exceptions and policy changes. A quality-check waiver names the exact check, candidate, evidence IDs, reason, residual risk and expiry/scope. The pinned profile must explicitly allow waiving the actual outcome (BLOCKED/unavailable or FAILED); a generic or absent waiver permission does not allow FAILED. A valid FAILED-outcome waiver may resolve that pre-review blocker in the SAME cycle, by the explicit §3 transition, without erasing the failure or rerunning the check. It cannot bypass other outstanding blockers. Waiver is HUMAN-WAIVED, never PASS.

No waiver of provenance/identity, required design authority, runtime/environment permissions, single-writer safety, hard review limits, independent review verdicts or explicit final acceptance. Policy changes are separate approved work, not an issue instruction or an override field. Deployment authority remains separately configured and disabled initially.

Alternative: delegate classes of decisions to named operators later; that requires explicit capability/authority configuration and audit tests.

### Q5 — Initial work authority without routine stage-kicking (O-008)

Recommend allowing an owner to authorise either one initial work/version or a finite batch naming exact work IDs, versions, scope, review limits and an optional creation deadline (mandatory for batches). The deadline bounds NEW cycle creation only: at or after expiry, no unused entry may create a cycle. A cycle created before expiry receives a recorded derived authority lasting until that cycle terminates or authority is explicitly revoked; expiry of the originating individual/batch grant does not stop PREPARING promotion, running work or valid verdict routing. Record creation time, grant ID and derived authority atomically. Revoking the original grant also revokes its derived authorities and follows §5 invalidation. Individual grants without a creation deadline remain usable until consumed or revoked. Gate revalidation checks the derived cycle authority, not the elapsed creation deadline. The controller advances eligible READY work automatically without another owner action. Required design approval still applies independently. Batch entries are single-use under the work-lineage invariant; they cannot authorise children or reset budgets. All refinements of pinned versions and revisions require an individual Q1-style child decision, including PREPARING refinement. A future standing risk-based intake policy is not authorised here.

Alternatives: require a separate owner action for every initial cycle (simpler, but adds manual intake friction); or accept open-ended policy-level initial authority (more autonomous, but requires an additional eligibility/security design). The bounded batch is a proposed middle ground, not accepted by approval of this revision task.

## 5. Evidence and acceptance boundary

### Context validity

Cycles pin contract/spec/policy/profile versions; they do not follow the newest version automatically. Publishing a new version alone leaves explicitly still-authorised pinned versions eligible. An owner adoption/replacement decision for this work, revocation of a pinned approval/version, or withdrawal of runtime/environment eligibility invalidates the active cycle's context: mark affected evidence stale and ESCALATE (or invalidate the merge handoff if ACCEPTED), preserve counters, contain active workers. Required checks cannot be changed in place. Any resulting scope/version change requires a child cycle. Authorisation validity is rechecked at every gate; this is what “current eligibility” means, not latest-version substitution.

Waiver expiry/revocation before acceptance similarly escalates, without relabelling it PASS. The owner may resolve that operational blocker only by independently verified existing check evidence or a newly valid profile-permitted waiver on the SAME candidate/context; otherwise create a new cycle. Expiry after acceptance blocks merge until revalidated under §7. A stale valid in-flight verdict consumes its reservation but cannot advance.

### Failed evidence, waivers and external execution

For one cycle/candidate/check definition/environment, any valid FAILED result remains authoritative against subsequent PASS results; retain every result, but do not use “latest wins” or rename a run to evade failure. A valid profile-permitted FAILED waiver changes the effective gate to HUMAN-WAIVED without rewriting the evidence. The distinct baseline-classification rule below may instead establish KNOWN_BASELINE_FAILURE; it preserves the same raw FAILED result and never turns it into PASS. Revocation/expiry restores the underlying FAILED blocker. A waiver of unavailable evidence does not cover a later actual FAILED result unless the owner grants a new waiver explicitly referencing that failure and the profile permits it. Candidate/profile changes require the already-defined new-candidate/new-cycle handling; evidence is never relabelled across cycles.

Independent verification executions, including human-operated external CI/test jobs, must be registered with logical check/run identity, exact candidate/context, authorised producer, finite deadline and allowed execution count BEFORE launch. Each required check has one initial verification execution per candidate; a safely recoverable infrastructure replacement may use Q3's configured cycle-wide allowance. A check intent blocked before registration/launch retains its unused initial allowance and follows the explicit pre-launch escalation/resolution rows in §3. Supplying configuration is not a rerun: once restored and control resumed, the initial launch is allowed. This exception requires proof no launch occurred; an ambiguous external launch remains a recovery/quarantine case, never a fresh initial execution. A real FAILED check is not eligible for a SAME-CANDIDATE rerun to clear failure, including owner-supplied reruns. A registered diagnostic comparison may collect additional evidence under Dmax without replacing that FAILED result. A Q6 correction creates a new candidate and new check obligations within the same cycle. Pre-registered independently produced evidence can be attached later without a second launch; unregistered rerun PASS is diagnostic only and cannot satisfy a gate or clear escalation. Owner UAT observations are separately authorised acceptance-phase evidence, not a way to relabel a failing executable check. Developer self-tests are claims, not authoritative verification; additional scratch diagnostics cannot discharge a gate.

Every authentic required-check failure received for the same candidate is retained and investigated; external evidence cannot be cherry-picked to hide a prior registered failure. Unexpected/conflicting output triggers escalation, not promotion. Resolving missing/BLOCKED artifacts with existing evidence means retrieving output from the SAME authorised execution, not accepting an unlimited sequence of new external jobs. Any legitimate Q6 fix creates a new candidate and its initial check executions; it resets none of the cycle-wide review, correction, diagnostic or replacement counts. Detailed check selection remains O-005, but these accounting rules apply to every selected check.

### Baseline-aware verification classification — direction accepted in A-008

Only a valid authenticated assertion result can enter this classification. Preserve raw FAILED separately from the effective disposition: CANDIDATE_DEFECT, KNOWN_BASELINE_FAILURE or UNRESOLVED. No disposition changes a review verdict. For new or modified tests/check definitions/fixtures relative to pinned B1, failure is a candidate defect (test or product); no baseline exception. Scope-changing or unsafe test modifications escalate instead of permitting a weaker contract.

For an unchanged existing test, compare candidate H against the exact pinned base B1, not current main. The pinned profile must define check identity, trusted comparison verifier, environment/dependency/configuration/command equivalence, failure fingerprints and finite repeat protocol. Candidate and baseline run in isolated read-only worktrees with separate scratch space and no owner credentials. Register every diagnostic before launch, including baseline SHA, candidate comparison key, environment and protocol digest, deadline, role and D ordinal. Admit the ENTIRE finite protocol only if remaining D capacity covers it; otherwise escalate as inconclusive. Diagnostics may launch only in VERIFYING/ACTIVE, never PAUSED/ESCALATED/RECOVERING/QUARANTINED. Duplicate requests reuse their recorded intent; no fresh free diagnostic per delivery/restart. A recoverable diagnostic infrastructure replacement consumes R under Q3 without inventing another initial D slot; exhausted/unsafe failure escalates.

Authenticated retained baseline evidence may be reused only if the complete pinned comparison key/protocol matches, all required samples are present and the profile's freshness/eligibility holds; unrelated main/CI failures are not evidence. Baseline PASS with candidate FAIL is a regression and uses Q6. Different failures, flaky/inconsistent samples, unsupported equivalence, unavailable baseline or failed protocol are UNRESOLVED; no optimistic exception. Bounded diagnostics can clarify only within the predeclared protocol/D allowance; exhaustion escalates without a discretionary model retry loop. A single baseline failure is not sufficient evidence for known flaky behaviour. Runtime failure is never an assertion-equivalence result.

KNOWN_BASELINE_FAILURE requires the full protocol to prove equivalent pre-existing failure, the profile explicitly permitting the target check's exception, no evidence of worsening/new failure, no relation to a behaviour this contract must fix, and no loss of meaningful verification of this work. Non-waivable safety/security/authority gates cannot use it. Verification records the evidence-based classification; an agent cannot grant it by assertion. If the check lacks a trustworthy automated equivalence/impact decision rule, mark UNRESOLVED for owner disposition rather than silently delegating authority to an LLM.

Before the exception satisfies a gate, atomically create/link a durable local known-issue record (stable dedupe key for check/failure/environment lineage) with both evidence sets, B1/H, policy/protocol, impact rationale and affected candidate. External tracker sync may be deferred; absent local tracking blocks advancement. Preserve every association, no duplicate issue per rerun. KNOWN_BASELINE_FAILURE is visible in the acceptance package and never reported as PASS or HUMAN-WAIVED. Re-evaluate the classification for each new candidate; evidence conflict, withdrawn exception authority or expiry before acceptance invalidates it and escalates. Post-acceptance invalidation blocks handoff under §7.

While non-escalated PAUSED or RECOVERING, valid assertion failures follow §3's pending-quality routing: record evidence without dispatch, then classify/apply Q6 only upon the defined ACTIVE-return transition. While delivery is already ESCALATED, valid failures are recorded as blockers under the sibling rule; no automatic diagnosis or worker dispatch. Existing authenticated evidence can support a permitted known-baseline resolution via the non-execution blocker-resolution row, with the full guard above and normal blocker recomputation/resume. A true candidate defect already escalated requires owner waiver where permitted or a child cycle, not a delayed automatic correction. Failure while ACTIVE with correction eligibility is not first escalated just to immediately bypass an escalation.

### Evidence phases

The work/profile assigns every criterion/check to a phase before readiness; no mandatory check may silently shift to a later phase.

- **Pre-review:** executable build/tests, applicable security/a11y/performance/visual checks, approved design references, implementation design comparison and runnable demo/walkthrough instructions. Required evidence must PASS, be explicitly permitted HUMAN-WAIVED or satisfy the full KNOWN_BASELINE_FAILURE guard before standard dispatch and remain current thereafter.
- **Review-stage:** required standard/adversarial verdicts and structured findings, produced by their respective independent reviewers. These cannot be demanded as inputs to their own stage. Each stage requires all earlier-phase evidence.
- **Acceptance-stage:** owner or named authorised human's hands-on observations/UAT and explicit disposition. Before review, the contract must name the procedure, candidate fixture and observer role; the actual human observation may be pending until AWAITING_ACCEPTANCE. No automated test obligation can be replaced by calling it UAT.

In AWAITING_ACCEPTANCE, the controller may attach authenticated human observations and assemble the package without changing code/context. Missing acceptance-stage observations keep the cycle in AWAITING_ACCEPTANCE with an incomplete package and no approval. A failed mandatory human observation escalates; missing/invalid earlier-phase evidence discovered here also escalates. Passing observations leave the stage unchanged until explicit owner approval. Record each attachment/outcome in the ledger. An agent may format or attach evidence, but cannot impersonate the human observer or infer acceptance.

Workers can author tests and report results; independent verification inspects the actual commit and required artifacts and reruns checks or validates trusted CI provenance. Runtime output alone is not a trusted test attestation. Runtime/model/skill versions are attribution metadata, not proof.

Mandatory evidence key: repository + contract/spec versions + cycle + policy/profile versions + head/base SHA + execution environment/check definition. Artifact references must resolve to retained content with a recorded digest. A mutable URL, success-shaped JSON or exit code zero is insufficient. Preserve FAILED, BLOCKED, HUMAN-WAIVED and KNOWN_BASELINE_FAILURE distinctly, including raw results behind effective dispositions.

Each Done when criterion maps to an executed check or explicit human observation. UI-sensitive work needs the approved UX artifact and comparison; backend/docs work records justified N/A rather than invented screenshots. A PASS reviewer cannot waive absent tests, accessibility/security requirements or design approval. Reviewers use separate fresh contexts and read-only candidate access; test writes go to isolated scratch space, not the candidate branch. Independence requires separate executions, not necessarily different vendors/models.

The acceptance package includes outcome, criterion matrix, current evidence, all review/correction/replacement/diagnostic histories and counters, known-baseline failures and issue links, finding dispositions, demo/walkthrough, design conformance, risks and release notes. Owner acceptance is a structured command bound to this package digest and exact candidate, never inferred from chat or absence of objections. Findings persist with confirmed/rejected/duplicate/uncertain dispositions. A finding disposition change alone does not rewrite a failed verdict or resume an escalated cycle.

Human acceptance binds to the package/candidate. A post-acceptance branch change blocks merge handoff and records approval invalidation without rewriting history. A merge/squash commit with a different identity requires integration evidence for the actual merged artifact before release readiness; approval of a PR is not evidence of successful deployment.

## 6. Durability, dispatch and recovery

SQLite transactions must atomically persist guarded state updates, event/dedupe records, reservations/counters, lease generation and external-action intents. Use state-version compare-and-swap and unique constraints for event keys, accepted results and active ownership. Transaction rollback leaves neither a consumed counter nor a half-transition.

Starting an external process is not atomic with SQLite. Persist an intent with a stable dispatch key before launching; attach the returned run/process identity afterward. On restart, reconcile unresolved intents before launching anything else. Adapter/launcher must prove lookup/deduplication by that dispatch identity, or the ambiguous launch is quarantined for human containment—not blindly repeated. Exactly-once external launch is not claimed merely because the database is transactional.

Lease generation fences controller/result acceptance, **not filesystem writes by a rogue/stale process**. Lease expiry alone does not grant a new writer. Confirm the prior process and descendants have stopped and write access is contained before handing over the branch/worktree. If the selected runtime cannot establish that, quarantine the workspace/branch and block reassignment. A new worktree alone is not proof that the old process cannot write the repository.

Restart reconciliation checks intents, processes, lease generations, branch heads/bases, artifacts, accepted verdicts and pending external sync. Duplicate webhooks wake reconciliation; they do not grant ownership. Persist a logical action key for GitHub publication and discover an existing PR before retrying an ambiguous publish. Notifications and PR sync failures cannot reset quality counters or allow duplicate development.

Operator controls: pause prevents new dispatch; shutdown/cancel attempts bounded termination; uncertain containment quarantines affected work. Resumption rechecks eligibility and evidence. Worker-reported policy changes, secrets requests and forbidden destinations are rejected outside the worker prompt. Precise OS confinement and launcher mechanisms remain implementation/spike obligations, not solved by this design prose.

## 7. Separate release handoff

Delivery ACCEPTED creates a separate merge-handoff record in `PENDING`; it is not permission to merge automatically. Initial merge authority is proposed as owner-only/manual and must be approved before SF-002E is READY (O-006). The record binds the accepted cycle, H1, target tip B1, approval and integration-check definition. Handoff transitions:

| From / actor | Guard / evidence | To / effect |
| --- | --- | --- |
| PENDING / controller detects drift, revoked authority, expired waiver or result conflict | Head differs from H1, target differs from B1, or context validity lost; record observation | INVALIDATED; no merge; accepted delivery history unchanged |
| PENDING / owner authorises and performs manual merge | Revalidated H1/B1 and pinned authority/evidence; protected or atomic expected-target update; record actor/action and actual merge identity M1 | MERGED; create release record from M1 |
| PENDING / operator cannot prove atomic target check or merge provenance | Record missing proof; do not rely on a prior non-atomic tip check | INVALIDATED; no authorised merge; any externally observed merge is quarantined from release eligibility pending human reconciliation |
| INVALIDATED / owner authorises revision | Explicit Q1 decision; expected work tip is accepted parent, no existing child; containment/result reconciliation complete | Atomically set handoff REVISED with unique child link, transfer work tip to PREPARING child `(0,0)`; parent stays ACCEPTED. Same decision replay returns child; different decision against old parent rejected |
| PENDING or INVALIDATED / owner declines merge | Exact handoff decision; no merge action in flight; containment/provenance reconciled | CLOSED; preserve acceptance history, release live-delivery slot; no merge. Later reopening requires explicit child decision and same unique-child/tip guard, atomically CLOSED→REVISED |

Base drift always invalidates BEFORE merge; integration tests are not a substitute for reviewed B1. A merge/squash M1 generated solely from the authorised H1 and unchanged B1 is a legitimate new identity, not a revision: preserve lineage, verify the actual integration artifact and required checks before RELEASE_READY. If an external manual merge used changed inputs, record the fact but block release readiness; do not call it a valid handoff. Runtime/API atomic merge enforcement is later work and blocks merge automation, not this design-only review.

Record actual merge identity and create a separate eligible release record only after the authorised merge is verified. Proposed release states follow the source: `MERGED` → `RELEASE_READY` → `STAGING_VALIDATED` (when configured) → `AWAITING_RELEASE` → `DEPLOYED` → `POST_DEPLOY_VERIFIED`, with `FAILED`/`ROLLED_BACK` alternatives.

Each release record binds environment, immutable artifact/version, operator, approvals, configuration/migration notes, smoke checks and rollback/forward-recovery procedure. Missing required staging evidence blocks; a permitted skip needs explicit policy rationale. Production execution stays disabled in this initial design. Documentation-only changes record “no deployable artifact” and applicable N/A, not a fictional DEPLOYED status.

Release failures create incident/escalation evidence and new tracked fix work; they neither consume nor replenish the delivery review budget. Product outcome observation is separate from technical deployment success and may return work to discovery.
