# Accepted risks

Review findings the owner chose not to fix (A-042). Each line says why the risk is acceptable and what event would reopen it. Unlike [parked.md](parked.md), a line here gates no ticket. When the reopen event happens, the finding becomes a ticket or a parked line.

| Source | Finding | Why accepted | Reopen when |
| --- | --- | --- | --- |
| 08-g (A-068) | Every pi run, developer and reviewer, can overwrite or delete `~/.pi/agent/auth.json`, the owner's pi login. | Runs could already read it (D-021). Without the write, a refresh inside the sandbox loses the rotated refresh token and logs pi out. The worst case is a fresh `pi` login. | A run damages the file, or pi gains a refresh-only command the controller could run outside the sandbox. |
| sweep-git-hardening (A-099) | Verify's checkout reads no git attributes, so a repository's `eol`, `ident` and filter conversions (git-lfs) are not applied there; checks see the commit's stored bytes. With the owner's `core.autocrlf=true`, `-text` and `binary` no longer opt files out. | Reading the candidate's attributes lets it pick a filter program the owner configured (git-lfs), which then runs outside the sandbox against a server the candidate names. No repository here relies on these conversions, and 08-a already listed them as a limit. | A repository the factory runs relies on `eol`, `ident` or LFS content in its checks. The alternative is `--attr-source=<head>` with every `filter` forced off, macro attributes included. |
| 10-b (A-078) | A workflow named by the repository layer (`.factory/config.json`) is imported into the controller and runs unsandboxed. | It is read at the base SHA, so only code the owner has merged runs; a candidate cannot reach it (A-037 puts damage before malice). Since sweep-head-workflow (A-095) this is checked: the base must be on a local branch or tag outside `sf/*`. A candidate the owner copies to a branch of their own counts as merged. | A workflow can be loaded as data, or the factory runs repositories whose base the owner does not control. 10-e (A-085): such a workflow could also read a grant file at import; refusing a repository workflow that asks for grants (A-083 Q5) does not stop that. |
| foundations research (A-115) | With pasta (A-106) and host loopback unmapped, a networked sandbox still reaches host services through Docker-bridge addresses (PostgreSQL on 172.17.0.1, SSH on 172.18.0.1, probed) and LAN hosts (the router on 192.168.1.1). pasta cannot filter destinations. | pasta closes 127.0.0.1 cheaply now; only the egress proxy closes the rest (`docs/research/2026-10-20-foundations/security.md`, gap 3 and P1). | The egress proxy row in `docs/plan.md` is built, or the factory runs a repository whose agents should not reach the LAN before then. |
| 11-a (A-130) | `cancel` prints its `Cycle:` and `Stage:` lines after every cancel is recorded. If a store write fails part way through a cancel of several cycles, the cycles already cancelled are not printed; the store keeps each cancel and the error prints. | Restoring the old order needs a print callback on `cancelWork` for that one failure. The store, not the output, is the record. | A cancel's output is used to tell which cycles were cancelled. |
| 11-d adversarial (A-143) | An owner command with no `--command-id` is not deduplicated. On a workflow with two human stages and a stage between them that keeps the head (OWNER → MERGE → FINAL), a retyped or redelivered `accept <sha>` also accepts the second human stage. | Only hand-run commands reach it: the observer kit always sends an ID, and A-140 records none rather than a random one that would deduplicate nothing. The default workflow has one human stage. | A workflow the owner runs has two human stages on one head, or a hand-run `accept` accepts a stage the owner did not mean to. |
