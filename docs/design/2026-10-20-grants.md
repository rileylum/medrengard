# Grants (ticket 10-e)

## Problem

A merge or deploy step needs a credential, and A-052 keeps credentials with the controller. A-074 decides the shape: a workflow asks for a grant on a command stage (`grants: ['github']`); only the personal or job layer gives it; the secret reaches that stage's sandbox alone, with network on; the stage runs only when every verdict and verification is for the current head; it writes the head it acted on to `outputDir/head`, and a missing or different head escalates.

Facts the design must respect:
- `verify` (`src/verify.ts`) builds one `Policy` per command stage. `Policy.env` reaches bwrap as `--setenv NAME VALUE` after `--clearenv` (`wrapBwrap`, `src/sandbox.ts`), and `runCheck` also adds it to the spawn environment.
- **A value in bwrap's argv is readable by every user on the machine.** `/proc/<pid>/cmdline` is world-readable when `/proc` is mounted without `hidepid`, as it is here, and the outer bwrap process lives as long as the command. `Policy.env` cannot carry a secret.
- The spawn environment (`/proc/<pid>/environ`) is readable only by the owner's own processes, which can read the secret's file anyway.
- Every adapter spawns with `process.env` (`src/runtime/spawn.ts`). Under bwrap, `--clearenv` hides it; under `none`, the developer and reviewers inherit the controller's whole environment.
- The repository layer may already set the workflow, read at the base SHA (10-b). It may not give grants: `OWNER_ONLY.grants` in `src/config.ts` refuses the key.
- `job.checks` may come from the repository layer. A stage that runs `job.checks` would run the repository's commands with the owner's token.
- `apply` lets the head change only through a commit stage's `developer_result`. A `head_changed` event in any other stage escalates.
- The reviewer is shown every command stage's `<name>.stdout|stderr|exit` for the head (`src/review.ts`). It is not shown `output/`.

## Interface

**Giving a grant** (personal or job layer, `src/config.ts`).

```json
"grants": {
  "github": { "variable": "GH_TOKEN", "file": "secrets/github-token" }
}
```

- `variable` is the environment variable the stage's commands see. It must match `[A-Za-z_][A-Za-z0-9_]*`. It may not be `PATH`, `HOME`, `LANG` or `SF_REQUEST`, which the controller sets.
- `file` holds the value. A relative path resolves against the layer's own file, like `runtimes` and `workflow`. The value is the file's text with one trailing newline removed. The file is read when the stage runs, not at load. `loadConfig` refuses a file that does not exist or that sits inside the job's repository, where a commit could carry it.
- There is no literal value and no value from the controller's environment. A literal would put the secret in a job file. A value in the controller's environment reaches every process the controller spawns under `none`.
- `grants` joins `PERSONAL_KEYS` (and so `JOB_KEYS`), and `NESTED`. The job file can add a grant to the personal file's grants, or replace one by name.

`Config` gains `grants: Record<string, { variable: string; file: string }>`, with paths absolute. `loadConfig` passes it to `run`, and `run` passes it to `verify`. `run` refuses a workflow that asks for a grant the configuration does not give. It does so before `develop`, so a paid developer run is not wasted. This follows the `workflowDir` check in `run`.

**Asking for a grant** (`StageDef` command, `src/lifecycle.ts`).

```ts
| { kind: 'command'; transitions: Transitions; budget?: number; run?: Command[]; network?: boolean;
    /** Names given by the personal or job layer. The stage's commands see each value in its variable (10-e). */
    grants?: string[] }
```

`checkWorkflow` refuses:
- `grants` that is not a non-empty array of distinct names matching `[a-z0-9_-]+`;
- a grant stage without its own `run`, because `job.checks` may come from the repository;
- a grant stage without `network: true`;
- a grant stage whose `FAIL` transition is set to anything but `ESCALATED`, because a grant stage acted outward and a retry could act again;
- a command named `head` in a grant stage, because that name is reserved for the controller's head check.

`loadConfig` refuses a repository workflow that asks for any grant.

**Delivering the secret** (`src/sandbox.ts`).

```ts
interface Policy {
  // ...
  /** Reach the command through the spawn environment, never argv: bwrap's argv is world-readable. */
  secrets?: Record<string, string>;
}
```

`runCheck` spawns with `{ ...process.env, ...policy.env, ...policy.secrets }`. When `secrets` is set, `wrapBwrap` replaces `--clearenv` with one `--unsetenv NAME` for each other name in that environment. bwrap then passes only the secrets through, and sets `PATH`, `HOME`, `LANG` and `policy.env` as it does today. argv carries names only, never a value. Without `secrets`, the argv is unchanged.

`verify` sets `secrets` only for a stage with `grants`, and reads each file just before it runs the stage. No other `Policy` in the code takes `secrets`.

**Under `sandbox.backend: none`.** `run` refuses a workflow with a grant stage. With nothing confining it, the developer could read the secret's file, and A-074's "that stage's sandbox alone" would not hold.

**The head gate** (`verify`, before anything runs). A grant stage runs only if all of these hold:
- for each stage that has recorded a verdict, verification or `accept` in this cycle, the last one it recorded is for the candidate head;
- at least one PASS verdict is for that head.

Otherwise `verify` throws before it writes anything, and `drive` records `reject_dispatch` with the reason. The cycle escalates, and nothing ran with the token. The second rule refuses a grant to a workflow with no review at all.

**The head file** (`verify`, after the commands). The controller reads `output/head` and trims one trailing newline. If the file is missing or names a different head, `verify` records a reserved check `head` with result FAIL. Its `head.stdout` says what was found. The cycle escalates through the grant stage's `FAIL`, which can only be `ESCALATED`. The verification event is still recorded, so the evidence binds to the SHA. This uses the same pattern as `TREE_CHECK`.

**Redaction.** Before writing `<name>.stdout` and `<name>.stderr`, `verify` replaces each grant's value with `[grant <name>]`. `output/` is not redacted. The command writes `output/`, and no reviewer is shown it (A-081 Q4).

**What is recorded.** The `verification` event gains `grants?: string[]`, the names the stage held, never the values. The field is optional, so older stores replay. `SHAPE` checks it. The default workflow's hash does not change.

**The command-stage kit.** `commandKit` gains a `grants` option of fake values. When it is set, one more case checks that the stage writes the request's head to `output/head`. This is the contract a user's merge command must keep.

## Alternatives

1. **`--setenv` through `Policy.env`, as 10-c left it.** No new code, but bwrap's argv would expose the token to every user for the length of the run. Rejected.
2. **The secret as a file inside the sandbox (`--ro-bind-data FD`), with the variable naming the file's path.** No environment at all, but bwrap reads the data from a file descriptor, and `spawnRuntime` passes stdio only. It is also not yet confirmed that `systemd-run --scope` keeps an extra descriptor. Most tools also want the token itself in a variable (`GH_TOKEN`), so every user would write a wrapper. Kept for later, for a credential that has to be a file (an SSH key or a kubeconfig).
3. **A load-time graph check instead of the run-time head gate: refuse a workflow where a grant stage can be reached without passing a verdict stage.** It catches a bad workflow before it runs, but it reasons about paths, not about what happened. It also cannot see a verdict for a stale head. Rejected. The run-time gate checks the events themselves.

## Tests

- `wrap` with `secrets` produces an argv that contains no secret value, and the command sees the variable inside bwrap. One test each for the cgroup isolation and the process-group isolation.
- A workflow DEVELOPING → VERIFYING → REVIEW → GRANTED, run with the fixture runtimes: the secret appears in GRANTED's environment and nowhere else. The developer, the check stage and the reviewer each dump their environment and argv to a file, and none of those files holds the value.
- `loadConfig`: the personal and job layers give a grant, the job layer replaces one by name, and the repository layer is still refused. A missing file, a file inside the repository and a bad `variable` are each refused. A repository workflow that asks for a grant is refused.
- `checkWorkflow` refuses each malformed `grants` value, a grant stage without `run`, one without `network: true`, one with a `FAIL` transition that is not `ESCALATED`, and a command named `head` in a grant stage. One test each.
- `run` refuses a grant the configuration does not give, and any grant under `none`, before the developer starts.
- The head gate: a verdict for an older head (a fix run that skipped review), and a cycle with no PASS verdict, each escalate with nothing run. A cycle whose last verdict and verification are both for the head runs.
- The head file: missing escalates, a different head escalates, and the right head passes. Each case records the verification.
- A command that prints its token shows `[grant github]` in `<name>.stdout` and in the reviewer prompt, and never the value.
- The `verification` event records the grant names. A store written before 10-e still replays, and the default workflow's hash still equals the pinned literal.
- The kit's head case passes on a fixture that writes the head and fails on one that does not.

## Risks

- **The controller cannot stop a stage from misusing its token** (A-074). A merge command that runs the candidate's code (`npm run merge` in the checkout) gives that code the token and the network. The gate and the head file make a wrong merge visible and escalated; they cannot prevent one. A grant stage should run a `{ file }` argument or a system binary, never the candidate's scripts. The note says this. The code cannot enforce it.
- **Redaction catches the literal value only.** A command that prints the token base64-encoded, or one character per line, gets past it. Redaction protects against accidental printing, not deliberate printing.
- **The owner's other processes can read the token** through the spawn environment of `systemd-run` and bwrap. They can read its file too. This is accepted as the same exposure.
- **`--unsetenv` is a deny list.** A name added to the spawn environment but not unset would pass through. The list is computed from the exact environment handed to the spawn, in one place, and a test pins it.

## Questions for the owner

**Q1 — A grant's value comes from a file only, and reaches the stage as an environment variable.** A-074 says the layer maps the name "to an environment variable or a file". I read that as where the value comes from. Recommended: from a file only, delivered as the variable the grant names. A value taken from the controller's environment would reach every process run under `none`. A file inside the sandbox (alternative 2) can come later, when a credential needs one.

**Q2 — Refuse grants under `sandbox.backend: none`.** Recommended: refuse. Nothing confines the developer there, so "that stage's sandbox alone" cannot hold.

**Q3 — The head gate: the last verdict, verification and `accept` from each stage are for the current head, and at least one PASS verdict is for it; otherwise escalate before anything runs.** Recommended: yes. The PASS-verdict rule means a workflow with no review at all cannot hold a grant.

**Q4 — A grant stage requires `run` and `network: true`, and its FAIL always escalates; a wrong `output/head` is a reserved `head` check that FAILs.** Recommended: yes. Each is one load-time rule. A stage that acted outward should not loop back and act again.

**Q5 — A repository workflow may not ask for grants.** A-074 bars the repository from giving grants, but says nothing about asking. A personal grant applies to every repository, including one cloned from someone else, whose workflow could ask for `github` and send the token anywhere. Recommended: refuse. An owner who wants a merge step names the workflow in their job or personal file.
