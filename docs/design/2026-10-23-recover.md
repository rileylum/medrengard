# Recover and resume (tickets 11-f and 11-f2)

## Problem

A controller that dies mid-run leaves a cycle at an agent stage with a run in `cycle.runs` that has no outcome. Since 11-e the run keeps going and writes its output and `exit` into `<runsDir>/runs/<runId>/`, but nothing reads them. Nothing drives the cycle on either: `main.ts` has no command for an open cycle, and `drive` (`src/run.ts`), called on that cycle, would launch a second run at the same stage. A-105 item 1 forbids that relaunch; A-122 says a run that finished while the controller was down is received under its run ID; A-105 item 2 says `resume` refuses a cycle whose job changed; A-105 item 3 says a lock is taken first and a gone developer run's branch tip is pinned.

Facts the design must respect:
- The live controller and a recovering process share one store. The store keeps one outcome per run ID, so a run received twice is recorded once (`receive`, `src/controller.ts`).
- A run is started in the store before it is launched: a developer by its `claim`, a reviewer by `run_started` (11-e). Between that row and the run folder there is a window (sandbox set-up, systemd-run start-up) where a live controller's run has no folder yet.
- `scopePath` computes a scope's cgroup beside the calling process's own cgroup. A recovering process in another cgroup (a timer's service, an SSH session) computes a different path, so recovery must find a scope by unit name (`systemctl --user show sf-<runId>.scope`), not by `scopePath`.
- Under process-group isolation nothing outlives the controller as a unit, and 11-e left liveness unsolved there.
- A developer claim is accepted only through `land` (`src/developer.ts`), which checks the head and fetches it to `sf/<cycleId>`. An adopted claim must pass the same check.

## Interface

```ts
// src/adapter.ts
/** What a started run left, seen by a process that is not its controller (11-f). */
export type Left =
  | { state: 'running' }
  | { state: 'stopped' }          // it was running; look ended it
  | { state: 'finished'; outcome: RunOutcome }
  | { state: 'gone' };            // no exit, and nothing holds the run open

interface Adapter {
  /* … */
  /**
   * Reads a run whose controller is gone; with `stop`, ends a running one first. Absent on an
   * adapter whose runs cannot outlive the controller (the in-process test doubles): recover
   * treats their runs as gone.
   */
  look?(runId: string, runDir: string, stop: boolean): Promise<Left>;
}

// src/recover.ts
export interface RecoverOptions {
  runsDir?: string;
  adopt: boolean;                 // false: "never adopt", A-105 exactly
  stop: boolean;                  // end running runs, then record them failed
  deadlineMs: number;             // for land and the recovery ref
  sandbox?: Sandbox;
}
export interface Recovered {
  cycleId: string;
  did: 'nothing' | 'received' | 'failed' | 'running' | 'locked' | 'refused';
  runId?: string; stage?: Stage; pid?: number; reason?: string;   // refused: the store cannot replay it, or no runtime
}
/** Resolves every started run with no outcome in the work's unsettled cycles. Never launches a run. */
export function recover(store: EventStore, workId: string, adapterFor: (runtime: string, role: Role) => DeveloperAdapter | undefined, job: Job, opts: RecoverOptions): Promise<Recovered[]>;

// src/lock.ts
/** Held while a process drives or recovers a work; returns the release. Throws Locked with the holder's PID. */
export function holdWork(runsDir: string | undefined, workId: string): () => void;

// main.ts
//   recover <job.json> [--stop]         11-f
//   resume <job.json>                   11-f2
```

- **One seam, one entry point.** `look` is the adapter's: only the adapter knows its spec's `parse`, its isolation and its unit name. `cliAdapter.look` reads the folder with `readRun` and parses it with `outcome(spec, r)`, the same two calls the live path makes, so an adopted run and a received one go through the same code. `recover` holds the policy: adopt or not, stop or not, what each state records.
- **Running, finished, gone.** `exit` present: finished. Otherwise running if anything still holds the run: the unit `sf-<runId>.scope` is active with `TasksCurrent` above 0 (cgroup isolation), or a process has the folder's `stdout` open (both isolations; a scan of `/proc/*/fd`; the wrapper holds it until it writes `exit`). Otherwise gone. `exit` is read again after each liveness check, so a run that ends in between is finished, not gone. The probe (11-f log) found every holder, inside bwrap's PID namespace and in its own session, in about 25 ms.
- **What recover records.** Per started run with no outcome, after taking the cycle's lock:
  - finished, `adopt`: `receive` under the run ID, with the same `accept` the live run had (for a developer, `land` with the base and previous head from the run's `input`). The outcome records `runtime` and `moduleHash`; the prompt versions are absent, since the folder's `stdin` holds the prompt itself.
  - finished, not `adopt`: `run_failed`, reason `controller died; adoption is off`.
  - running: nothing, reported as running; with `--stop`, `look` SIGKILLs it (the scope by `systemctl --user kill`, and every process holding `stdout`) and recover records `run_failed`, reason `stopped by recover`.
  - gone: for a commit stage, pin the clone's branch tip under `refs/sf-recovery/<runId>` (A-105 item 3) through the sandboxed `cloneGit`; then `run_failed`, reason `controller died; the run left no exit`. A claim with no folder at all (the parked 05-b store failure) is gone the same way.
  Cycles at a human stage, ESCALATED, settled, or with no unconsumed run are left as they are. A cycle the store cannot replay is reported, not thrown, so one bad cycle hides no other.
- **The lock.** `holdWork` keeps one row per work in `<runsDir>/locks.sqlite`: the holder's PID and its start time from `/proc/<pid>/stat`. A lock whose holder is gone, or whose PID now has another start time, is taken over; the check and the take share SQLite's write lock, which a lock file cannot give a takeover (two processes can each unlink or rename over the same stale file). Apart from the event store, which keeps one table and no leases. Per work, not per cycle: `run` holds it before `develop` opens the cycle, and a work has one cycle a run acts on. `run`, `drive`, `decideAndDrive` (so every owner move that drives) and `recover` take it; recover skips a locked work and says which PID holds it. This is what keeps recover from calling a live controller's not-yet-launched run gone.
- **Leftover units (parked row 21).** `recover` ends by clearing the units of runs under its `runsDir` (`sf-<id>.scope` for each folder in `<runsDir>/runs/`) that have nothing in them: `stop` an active one whose `TasksCurrent` is 0, `reset-failed` a failed one (including scopes systemd stopped at their time limit). An empty unit holds no process, so this cannot touch a live run; naming them leaves another store's failed units to whoever may still read them.
- **Adoption is policy (A-113).** The capability is `look` plus `receive`; the default is `adopt: true` (A-122). The setting is a config key `adopt` in the personal and job layers; the repository layer cannot set it, as it cannot set `runsDir` or `sandbox`.
- **`resume` (11-f2).** `resume <job.json>` takes the lock and drives the work's open cycle from its stage through `drive`. `drive` refuses a cycle with a started run and no outcome (`run <id> started and has no outcome; run recover`), so no path relaunches a started run. A cycle at a human stage or ESCALATED is printed with the owner's next commands, not driven. An agent stage with no started run (the controller died before the start row) launches, as it should: no run was started, so none is relaunched. A command stage reruns (A-105 item 3).
- **A changed job (A-105 item 2, 11-f2).** The open row records `job`, a SHA-256 of the ticket text and the job's `checks` as JSON. `resume` refuses a cycle whose hash differs, naming what changed. A cycle opened before 11-f2 has no hash and resumes, with a printed line saying the job could not be compared.

## Alternatives

1. **Recover also drives the cycle on.** One command does everything after a crash. Rejected: `recover` would spend money, so a systemd timer running it would launch paid runs unattended. Split, `recover` only records and a timer may run it freely; `resume` spends and the owner runs it.
2. **Liveness by a PID the wrapper writes**, with its start time, instead of the `/proc` fd scan. Rejected unless the probe fails: it changes `spawn.ts`'s wrapper (and pulls in parked row 57), and a PID names one process where the open file names every process still holding the run.
3. **No lock; call a run gone only when its start row is older than a start-up window.** Rejected: the window is a guess (sandbox set-up varies), and two `resume`s at once would each launch a reviewer run, which the lock also stops.

## Threat model

- New state read outside a sandbox: the run folder (already read by the live path through `readRun`, capped), unit properties from `systemctl`, `/proc/*/fd` link targets (owner's processes only), and the lock file. A run cannot write the folder (11-e) or the locks folder (not bound).
- An adopted developer claim gets `land`'s checks, as a live one does. An adopted run's output was written with no controller watching the cap; `readRun` caps it on read, so it is an overflow, not a large string.
- A run can hold its own `stdout` open from a `setsid` descendant to look running under process-group isolation. It could already run on there; recover then reports it running and the owner stops it with `--stop`.

## Questions for the owner

1. Recover records and never launches; `resume` drives and spends (recommended), or one command that does both (alternative 1)?
2. A running run: leave it and report it, with `--stop` to end it (recommended), or wait for it?
3. Liveness under process-group isolation: a scan for processes holding the run's `stdout` (recommended, after a probe), a PID the wrapper writes (alternative 2), or call such a run gone, as 11-e's note allowed?
4. The `adopt` key in the personal and job layers, default true (recommended), or the job layer only?
5. A cycle opened before the job hash: resume it with a warning (recommended), or refuse it?
6. Two tickets (recommended): 11-f is `recover`, the lock, `look` and the unit clean-up; 11-f2 is `resume`, the job hash and the store fixes. Or one ticket.
7. Parked rows naming 11-f (recommended):
   - Cover in 11-f: 21 (empty and failed units) and 26 (a store failure after a claim: a gone run).
   - Cover in 11-f2: 48 (`cycles` reports a diverged cycle instead of throwing for the whole work) and 51 (`moveEvent` loads only the cycle the move names).
   - Move: 30 to the next ticket that touches `verify.ts` (11-f does not); 49 (an ACCEPTED cycle closes its work) to row 12, where dispatch decides when work is available; 50 (`retry` after `base_changed`) to the Owner tools row, which produces `base_changed`.
   - Drop: 46 (`decisionConfig` on a store written before 10-b); it fails closed, and naming `base` in the job file is the workaround.

## Not decided here

- `recover` across every work in a `runsDir`, for a timer with no job file: with row 12's `dispatch`, which needs the same runtime registry without a job.
- Relaunching a crashed run once (A-105 item 1 withdrew it until `run_failed` records a cause).
- Command stages outliving the controller: `resume` reruns them.
