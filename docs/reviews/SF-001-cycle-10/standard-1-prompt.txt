01  Executive summary
The current workflow already uses three largely successful coding streams, currently coordinated through Herdr and Superpowers-inspired skills. The bottleneck is operational: issues are assigned in batches and human input is required to advance the orchestrators through their stages. The redesign addresses this with a durable deterministic control plane, not an additional supervisory LLM.
The owner should spend time upstream on problem discovery, UX exploration, prototyping and acceptance of solution designs, and downstream on reviewing demonstrated outcomes and release decisions. Between those points, goal-oriented tickets flow through portable implementation agents, independent quality gates and bounded review. Approved changes can then follow a release policy, while production evidence feeds Continuous Improvement. Not every issue requires every activity; a risk-based profile selects the necessary work.
TARGET OPERATING MODEL  /  Design collaboratively → approve a versioned specification → issue small, verifiable delivery contracts → factory schedules agents → independent verification with strict review budgets → human reviews a focused evidence package → improvement loop prevents repeat defects.
Decided direction
Four conceptual capabilities: Design Studio, deterministic Factory, Review Desk and Continuous Improvement. These do not initially require four separate applications.
Controller owns the issue lifecycle, scheduling, queue, durable state, monitoring, review limits and escalation; LLM agents own reasoning and implementation.
Three concurrent development slots; two or three concurrent reviewer slots, implemented as pools rather than permanent teams.
Maximum two standard review attempts per delivery cycle, and one adversarial review attempt; failures at the limit require human intervention.
Tickets define a goal, observable “Done when” checks, constraints and approved design context.
Vendor/system portability across Pi, Codex, Claude Code and GitHub Copilot, with separate corporate and personal execution contexts.
Human approval for final PR acceptance and for substantive changes to approved intent or the factory’s own governing rules.
Formalise the full software lifecycle without turning it into a waterfall: discovery and validation are proportional to uncertainty; implementation/review remain autonomous; release and production feedback are modelled even when execution is initially manual.
Key technical proposals
Use TypeScript initially for the core and CLI/SDK adapters, SQLite for local durable state, and GitHub Issues/PRs for human-visible work and decisions.
Use isolated Git worktrees, machine-readable artifacts and verified commit-bound evidence; do not require native agent-session resumption.
Use portable SKILL.md skills and version-controlled repository knowledge; start with normal search before adding embeddings or a vector database.
Keep the product’s first review experience in GitHub PRs rather than building a custom web dashboard.
Treat meta-review suggestions as proposed work, not automatic edits to skills, security policy, quality gates or orchestration rules.
Non-goals for initial release
A new agent runtime; centralised credential sharing; automatic production deployments in the first release; unrestricted merges; large cross-repository scheduling; a general-purpose semantic memory service; autonomous policy changes. The release *workflow* and its evidence are in scope even while deployment remains manual.

SDLC tailoring rule
Classify work along ambiguity, UX impact, technical uncertainty, security/data sensitivity, blast radius and reversibility. The controller enforces the selected required artifacts and gates; workers may add more investigation but cannot waive required gates.
Trivial: explicit goal and done-when evidence; usually skip discovery sessions, prototypes and human design approval unless risk dictates otherwise.
Routine: confirm UX/API conventions and acceptance scenarios; use a lightweight design review or prototype only when behaviour is uncertain.
Complex/high-risk: explicit discovery and solution rationale, relevant UX mockups/prototypes or feasibility spikes, human approval, expanded verification, and release-impact assessment.

For substantive work, first identify who is affected, the current workflow, observed pain, assumptions, constraints and what success would look like. Define intended product outcomes or observable success signals before choosing an implementation.
For small or well-understood issues, capture the short rationale and proceed directly to a ready ticket.

Definition of Ready is risk-aware, not template-completion theatre
A browser-facing change with approved UX must link designs, flows and meaningful states; a backend-only fix is not forced to produce screenshots.

Scheduling and resource pools
Begin with three development slots, two or three standard-review slots, and at most one concurrent adversarial run. This represents maximum concurrency, not six permanently running sessions. Respect task dependencies and an adjustable cap on PRs waiting for human review. Avoid assigning two writers to the same worktree or concurrently changing the same branch.
Failure and recovery
Infrastructure retry: idempotent retries with backoff; never count a failed launch as a completed quality-review attempt.
Worker timeout/crash: checkpoint artifacts, terminate or recover lease, create a fresh run with durable context, and limit restart churn.
Invalid completion: never advance solely because process state becomes idle/done; inspect machine-readable result and external evidence.
Changed head/base: invalidate stale review and acceptance evidence; reverify exact commit SHA before presenting a PR.
Repeated attempts or blocked decisions: package context, recommended options and evidence; escalate rather than burning tokens indefinitely.

HARD QUALITY LIMITS  /  Exactly one initial standard-review attempt plus at most one post-fix standard-review attempt in a delivery cycle. At most one adversarial-review attempt. Review verdicts must reference a specific commit SHA. An adverse result at the budget limit stops and escalates.
Clarifications to decide
After a human requests changes to a PR, does that explicitly authorise a new delivery cycle with fresh review counts? Proposed: yes, only when recorded as a new revision cycle.
Does adversarial review always run on trivially scoped tasks? Proposed: yes initially, then allow policy-driven exemptions with evidence and explicit approval.
If an issue fails adversarial review with a small correctable defect, may the owner approve one targeted fix and a fresh adversarial attempt? Proposed: only via an explicit override with an audit trail.
Quality gates beyond agent review
A reviewer pass cannot substitute for required executable verification. Test/build results, acceptance evidence, design conformance and risk-specific checks must be associated with the exact commit being reviewed. Release remains a separate post-acceptance lifecycle with its own approval and verification evidence.
08  Worker contracts, evidence and independence
Development worker
Receives approved issue/version, workspace, constraints, repository knowledge map, allowed tools, verification requirements and a fixed artifact path. May invoke plan/prototype/implement/test skills. Must commit changes and output a structured result with honest blockers, test results and any requirement deviations.
Normal reviewer
Receives requirements, reviewed commit SHA, diff, relevant architectural instructions and independent CI evidence. Should not inherit the developer’s reasoning transcript by default. Reviews correctness, maintainability, regressions, acceptance coverage and project constraints. Returns findings linked to files/lines and a PASS or FAIL verdict.
Adversarial reviewer
Runs once against an accepted standard-review candidate. Explicitly attempts to falsify the acceptance conditions, examine negative cases, challenge surprising assumptions, look for security/data edge cases and execute relevant tests. Does not merely paraphrase the ordinary review. Reports a single verdict with reproducible evidence.

Repository quality profile: discoverable startup, build/test commands, CI identity, minimum required checks and known exclusions.

Design conformance vs user acceptance
Design conformance asks whether the implementation matches the approved UX and behaviour; acceptance asks whether the result solves the agreed problem in the actual environment. Both may require human judgment. Review packages should support a short hands-on walk-through and distinguish real-user feedback from simulated agent feedback.
Security and accessibility boundaries
Use repository-level secure-development defaults and targeted threat modelling for sensitive components. Human review remains mandatory for high-impact authentication, permission, personal-data and migration changes. Accessibility requirements should be part of design and acceptance, not discovered only in final code review.

Meta-reviewer: recurring defect analysis
Run on a scheduled cadence or after a sufficient sample (proposed: weekly or approximately 10 completed issues); serious incidents may trigger immediate analysis.
Cluster confirmed findings by defect class, code area, task type and common root cause; separate reviewer false positives from actual defects.
Investigate whether the issue stems from product ambiguity, architecture, testing gaps, tooling friction, skill wording, or reviewer standards.
Propose improvements supported by links to source PRs, observed frequency, expected prevention mechanism and a measurable done-when condition.
Generate an ordinary proposed improvement ticket; the normal factory and human approval policies apply.
Repository Health agent: prevent failures before reviews
On repo onboarding and periodically thereafter, evaluate whether the repository is agent-ready: reproducible startup, dependency setup, test reliability, architecture docs, fixture availability, type/lint guardrails, browser/API testability, security boundaries and agent instruction clarity. Return evidence-backed risks and a prioritised improvement backlog, not arbitrary scores.

SELF-MODIFICATION BOUNDARY  /  The meta-reviewer can propose changes but cannot silently relax gates, change its own scoring criteria, rewrite skills, suppress findings or bypass approval. A reported “improvement” is not accepted until verified and approved through the appropriate governance path.
Evaluation and indicators
Measure recurring confirmed findings per accepted issue (normalised for issue volume and severity), review attempts per accepted PR, human interruptions, time spent waiting, post-merge escapes, rate of rejected meta-review proposals and harness benchmark performance. Compare similar task types and repository areas rather than attributing every trend to the model.
Production and product-outcome feedback
The improvement loop must ingest more than review defects: production incidents, operational telemetry, support reports, usability findings, adoption/engagement and outcome metrics. Distinguish code defects from valid implementations of misguided requirements or poor UX; the latter may require new Design Studio work, not another coding prompt.
Define an owner, source and collection method for post-release success signals; do not fabricate product analytics that are not available.
Track confirmed post-merge escapes and deployment problems against the responsible release and quality profile.
When outcomes fail despite correct implementation, create a discovery/design improvement rather than assuming code rework.
For serious incidents, generate a reviewable incident/postmortem record, prevention proposal and focused regression test where appropriate.
12  Safety, governance and operational controls
Approval boundaries
Apply least-privilege credentials and per-repository action policies; issue text and tool output are untrusted inputs.
Approval required for changes to security controls, auth, production data, sensitive migrations, permissions, deployment policy, or high-impact architecture.
Separate personal and corporate source, artifact, credential, log and telemetry domains; obtain explicit corporate approval for all runtimes and unattended operation.
Maintain append-only state-transition history with actor, evidence, head SHA, policy version and any human override.
Support pause, cancel, quarantine and global shutdown; never leave orphaned workers with uncontrolled write access.
Prevent prompt injection from modifying policy or invoking unauthorised operations; validate outputs and enforce permissions outside the agent.
Backpressure, observability and cost
The controller should enforce rate/concurrency caps, maximum outstanding human-review PRs, timeout ceilings and a bounded per-task expenditure policy where telemetry is available. Publish a readable “needs my decision” inbox and an optional operational dashboard, but avoid notification spam on successful stage transitions.

Post-merge release handling is a separate permissioned state machine: merge approval creates a release candidate; its staging, deployment and post-deployment evidence is tracked by environment and artifact version. It must never be inferred from an agent completion message.
Appendix B  Controller and harness acceptance tests
A READY issue reaches a PR and complete acceptance package with no manual stage transition.
An issue rejected by the first standard review is fixed and reviewed exactly once more; a second rejection escalates.
An adversarial rejection escalates immediately without a second adversarial attempt.
An invalid agent result, zero exit without artifacts, or an idle session cannot advance state.
Crashes, duplicate webhook delivery and stale leases cannot duplicate assignments, commits or review counters.
Review evidence references the actual reviewed SHA; new commits invalidate stale evidence.
An agent cannot modify accepted scope or remove risk gates through prompt instructions or issue content.
Runtime adapters pass the same fake-vendor contract suite and preserve cancellation/error semantics.
A corporate environment cannot dispatch a task to a forbidden personal runtime or log sink.
A structured review finding survives restarts and is classifiable as confirmed, rejected or uncertain.
A meta-reviewer may create an improvement proposal but cannot mutate critical harness files or relax workflow policy.
A revised skill is benchmarked against known failures and must pass a human authorisation gate.
A user-facing issue requiring UX approval cannot become READY without a referenced approved mockup/prototype or documented exception.
A trivial non-UI issue can become READY without irrelevant wireframes or discovery meetings.
A visual regression or design non-conformance blocks the configured UX gate even if standard code review passes.
Evidence for unit, integration, E2E, security, a11y or performance checks is required exactly when the selected quality profile demands it.
Missing tests or unsupported agent assertions never satisfy a mandatory independent quality check.
A human can walk through the delivered feature using a working preview or reproducible steps before accepting it.
Post-merge release states cannot trigger unauthorised production deployment; release failures record verified evidence and escalate.
Successful deployment does not imply product success; outcome observation can produce discovery or continuous-improvement tickets.

13: ## One delivery cycle
14: 
15: 1. **Intake and tailoring.** Record problem, intended outcome, evidence versus assumptions, risk dimensions and route (Fast/Routine/Design). Note why mockups, prototypes or spikes are required or unnecessary.
16: 2. **Design where needed.** Draft a versioned spec with alternatives and unresolved questions. Obtain explicit owner approval of the exact version before declaring dependent implementation READY. Drafting is allowed without approval; implementing unapproved material design is not.
17: 3. **Prepare the contract.** Use `docs/templates.md`. Map every Done when criterion to a credible independent check. Record dependencies, quality/release obligations and blockers. Classify readiness as READY, NEEDS_REFINEMENT or NEEDS_DESIGN_APPROVAL.
18: 4. **Claim and implement.** Record actor, cycle, branch/worktree, base SHA, approved spec and policy version. One writer per branch. Implement only the contract, run self-checks, commit, and provide results with honest blockers. Material scope/architecture changes return to design.
19: 5. **Verify independently.** Check the actual commit, required artifacts and executable results. A successful exit, session idle state or developer assertion is insufficient. Until CI exists, record who independently reran checks and in which environment; do not describe that as CI.
20: 6. **Standard review.** Use a fresh context with the contract, diff, SHA, repository instructions and independent evidence—not the implementation transcript. Record one completed PASS/FAIL verdict and findings. First FAIL permits a bounded fix and second standard review; second FAIL stops and escalates. A PASS proceeds to adversarial review.
21: 7. **Adversarial review.** Proposed initial policy: every change gets one independent adversarial attempt after standard PASS. Challenge acceptance, negative cases, security/data edges and assumptions. FAIL stops immediately; no automatic fix/re-review loop.
22: 8. **Human acceptance.** Assemble the evidence package and walkthrough. Owner approves, requests changes or rejects/rethinks. No approval is inferred. A revision must name its scope and any explicitly authorised new cycle/budget; until reset semantics are agreed, stop for a decision.
23: 9. **Release and learn.** Separately record merge/release disposition, environment and candidate, applicable smoke/recovery evidence, authority and outcome observation. Documentation-only work can state no deployable artifact and explain why deployment checks are N/A. Record friction and confirmed defects as proposed preventive work, not automatic policy edits.

35: ### Structured Design Studio → controller handoff
36: 
37: The Design Studio prepares immutable specification and contract artifacts, not execution authority. The first owner interface is a local CLI over a deterministic command boundary; future UI/GitHub integrations must use the same validation semantics. Chat, an LLM interpretation, a Git commit or a READY label alone grants no authority.
38: 
39: Commands include `approve-policy`, `approve-design`, `authorise-work` (individual/batch), `revoke`, `pause`, `resume`, `request-revision`, `accept-delivery`, and separate `authorise-merge`. Each binds command/dedupe ID, authenticated owner identity, exact action, work/cycle/expected version where applicable, artifact digests/versions, policy digest, scope and relevant expiry. Preview the exact objects and effective limits before confirmation. The controller validates actor capability, current authority, versions and all transition guards, then atomically persists the decision/event and effect. Same ID/same payload returns the original result; same ID/different payload is rejected; different IDs cannot bypass work-tip uniqueness. Transport replay never creates a second cycle. An acceptance command binds the candidate AND acceptance-package digest; missing/stale gates reject it. Merge remains a separate guarded action, never implicit in acceptance.
40: 
41: Owner authentication/transport and process privilege separation are implementation obligations BEFORE enabling owner commands or worker execution. Worker launch environments must not possess the owner credential, privileged socket access or policy-store write capability. A shared Unix identity with unrestricted access is not adequate separation. A worker's repository policy-file edit is only a proposal, never a runtime policy activation. If that isolation cannot be established, block execution; do not rely on a prompt instruction. Secrets are referenced through protected storage, not embedded in policy files. CLI syntax and foreground/daemon transport remain separately designed; no CLI exists yet.
42: 
43: Design approval and work authorisation are separate decisions: approving a design does not authorise every derived contract. An authorised contract can wait on dependencies/design approval. The controller alone derives READY and rechecks readiness at dispatch.
44: 
45: Work readiness is distinct from cycle stage: `NEEDS_REFINEMENT`, `NEEDS_DESIGN_APPROVAL`, `READY`. Becoming work-READY requires valid fields, resolved dependencies, required design approval or allowed N/A, eligible repository/environment and a defined quality profile. Dispatch rechecks these conditions, rather than trusting an old label.
46: 
47: A cycle is created under recorded owner authority (individual initial-work authorisation, a bounded initial-work batch under proposed Q5, or an individual Q1 revision), before readiness promotion, in `PREPARING`, control `ACTIVE`, counters `(0,0)`. It pins immutable contract/spec/policy/profile versions, authority references and review limits, even when a referenced design still awaits approval. The controller promotes it to `QUEUED` only once work readiness is READY. Changes to those pinned versions require a new authorised cycle; never edit them in place. READY in the source roadmap denotes work readiness, not a second cycle stage.
48: 
49: **One lineage per work ID:** the work record has exactly one current cycle tip and at most one nonterminal cycle. Initial creation is allowed only when no cycle has ever existed for that work. ACCEPTED with PENDING or INVALIDATED handoff still occupies the work's live-delivery slot. Supersession transfers that slot atomically to one child, recording a unique parent→child link and updating the work tip. Every child creation must compare-and-swap the expected current tip and require no existing child. A replay of the same decision returns the existing child; a different decision against a parent that already has a child is rejected, even if its event ID is new. A second initial authorisation is rejected regardless of the current stage. Cancelled work can only be reopened by an explicit child-cycle authorisation from its current tip after containment; completed/merged work's new product scope uses a new work ID. No branch/contract-version change creates an exception to this invariant. In the initial single-delivery mode, PREPARING through acceptance/handoff resolution occupy the slot; M5 must revisit strict base-drift policy before enabling concurrent delivery.

51: ## 3. Delivery states and transition rules
52: 
53: Delivery states: `PREPARING`, `QUEUED`, `DEVELOPING`, `VERIFYING`, `STANDARD_REVIEW`, `ADVERSARIAL_REVIEW`, `AWAITING_ACCEPTANCE`, `ACCEPTED`, `ESCALATED`, `CANCELLED`, `SUPERSEDED`.
54: 
55: Orthogonal execution control: `ACTIVE`, `PAUSED`, `RECOVERING`, `QUARANTINED`. Only ACTIVE permits ordinary dispatch/advancement. Recovery may record observations and stop workers, but cannot advance quality gates. Store the interrupted stage and reason; do not use PAUSED as a new cycle or budget reset.
56: 
57: All transitions require matching cycle/state version, allowed actor, applicable control state, current approval/policy eligibility and a unique event. The following adds stage-specific guards. Invalid input never triggers the indicated successful transition. Escalation defaults to control PAUSED once containment is proven; uncertain containment requires QUARANTINED. For safe VERIFYING blockers, containment means verified read-only candidate access and isolated check scratch space, not necessarily process termination; the sibling-execution rule below applies. Safety/context invalidation and cancellation still require stopping workers. Controller failure/staleness handling may interrupt any nonterminal control state; ordinary quality advancement requires ACTIVE.

Cancel/child finalisation reconciles available late results before closing reservations. Ordinary non-escalated owner pause still retains the SAME admitted intent and spent slot for revalidated resume. Neither trigger is reinterpreted as the other.

Legitimately renewing the waiver does not rewrite that PASS or grant automatic routing. Terminal cancellation/supersession never releases held results. Quarantine exit only returns PAUSED with delivery still ESCALATED; pending cancel or containment intent cannot be bypassed by a held PASS.

114: 
115: Each escalation records durable blocker IDs with kind, affected check(s)/candidate, evidence, required resolution and OPEN/RESOLVED status. Ordinary pending/running checks are not escalation blockers until an actual failure, missing completion artifact or dispatch/configuration problem is observed.

A command targeting multiple blockers commits all targeted resolutions atomically only if each target's own guard passes; otherwise reject that command without partial mutation. Separate valid commands may always resolve items incrementally.

If any OPEN blocker remains, stay ESCALATED/PAUSED and dispatch nothing. Only if none remain, pinned context/containment are valid and no terminal quality verdict is bypassed, restore `resume_stage`/PAUSED. Initial check allowances remain per-check: after resume each eligible, never-launched check may launch its initial execution once. Neither resolving a blocker nor restoring VERIFYING means its check has passed. Gate advancement still waits for every required check's valid evidence. CAS conflicts reload/revalidate the entire set, so a concurrent new failure cannot be lost behind a resolution.

121: ### Running sibling checks during VERIFYING escalation
122: 
123: For a safe verification-only blocker (missing configuration for a never-launched check, a failed pre-review check, or missing evidence with no provenance/safety anomaly), already-registered sibling checks continue under ESCALATED/PAUSED observation if their own authority/environment remain eligible, their execution deadlines remain finite/unchanged, and enforced confinement prevents writes to the candidate or other checks' scratch areas. Record the identity/confinement proof and decision to keep observing each such run. No new or replacement execution launches while ESCALATED, even if another check's configuration is fixed. Unknown confinement, unsafe behaviour, candidate drift, authority revocation or owner cancel overrides this exception: request bounded termination and quarantine if containment cannot be proved.

Missing attachment of an independently authenticated, valid completed result is instead the evidence-retrieval case defined below. Neither result advances the delivery stage or clears unrelated blockers. An in-flight check remains running rather than becoming “missing evidence” merely because another check escalated. An observed sibling timeout/crash follows the uniform paused-execution-failure rule below, whether delivery is still ESCALATED or has been restored to VERIFYING/PAUSED. No post-restoration exception or deferred Q3 retry exists.

127: ### Uniform paused-execution-failure rule — direction accepted in A-004
128: 
129: An **execution failure** here means an infrastructure failure of an assigned execution: failed launch, crash, timeout, transport failure requiring replacement, or malformed/unattributable/conflicting completion. No completion by the execution deadline is a timeout, not proof of success. This is distinct from both a valid quality FAIL and a valid completed execution whose retained artifact has not yet been retrieved/attached.
130: 
131: The **evidence-retrieval** case requires an independently authenticated completion receipt proving the same registered run, candidate/context, valid result and retained artifact identity/digest/location; a worker's unsupported claim or a malformed result is insufficient. The artifact's absence from the package adds an OPEN evidence-retrieval blocker, not paused-execution-failure. Retrieving and validating that exact retained output may resolve it under §5/SC-53 even while PAUSED or ESCALATED; no new execution is allowed and it is not reclassified merely by entering PAUSED. If the receipt is invalid, output conflicts, or execution success cannot be established by the deadline, apply execution-failure/provenance handling instead; retrieval cannot repair malformed completion. A genuine quality FAIL in the retrieved output retains its sticky-failure/review semantics, never PASS by attachment.
132: 
133: Valid reviewer FAIL and valid test assertion failure keep their existing review-budget, sticky-failure and profile-waiver semantics; no execution restart is inferred from them.
134: 
135: If an execution failure is observed while control is PAUSED, while RECOVERING from PAUSED, OR while delivery is ESCALATED under ANY control state (including ACTIVE-origin RECOVERING), the controller immediately records an OPEN `paused-execution-failure` blocker with run identity, failure evidence and containment status. Delivery becomes/remains ESCALATED. Confirmed termination yields control PAUSED; unknown containment triggers bounded stop/reconciliation and QUARANTINED if proof is unavailable. Attach termination proof when obtained; it is not a prerequisite for recording the blocker. This blocker requires an individually authorised Q1 child cycle or cancellation. It cannot be waived, cleared by supplying configuration, or transformed into a pending same-cycle replacement. Used initial allowances and the cycle-wide Q3 count remain unchanged regardless of remaining configured replacement capacity.
136: 
137: This applies to owner-paused work and verification restored to PAUSED alike. A healthy observed run may continue or complete under the existing safe-observation rule. Losing observation alone is not proof of a healthy run or a licence to relaunch; reconcile identity and containment first. If reconciliation establishes failure, apply this rule. ESCALATED delivery has the same explicit blocker and containment outcome under every control state; it cannot remain stuck in ACTIVE-origin RECOVERING awaiting an ineligible retry. The blocker name records the conservative no-resume policy, not a requirement that control was literally PAUSED. The escalation gate is not a source of execution authority.

139: **Escalated recovery settles to PAUSED — direction accepted in A-007:** recovery never returns ACTIVE while delivery remains ESCALATED, regardless of interruption origin or escalation timing. PAUSED prevents dispatch/advancement, not permitted observation. Once required reconciliation and containment are complete, retain safe sibling observations and settle ESCALATED/PAUSED; unresolved stops continue bounded containment, uncertain containment uses quarantine, and pending cancellation follows its existing finalisation rules. This removes the former ACTIVE-preserving exception and any presumed escalation-before-default-pause window. Interruption origin remains audit evidence, not permission to restore ACTIVE. Explicit owner resume is still a separate existing transition; it does not make ESCALATED delivery dispatchable.

In the same state-version transaction, record the escalation/blockers, each eligible run's identity/confinement evidence and keep-observing decision, and the applicable recovery control outcome below. A previously absent keep-observing record is not by itself a stop trigger until this eligibility evaluation has run. If current identity/context/confinement or healthy-run evidence cannot be established, do not defer the decision awaiting potentially better evidence: apply existing bounded stop/quarantine rules. A pending stop/containment/cancel intent is never withdrawn by fresh healthy evidence. If escalation was already recorded, its decisions and stop intents remain binding; reconciliation revalidates continuation against current evidence, never grants it over a required stop. An owner pause uses its own transition to PAUSED with safe observations retained; a concurrent recovery transaction must reload/revalidate after a state-version conflict.

143: **Empty escalated recovery:** after reconciling known outcomes, RECOVERING with ESCALATED delivery (ACTIVE or PAUSED origin) and no live runs, unresolved launch intents, pending stops/containment/cancellation, or unprocessed results settles to PAUSED under the explicit empty-set row below. This includes a genuinely empty execution history and a fully reconciled completed history. This row takes precedence over the healthy-completion exit when its guards hold; an empty set never vacuously authorises ACTIVE. Failure observations and their required blockers are processed first; missing proof of absence/containment is not an empty set. Blockers and completed evidence remain intact, with no dispatch or quality advancement.

173: ### Reservation lifecycle
174: 
175: A review attempt reservation is `RESERVED`, then either `CONSUMED` by one valid completed verdict (including stale PASS/FAIL), or `CLOSED_UNUSED` when the cycle is cancelled/superseded and the run is proven unable to produce a further verdict. RESERVED survives pause, recovery, escalation and a Q3 replacement run. No release back to the same cycle's available budget is permitted. CLOSED_UNUSED is retained history, not a reusable ordinal. Duplicate results are no-ops; conflicting results escalate the nonterminal cycle and preserve the first accepted result (terminal cycles retain an anomaly and block any merge handoff).
176: 
177: Completed plus outstanding review reservations cannot exceed the limit. Only one review attempt is active per cycle at a time. A safely replaced run is fenced/closed before accepting the replacement's verdict; delayed output from that replaced run is diagnostic only. Completed verdict/counter/transition are one transaction. A valid assigned verdict arriving after escalation due to staleness still consumes its reservation but cannot resume the cycle. Cancellation/supersession finalisation waits for reconciliation of completed verdicts; later output from closed runs is retained diagnostically, never used to reopen budgets.

179: ## 4. Review-budget and revision policy proposals
180: 
181: ### Q1 — New cycles require explicit authorisation (O-002)
182: 
183: A new immutable cycle requires an explicit owner command naming the parent, findings/scope, exact contract/spec/policy/profile versions and limits. Required after terminal failure, acceptance-stage requested revision or pinned-policy/context changes. A bare “fix this” message is not authority. Child creation retains the lineage/containment guards and old counters; all required gates repeat.
184: 
185: Before terminal failure, either standard or adversarial FAIL may use Q6's configured same-cycle correction path. After terminal escalation, unused capacity is not permission to reopen that path. No review-counter resets or old-PASS reuse. Initial implementation supports an owner-requested budget change through a newly authorised child with a different pinned policy, not in-place mutation of a live cycle.
186: 
187: ### Q2 — Freeze review candidates; escalate unexpected changes (O-003)
188: 
189: Code changes are permitted only in initial DEVELOPING or a controller-admitted Q6 correction episode. A correction creates a distinct candidate and invalidates all prior candidate-specific verification and review PASSes for advancement; repeat verification, standard and adversarial review. This includes authorised correction after adversarial FAIL. Unexpected head changes during review/acceptance still escalate; scope/base/pinned-context changes require a child cycle, never an automatic rebase or budget reset.
190: 
191: The target-branch tip B1 is captured at the first development claim, not at work intake. A moving target branch is detected before each dispatch, result/verdict acceptance, package presentation, human acceptance and merge handoff. After capture, any target-tip drift in DEVELOPING (including the fix), VERIFYING, either review or AWAITING_ACCEPTANCE escalates, preserving counters. No automatic rebase is permitted, including during the post-FAIL fix. The authorised developer may change the work-branch head only in its assigned DEVELOPING stage; external/unattributed head changes always escalate. PREPARING/QUEUED have no captured candidate, so target movement there only changes the tip captured at claim. After ACCEPTED, drift invalidates the separate merge handoff (§7).
192: 
193: Never silently replace the stored base. Old evidence stays in history marked stale. New commits are not assumed harmless, even if labelled docs-only. A stale valid FAIL increments its role counter but escalates; it does NOT grant a Q6 correction. Staleness handling takes precedence over normal PASS/FAIL stage routing.
194: 
195: A well-formed verdict for its assigned candidate consumes its reserved attempt even if that candidate became stale while the reviewer ran. Record it as historical evidence, but it cannot advance the new candidate. Malformed or misattributed results do not consume a completed quality verdict. Cancelled/no-verdict runs retain their reservation until safely resolved; cancellation is not a budget-recycling mechanism.
196: 
197: Rejected alternative: automatically review an externally changed latest head while capacity remains. Only explicit Q6 correction intents authorise same-cycle new candidates; counters and pinned B1 never reset.
198: 
199: ### Q3 — Bounded operational retries; no hidden quality-fix loop (O-004)
200: 
201: Use the pinned policy's `max_replacement_executions` (Rmax) and `replacement_backoff_seconds`, shared across all worker, verifier, diagnostic and reviewer executions in the cycle. Each eligible replacement consumes one allowance atomically BEFORE launch; exhausted allowance escalates. No reset between stages/candidates/restarts. A no-op observation/reattachment is not a replacement. The old values one and five seconds are illustrative configuration values, not hard-coded product ceilings. Manual bootstrap still stops for owner guidance after any infrastructure failure.
202: 
203: Eligible only for ACTIVE-origin recovery with no intervening pause/escalation AND no pending Q6 correction intent. Q6's old-candidate failure precedence below overrides Q3 eligibility even when R remains. Otherwise eligible failure kinds are: proven failed launch, transient verifier transport failure, or timeout/crash after termination is confirmed. Under accepted direction A-004, an execution failure during PAUSED/paused-origin recovery (including after stage restoration) requires child cycle/cancellation, even with unused Q3 budget; see the uniform rule in §3. Invalid/missing result artifacts, identity mismatch, unsafe activity or uncertain termination escalate immediately. Actual assertion failures are quality evidence, not transport errors: classify under §5 and, if eligible, use Q6's shared worker-correction allowance, not Q3. Malformed output or a launch/crash/timeout never becomes a known baseline test failure.
204: 
205: Each execution needs finite configured execution, heartbeat/lease and cancellation deadlines before eligibility. Exact durations are environment configuration to be validated by runtime spikes; missing values block unattended dispatch. No indefinite waits or polling. An execution deadline is not renewed by heartbeat.
206: 
207: Rejected alternatives: retry forever; reuse review counts as retry limits; or reset retries per run/stage. The proposed cycle-wide allowance is easy to audit, though it may cause extra human intervention. Tune only through approved policy versions and measured evidence.
208: 
209: ### Configured policy authority — direction accepted in A-008
210: 
211: The authoritative product policy is an owner-approved immutable configuration artifact, identified by version AND content digest in protected controller storage. The specification defines how it is interpreted. Numerical limits are not compiled constants or permanent 2+1 ceilings. Approval must bind the exact bytes; changing a repository file neither activates it nor changes an existing cycle. New versions govern only newly authorised cycles unless an explicit child decision adopts them. Revocation follows §5; publication alone leaves existing pinned authority intact.
212: 
213: Before creation/readiness, validate the entire policy: Smax/Amax are finite integers >=1 (both independent gates remain required); Cmax, Rmax and Dmax are finite integers >=0; deadlines and replacement backoff are finite positive values. Reject missing/unknown fields, negative/fractional/infinite values, contradictory profiles and unapproved digests. No silent fallback or unlimited sentinel. Concrete default values and environment-specific QA profiles remain separate approved configuration, not inferred from examples.
214: 
215: - Smax / `max_standard_reviews`: total standard ordinals across ALL candidates in a cycle.
216: - Amax / `max_adversarial_reviews`: total adversarial ordinals across ALL candidates.
217: - Cmax / `max_worker_corrections`: shared total correction episodes initiated by verification or either review role; initial development is not a correction.
218: - Rmax / `max_replacement_executions`: infrastructure replacements only, governed by Q3's eligibility rules.
219: - Dmax / `max_diagnostic_executions`: total registered baseline-comparison/diagnostic executions across the cycle; never grants quality rerun PASS or worker correction authority.
220: - Profile: required check identities, phases, known-baseline eligibility/comparison protocol, non-waivable gates and permitted outcome-specific waivers; execution/lease/cancellation deadlines, runtime/model/environment eligibility and capacity limits are configuration inputs too. Increasing concurrency does not bypass the initial single-delivery/single-writer eligibility rule.
221: 
222: Configuration cannot disable owner authentication, immutable evidence/counters, same-candidate independent passes, containment, or explicit final acceptance. A worker cannot configure itself out of these invariants. Every cycle stores effective values alongside the digest; every gate verifies the pin/authority and remaining capacity.
223: 
224: ### Q6 — Shared bounded correction admission
225: 
226: Let S/A be completed verdict counts, SR/AR outstanding reservations, C the count of correction intents already committed. After counting the current FAIL, a new correction requires **S + SR < Smax, A + AR < Amax, C < Cmax**. Both future reviews are necessary even after adversarial failure. A PASS on the last available ordinal is valid; reaching a cap alone is not failure. Correction may be unnecessary (Cmax=0) on a fully passing initial candidate. Review capacity sufficient for one best-case remaining path does not promise success; further failures re-evaluate the same guards.
227: 
228: Admission also requires ACTIVE control, current candidate/context/authority, in-scope reproducible defect, and no unresolved safety, infrastructure or other escalation blocker. It is allowed only from VERIFYING or the failing review stage, never as an operational escape from ESCALATED. If a guard fails, escalate and retain all results; no worker is dispatched merely because one budget has capacity.
229: 
230: Commit a unique candidate-bound correction intent and increment C once in the same CAS transaction as failure handling. Verification may need classification first (§5); no correction is committed for a known-baseline exception. Multiple classified defects for that candidate join the same pending episode, not multiple increments; check for that existing intent before applying the new-episode C guard. Freeze further ordinary check/review dispatch. Already-launched checks/diagnostics finish under their original finite deadlines; reconcile all outcomes and prove all old executions/write access contained before entering DEVELOPING or launching a writer. Needed bounded classification of already-observed failures may still run from Dmax while ACTIVE. Never terminate a check merely to claim its missing evidence passed; existing stop/failure rules take precedence. **Old-candidate precedence:** once the correction intent exists, Q3 is ineligible for EVERY execution associated with that candidate, including sibling checks and classification diagnostics; freeze includes replacement dispatch. A crash/timeout/transport failure, even proven contained, escalates with C retained and R unchanged, not an old-candidate replacement or silently discarded failure. Unsafe/uncertain containment still uses quarantine. Additional valid assertion failures must be classified before writer dispatch; if classification is necessary but inconclusive, unsafe or cannot fit its remaining D protocol, escalate rather than assuming the discarded candidate makes that evidence irrelevant. This conservative rule intentionally may forfeit an admitted correction; no missing/uncertain evidence is hidden by moving to a new candidate. New safety/infrastructure/context blockers likewise abandon automatic correction and escalate with C retained, not refunded. If the writer is not yet dispatched, §3 atomically marks the intent ABANDONED_ESCALATION and records every unresolved source failure as an explicit blocker; no later blocker resolution/resume reactivates it. An ordinary non-escalated PAUSE instead retains the intent without dispatch; explicit resume revalidates all guards except the already-consumed C slot. No new episode is created by replay or restart.
231: 
232: Once the pending episode is fully reconciled, controller transitions to DEVELOPING/ACTIVE for one findings-scoped worker execution with durable intent and normal single-writer guards. The new result must be a distinct committed candidate addressing the recorded defects; no-op or scope-changing results escalate. Test changes must preserve approved acceptance meaning/coverage; deleting/weakening tests to hide failure is a material deviation. At VERIFYING, the new candidate gets its own initial check executions; previous failures remain associated with the old candidate/episode and do not falsely block the new one. S, A, C, R and D remain cycle totals. Changed candidate requires fresh standard AND adversarial PASS, with no old PASS substitution. A failure still present on the new candidate requires another admitted episode; it is never cleared by a same-candidate rerun.
233: 
234: ### Q4 — Owner authority and non-waivable invariants (O-008)
235: 
236: Recommend the owner as sole initial approver for design, revisions, profile exceptions and policy changes. A quality-check waiver names the exact check, candidate, evidence IDs, reason, residual risk and expiry/scope. The pinned profile must explicitly allow waiving the actual outcome (BLOCKED/unavailable or FAILED); a generic or absent waiver permission does not allow FAILED. A valid FAILED-outcome waiver may resolve that pre-review blocker in the SAME cycle, by the explicit §3 transition, without erasing the failure or rerunning the check. It cannot bypass other outstanding blockers. Waiver is HUMAN-WAIVED, never PASS.
237: 
238: No waiver of provenance/identity, required design authority, runtime/environment permissions, single-writer safety, hard review limits, independent review verdicts or explicit final acceptance. Policy changes are separate approved work, not an issue instruction or an override field. Deployment authority remains separately configured and disabled initially.
239: 
240: Alternative: delegate classes of decisions to named operators later; that requires explicit capability/authority configuration and audit tests.
241: 
242: ### Q5 — Initial work authority without routine stage-kicking (O-008)
243: 
244: Recommend allowing an owner to authorise either one initial work/version or a finite batch naming exact work IDs, versions, scope, review limits and an optional creation deadline (mandatory for batches). The deadline bounds NEW cycle creation only: at or after expiry, no unused entry may create a cycle. A cycle created before expiry receives a recorded derived authority lasting until that cycle terminates or authority is explicitly revoked; expiry of the originating individual/batch grant does not stop PREPARING promotion, running work or valid verdict routing. Record creation time, grant ID and derived authority atomically. Revoking the original grant also revokes its derived authorities and follows §5 invalidation. Individual grants without a creation deadline remain usable until consumed or revoked. Gate revalidation checks the derived cycle authority, not the elapsed creation deadline. The controller advances eligible READY work automatically without another owner action. Required design approval still applies independently. Batch entries are single-use under the work-lineage invariant; they cannot authorise children or reset budgets. All refinements of pinned versions and revisions require an individual Q1-style child decision, including PREPARING refinement. A future standing risk-based intake policy is not authorised here.
245: 
246: Alternatives: require a separate owner action for every initial cycle (simpler, but adds manual intake friction); or accept open-ended policy-level initial authority (more autonomous, but requires an additional eligibility/security design). The bounded batch is a proposed middle ground, not accepted by approval of this revision task.

248: ## 5. Evidence and acceptance boundary
249: 
250: ### Context validity
251: 
252: Cycles pin contract/spec/policy/profile versions; they do not follow the newest version automatically. Publishing a new version alone leaves explicitly still-authorised pinned versions eligible. An owner adoption/replacement decision for this work, revocation of a pinned approval/version, or withdrawal of runtime/environment eligibility invalidates the active cycle's context: mark affected evidence stale and ESCALATE (or invalidate the merge handoff if ACCEPTED), preserve counters, contain active workers. Required checks cannot be changed in place. Any resulting scope/version change requires a child cycle. Authorisation validity is rechecked at every gate; this is what “current eligibility” means, not latest-version substitution.
253: 
254: Waiver expiry/revocation before acceptance similarly escalates, without relabelling it PASS. The owner may resolve that operational blocker only by independently verified existing check evidence or a newly valid profile-permitted waiver on the SAME candidate/context; otherwise create a new cycle. Expiry after acceptance blocks merge until revalidated under §7. A stale valid in-flight verdict consumes its reservation but cannot advance.
255: 
256: ### Failed evidence, waivers and external execution
257: 
258: For one cycle/candidate/check definition/environment, any valid FAILED result remains authoritative against subsequent PASS results; retain every result, but do not use “latest wins” or rename a run to evade failure. A valid profile-permitted FAILED waiver changes the effective gate to HUMAN-WAIVED without rewriting the evidence. The distinct baseline-classification rule below may instead establish KNOWN_BASELINE_FAILURE; it preserves the same raw FAILED result and never turns it into PASS. Revocation/expiry restores the underlying FAILED blocker. A waiver of unavailable evidence does not cover a later actual FAILED result unless the owner grants a new waiver explicitly referencing that failure and the profile permits it. Candidate/profile changes require the already-defined new-candidate/new-cycle handling; evidence is never relabelled across cycles.
259: 
260: Independent verification executions, including human-operated external CI/test jobs, must be registered with logical check/run identity, exact candidate/context, authorised producer, finite deadline and allowed execution count BEFORE launch. Each required check has one initial verification execution per candidate; a safely recoverable infrastructure replacement may use Q3's configured cycle-wide allowance. A check intent blocked before registration/launch retains its unused initial allowance and follows the explicit pre-launch escalation/resolution rows in §3. Supplying configuration is not a rerun: once restored and control resumed, the initial launch is allowed. This exception requires proof no launch occurred; an ambiguous external launch remains a recovery/quarantine case, never a fresh initial execution. A real FAILED check is not eligible for a SAME-CANDIDATE rerun to clear failure, including owner-supplied reruns. A registered diagnostic comparison may collect additional evidence under Dmax without replacing that FAILED result. A Q6 correction creates a new candidate and new check obligations within the same cycle. Pre-registered independently produced evidence can be attached later without a second launch; unregistered rerun PASS is diagnostic only and cannot satisfy a gate or clear escalation. Owner UAT observations are separately authorised acceptance-phase evidence, not a way to relabel a failing executable check. Developer self-tests are claims, not authoritative verification; additional scratch diagnostics cannot discharge a gate.
261: 
262: Every authentic required-check failure received for the same candidate is retained and investigated; external evidence cannot be cherry-picked to hide a prior registered failure. Unexpected/conflicting output triggers escalation, not promotion. Resolving missing/BLOCKED artifacts with existing evidence means retrieving output from the SAME authorised execution, not accepting an unlimited sequence of new external jobs. Any legitimate Q6 fix creates a new candidate and its initial check executions; it resets none of the cycle-wide review, correction, diagnostic or replacement counts. Detailed check selection remains O-005, but these accounting rules apply to every selected check.
263: 
264: ### Baseline-aware verification classification — direction accepted in A-008
265: 
266: Only a valid authenticated assertion result can enter this classification. Preserve raw FAILED separately from the effective disposition: CANDIDATE_DEFECT, KNOWN_BASELINE_FAILURE or UNRESOLVED. No disposition changes a review verdict. For new or modified tests/check definitions/fixtures relative to pinned B1, failure is a candidate defect (test or product); no baseline exception. Scope-changing or unsafe test modifications escalate instead of permitting a weaker contract.
267: 
268: For an unchanged existing test, compare candidate H against the exact pinned base B1, not current main. The pinned profile must define check identity, trusted comparison verifier, environment/dependency/configuration/command equivalence, failure fingerprints and finite repeat protocol. Candidate and baseline run in isolated read-only worktrees with separate scratch space and no owner credentials. Register every diagnostic before launch, including baseline SHA, candidate comparison key, environment and protocol digest, deadline, role and D ordinal. Admit the ENTIRE finite protocol only if remaining D capacity covers it; otherwise escalate as inconclusive. Diagnostics may launch only in VERIFYING/ACTIVE, never PAUSED/ESCALATED/RECOVERING/QUARANTINED. Duplicate requests reuse their recorded intent; no fresh free diagnostic per delivery/restart. A recoverable diagnostic infrastructure replacement consumes R under Q3 without inventing another initial D slot; exhausted/unsafe failure escalates.
269: 
270: Authenticated retained baseline evidence may be reused only if the complete pinned comparison key/protocol matches, all required samples are present and the profile's freshness/eligibility holds; unrelated main/CI failures are not evidence. Baseline PASS with candidate FAIL is a regression and uses Q6. Different failures, flaky/inconsistent samples, unsupported equivalence, unavailable baseline or failed protocol are UNRESOLVED; no optimistic exception. Bounded diagnostics can clarify only within the predeclared protocol/D allowance; exhaustion escalates without a discretionary model retry loop. A single baseline failure is not sufficient evidence for known flaky behaviour. Runtime failure is never an assertion-equivalence result.
271: 
272: KNOWN_BASELINE_FAILURE requires the full protocol to prove equivalent pre-existing failure, the profile explicitly permitting the target check's exception, no evidence of worsening/new failure, no relation to a behaviour this contract must fix, and no loss of meaningful verification of this work. Non-waivable safety/security/authority gates cannot use it. Verification records the evidence-based classification; an agent cannot grant it by assertion. If the check lacks a trustworthy automated equivalence/impact decision rule, mark UNRESOLVED for owner disposition rather than silently delegating authority to an LLM.
273: 
274: Before the exception satisfies a gate, atomically create/link a durable local known-issue record (stable dedupe key for check/failure/environment lineage) with both evidence sets, B1/H, policy/protocol, impact rationale and affected candidate. External tracker sync may be deferred; absent local tracking blocks advancement. Preserve every association, no duplicate issue per rerun. KNOWN_BASELINE_FAILURE is visible in the acceptance package and never reported as PASS or HUMAN-WAIVED. Re-evaluate the classification for each new candidate; evidence conflict, withdrawn exception authority or expiry before acceptance invalidates it and escalates. Post-acceptance invalidation blocks handoff under §7.
275: 
276: While non-escalated PAUSED or RECOVERING, valid assertion failures follow §3's pending-quality routing: record evidence without dispatch, then classify/apply Q6 only upon the defined ACTIVE-return transition. While delivery is already ESCALATED, valid failures are recorded as blockers under the sibling rule; no automatic diagnosis or worker dispatch. Existing authenticated evidence can support a permitted known-baseline resolution via the non-execution blocker-resolution row, with the full guard above and normal blocker recomputation/resume. A true candidate defect already escalated requires owner waiver where permitted or a child cycle, not a delayed automatic correction. Failure while ACTIVE with correction eligibility is not first escalated just to immediately bypass an escalation.

278: ### Evidence phases
279: 
280: The work/profile assigns every criterion/check to a phase before readiness; no mandatory check may silently shift to a later phase.
281: 
282: - **Pre-review:** executable build/tests, applicable security/a11y/performance/visual checks, approved design references, implementation design comparison and runnable demo/walkthrough instructions. Required evidence must PASS, be explicitly permitted HUMAN-WAIVED or satisfy the full KNOWN_BASELINE_FAILURE guard before standard dispatch and remain current thereafter.
283: - **Review-stage:** required standard/adversarial verdicts and structured findings, produced by their respective independent reviewers. These cannot be demanded as inputs to their own stage. Each stage requires all earlier-phase evidence.
284: - **Acceptance-stage:** owner or named authorised human's hands-on observations/UAT and explicit disposition. Before review, the contract must name the procedure, candidate fixture and observer role; the actual human observation may be pending until AWAITING_ACCEPTANCE. No automated test obligation can be replaced by calling it UAT.
285: 
286: In AWAITING_ACCEPTANCE, the controller may attach authenticated human observations and assemble the package without changing code/context. Missing acceptance-stage observations keep the cycle in AWAITING_ACCEPTANCE with an incomplete package and no approval. A failed mandatory human observation escalates; missing/invalid earlier-phase evidence discovered here also escalates. Passing observations leave the stage unchanged until explicit owner approval. Record each attachment/outcome in the ledger. An agent may format or attach evidence, but cannot impersonate the human observer or infer acceptance.
287: 
288: Workers can author tests and report results; independent verification inspects the actual commit and required artifacts and reruns checks or validates trusted CI provenance. Runtime output alone is not a trusted test attestation. Runtime/model/skill versions are attribution metadata, not proof.
289: 
290: Mandatory evidence key: repository + contract/spec versions + cycle + policy/profile versions + head/base SHA + execution environment/check definition. Artifact references must resolve to retained content with a recorded digest. A mutable URL, success-shaped JSON or exit code zero is insufficient. Preserve FAILED, BLOCKED, HUMAN-WAIVED and KNOWN_BASELINE_FAILURE distinctly, including raw results behind effective dispositions.
291: 
292: Each Done when criterion maps to an executed check or explicit human observation. UI-sensitive work needs the approved UX artifact and comparison; backend/docs work records justified N/A rather than invented screenshots. A PASS reviewer cannot waive absent tests, accessibility/security requirements or design approval. Reviewers use separate fresh contexts and read-only candidate access; test writes go to isolated scratch space, not the candidate branch. Independence requires separate executions, not necessarily different vendors/models.
293: 
294: The acceptance package includes outcome, criterion matrix, current evidence, all review/correction/replacement/diagnostic histories and counters, known-baseline failures and issue links, finding dispositions, demo/walkthrough, design conformance, risks and release notes. Owner acceptance is a structured command bound to this package digest and exact candidate, never inferred from chat or absence of objections. Findings persist with confirmed/rejected/duplicate/uncertain dispositions. A finding disposition change alone does not rewrite a failed verdict or resume an escalated cycle.
295: 
296: Human acceptance binds to the package/candidate. A post-acceptance branch change blocks merge handoff and records approval invalidation without rewriting history. A merge/squash commit with a different identity requires integration evidence for the actual merged artifact before release readiness; approval of a PR is not evidence of successful deployment.

298: ## 6. Durability, dispatch and recovery
299: 
300: SQLite transactions must atomically persist guarded state updates, event/dedupe records, reservations/counters, lease generation and external-action intents. Use state-version compare-and-swap and unique constraints for event keys, accepted results and active ownership. Transaction rollback leaves neither a consumed counter nor a half-transition.
301: 
302: Starting an external process is not atomic with SQLite. Persist an intent with a stable dispatch key before launching; attach the returned run/process identity afterward. On restart, reconcile unresolved intents before launching anything else. Adapter/launcher must prove lookup/deduplication by that dispatch identity, or the ambiguous launch is quarantined for human containment—not blindly repeated. Exactly-once external launch is not claimed merely because the database is transactional.
303: 
304: Lease generation fences controller/result acceptance, **not filesystem writes by a rogue/stale process**. Lease expiry alone does not grant a new writer. Confirm the prior process and descendants have stopped and write access is contained before handing over the branch/worktree. If the selected runtime cannot establish that, quarantine the workspace/branch and block reassignment. A new worktree alone is not proof that the old process cannot write the repository.
305: 
306: Restart reconciliation checks intents, processes, lease generations, branch heads/bases, artifacts, accepted verdicts and pending external sync. Duplicate webhooks wake reconciliation; they do not grant ownership. Persist a logical action key for GitHub publication and discover an existing PR before retrying an ambiguous publish. Notifications and PR sync failures cannot reset quality counters or allow duplicate development.
307: 
308: Operator controls: pause prevents new dispatch; shutdown/cancel attempts bounded termination; uncertain containment quarantines affected work. Resumption rechecks eligibility and evidence. Worker-reported policy changes, secrets requests and forbidden destinations are rejected outside the worker prompt. Precise OS confinement and launcher mechanisms remain implementation/spike obligations, not solved by this design prose.

310: ## 7. Separate release handoff
311: 
312: Delivery ACCEPTED creates a separate merge-handoff record in `PENDING`; it is not permission to merge automatically. Initial merge authority is proposed as owner-only/manual and must be approved before SF-002E is READY (O-006). The record binds the accepted cycle, H1, target tip B1, approval and integration-check definition. Handoff transitions:
313: 
314: | From / actor | Guard / evidence | To / effect |
315: | --- | --- | --- |
316: | PENDING / controller detects drift, revoked authority, expired waiver or result conflict | Head differs from H1, target differs from B1, or context validity lost; record observation | INVALIDATED; no merge; accepted delivery history unchanged |
317: | PENDING / owner authorises and performs manual merge | Revalidated H1/B1 and pinned authority/evidence; protected or atomic expected-target update; record actor/action and actual merge identity M1 | MERGED; create release record from M1 |
318: | PENDING / operator cannot prove atomic target check or merge provenance | Record missing proof; do not rely on a prior non-atomic tip check | INVALIDATED; no authorised merge; any externally observed merge is quarantined from release eligibility pending human reconciliation |
319: | INVALIDATED / owner authorises revision | Explicit Q1 decision; expected work tip is accepted parent, no existing child; containment/result reconciliation complete | Atomically set handoff REVISED with unique child link, transfer work tip to PREPARING child `(0,0)`; parent stays ACCEPTED. Same decision replay returns child; different decision against old parent rejected |
320: | PENDING or INVALIDATED / owner declines merge | Exact handoff decision; no merge action in flight; containment/provenance reconciled | CLOSED; preserve acceptance history, release live-delivery slot; no merge. Later reopening requires explicit child decision and same unique-child/tip guard, atomically CLOSED→REVISED |
321: 
322: Base drift always invalidates BEFORE merge; integration tests are not a substitute for reviewed B1. A merge/squash M1 generated solely from the authorised H1 and unchanged B1 is a legitimate new identity, not a revision: preserve lineage, verify the actual integration artifact and required checks before RELEASE_READY. If an external manual merge used changed inputs, record the fact but block release readiness; do not call it a valid handoff. Runtime/API atomic merge enforcement is later work and blocks merge automation, not this design-only review.
323: 
324: Record actual merge identity and create a separate eligible release record only after the authorised merge is verified. Proposed release states follow the source: `MERGED` → `RELEASE_READY` → `STAGING_VALIDATED` (when configured) → `AWAITING_RELEASE` → `DEPLOYED` → `POST_DEPLOY_VERIFIED`, with `FAILED`/`ROLLED_BACK` alternatives.
325: 
326: Each release record binds environment, immutable artifact/version, operator, approvals, configuration/migration notes, smoke checks and rollback/forward-recovery procedure. Missing required staging evidence blocks; a permitted skip needs explicit policy rationale. Production execution stays disabled in this initial design. Documentation-only changes record “no deployable artifact” and applicable N/A, not a fictional DEPLOYED status.
327: 
328: Release failures create incident/escalation evidence and new tracked fix work; they neither consume nor replenish the delivery review budget. Product outcome observation is separate from technical deployment success and may return work to discovery.
