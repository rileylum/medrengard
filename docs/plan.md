## What the engine must allow for

Rows 9 and 10 are built with the later rows and open questions in view (A-055), so each later feature is a workflow, a step or an extension, not a change to the engine. What each one needs from the engine:

| Later work | Needs from rows 9 and 10 |
| --- | --- |
| Recovery (row 11) | A driver that resumes a cycle from its stored stage, not only from the developer run. Runs recorded as started, so an orphan can be found. A crashed run escalates; no relaunch budget for now (A-105) |
| Tracker and code host (row 12) | Human decision steps that an outside source can settle (a merge on GitHub becomes `accept`). Capability grants, so a merge or deploy extension can hold credentials that no agent sandbox sees (O-016) |
| Role prompts and skills (O-013, O-014) | Prompts and skills attached to agent steps in the workflow, not written in `developer.ts` and `review.ts`. The prompt split in two: the controller's contract (claim format, SHAs, delimiters), which the core owns, and the role's judgement text, which the workflow owns. A content hash of each recorded on the run. Live run 2026-10-20 (`/var/tmp/software_factory/live-1/`) found two gaps in today's wording. First, the developer's contract says "commit it" but not which git commands it may run (only `git add`, `commit`, `status` and `rev-parse`). Run 2 wrote the change, did not commit, and claimed the base SHA; the likely cause is a commit through `$(cat <<EOF …)`, which the allow list denies. Second, the reviewer prompt shows a check's exit and output but not the command it ran (fix it in this row, so the contract hash changes once; A-112). Run 1's reviewer read a silent check's `exit 0` as the script's own exit and failed a correct change; the developer disputed, and the cycle escalated |
| Acceptance evidence (A-051, O-015) | Steps that compose: an agent step writes a script, a controller command step runs it at the SHA. A rerun budget per step. Artifacts stored under `evidence/<head>/` . Use case to support (A-112): a verdict step attaches a script, a command step runs it at the SHA, and a finding whose script passes is downgraded, so an adversarial FAIL is shown, not argued |
| Structured findings | Data passed between steps through the workflow (a review's findings into the fix step), not hard-coded in `fix()`. A-109: findings with severity, scenario and action; other structured inputs and outputs across the core; a workflow or extension may declare a step's input and output shape |
| Pools | A driver per cycle with no shared state, so several cycles can run at once. Open, no direction (A-112): one process per cycle, or one process for many, which needs async `accept`, `receive` and `land`, because the controller's git is synchronous and blocks every cycle's timers up to a stage deadline (`docs/research/2026-10-20/architecture.md` finding 9). Pi's shared `auth.json` matters under concurrent runs (A-068). From treehouse: lease IDs released only by compare-under-lock, and quarantine of a slot that cannot be verified (`harnesses.md` finding 8). Row 13 researches and compares afresh |
| Improvement loop and metrics | The observation stream, and step and run timings in the event log. Each run's raw runtime output kept under `runsDir`: live run 2026-10-20 could not show why the developer did not commit, because claude runs with `--no-session-persistence` and nothing keeps its stdout or stderr |
| Run records (A-111, soon) | `run_failed` records a cause (infra, limit, output); each run records cost, tokens, model and CLI version; `claude` gets turn and budget caps. Also each run's raw runtime output, kept under `runsDir` (the Improvement loop row's gap; A-112). The data for tuning the workflow from logs, and what a later relaunch would key on (A-105) |
| JSON workflows (A-111, soon) | A workflow loads from JSON; a repository's workflow must be data, so no repository code runs in the controller (closes A-078) |
| Protocol version (A-111, soon) | `protocol: 1` on RunRequest, `request.json` and events |
| Extension extras (A-112, after the protocol version) | `runtimes.<name>.network`, default `true`; `src/kits/` bound read-only at `/sf/kits` in every command and runtime sandbox, with a `serve()` helper; the path versioned with the protocol |
| Owner tools (A-111) | A `doctor` command (sandbox, runtimes, programs, and which layer set each config key); a `status` command; job-file errors that name each bad field; a warning at `accept` when the base moved |
| Guide stand-ins (A-112, low priority) | One dedicated ticket: `replayRow` (stream.ts), `fixInput` (developer.ts) and `openRefusal` (store.ts) split out without I/O, and `learn/` imports them instead of copying. The guide is experimental; core tickets do not carry this |
| Housekeeping (A-111) | Clone and checkout cleanup after `accept` or `cancel` (562 MB per cycle on a 508 MB repository); a size cap on what `land` fetches into the owner's repository, measured in the clone before the fetch, default 100 MB, set in the job file (A-112); faster tests (split `developer.test.ts`, the runtime kit's fixed wait) |
| Release tracking and deployment (O-009) | Command stages after acceptance, with grants |
| Design Studio (O-012) | Stages with no candidate yet. The SHA guarantee applies to steps that produce evidence about code |
| herdr frontend (O-010) | The observation stream drives the board. An owner's message to an agent is recorded as an event that later steps can see |
| Configuration | Layers: factory defaults, personal, repository, job |

Measure as you go: stage waits, manual interventions, review attempts, confirmed defects. Automate the next most repeated manual step.
