First ticket: one driver entry point, `drive`, `src/decide.ts` and `main()` under `import.meta.main` (A-112, `architecture.md` finding 2). Same ticket (A-123): each row stores the stage `apply` produced as a checksum, and a mismatch on load refuses to drive the cycle and names the first row that diverged; the open row records an engine version; replaying a recorded workflow runs a light replay check, and the full `checkWorkflow` runs only on new cycles (`engine.md` P6). Fourth: an escalated cycle waits for the owner, who may retry, overrule (A-109 B), fix, accept with risk, route or cancel, before `recover` (A-114, A-115). Same ticket (A-123): `request_changes` carries `head`, checked as `accept`'s is, and every event from outside a run carries a `commandId` the store deduplicates; observers resend the same ID on retry (`engine.md` P2). Fifth: runs that outlive the controller; each run's output and exit code go to files in its run folder, kept by a supervisor that is not the controller (a systemd transient unit, or a one-line wrapper), so `recover` finds a started run still running (watch or stop), finished (received under its original run ID, no new spend) or gone (escalated, A-105). Adopting finished runs is the default; a "never adopt" setting keeps A-105 exactly (A-122; `docs/research/2026-10-20-foundations/runtime-process.md` proposals 4 and 7) Design inputs: A-105 and `docs/research/2026-10-20/` (harnesses finding 1, deep-research proposals 1 and 2). ## What the engine must allow for

Rows 9 and 10 are built with the later rows and open questions in view (A-055), so each later feature is a workflow, a step or an extension, not a change to the engine. What each one needs from the engine:

| Later work | Needs from rows 9 and 10 |
| --- | --- |
| Recovery (row 11) | A driver that resumes a cycle from its stored stage, not only from the developer run. Runs recorded as started, so an orphan can be found. A crashed run escalates; no relaunch budget for now (A-105) |
| Tracker and code host (row 12) | Human decision steps that an outside source can settle (a merge on GitHub becomes `accept`). Capability grants, so a merge or deploy extension can hold credentials that no agent sandbox sees (O-016). A-113: an extension point decides which ticket may start next and when; the default policy refuses a new cycle while K cycles wait on the owner (AWAITING_ACCEPTANCE or ESCALATED), and an owner may replace it. Confirmed by the research (`harnesses.md` finding 8): read config from the default branch (A-095, A-100); never auto-merge; the tracker credential stays on the host (grants). The dispatch extension point takes the decision shape (A-124): a pure function, JSON in and out, sandboxed with no network, grants or writes and a short deadline; its answer is recorded as an event so replay never re-asks. The default rule stays a number in config (`extend-config.md` proposal 7; widens D-024 to three shapes) |
| Role prompts and skills (O-013, O-014) | Prompts and skills attached to agent steps in the workflow, not written in `developer.ts` and `review.ts`. The prompt split in two: the controller's contract (claim format, SHAs, delimiters), which the core owns, and the role's judgement text, which the workflow owns. A content hash of each recorded on the run. Live run 2026-10-20 (`/var/tmp/software_factory/live-1/`) found two gaps in today's wording. Run 1's reviewer read a silent check's `exit 0` as the script's own exit and failed a correct change; the developer disputed, and the cycle escalated. A-113: a runtime entry may name a model or extra arguments (the job file's `model` key is ignored today), and a test proves a workflow with a second commit stage under its own role and runtime (for example a stronger model for the last fix); the default workflow keeps one developer Runtime entries as data (A-120): `runtimes.<name> = { base, model?, effort?, args?, network?, env? }`; a knob a runtime cannot express fails at load; the repository layer may name a runtime per role but never define runtimes, models or arguments (`extend-config.md` proposal 5) |

Claims through each CLI's schema option (A-116): claude `--json-schema`, a terminating `submit_claim` tool for pi; the fenced block stays as the fallback, and `apply` still validates (`runtime-process.md` proposal 3).
